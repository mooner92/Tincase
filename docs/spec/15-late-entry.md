# 15. 늦게 낸 사람 — 담당자가 대신 쓰고, 병합본 맨 뒤에 붙인다

상태: **구현 중 (2026-10-15)** · 접두사 `LE`
관련: [ADR-0023](../adr/0023-late-entry.md) · [TACP-18·22](../../TACP.md) · [08 병합 엔진](08-hwp-merge-engine.md)(HM-47·49·59) · [10 웹 작성](10-web-authoring.md)(WA-20) · [12 본부·전사 취합](12-org-rollup.md)(ADR-0015·0021)

> ⚠ 공개 저장소다. 사람 이름은 쓰지 않는다 — 역할로만 적는다.

---

## 0. 요구와 결정 (2026-10-15 운영자)

- 「혹여라도 늦게 내는 분들 내용을 담당자들이 임의로 추가할 수 있게 — 그 사람 계정이 올린 것처럼.」
- 「병합이 끝났을 때 추가를 원하면 병합본(혹은 승인이 끝난 본부·전사본) **맨 뒤에** 붙이고, **다시 병합하지 않게.** 조정해 놓은 것이 흐트러지니까.」
- 「지금은 늦게 낸다고 하면 중간에 추가하는 것이 너무 복잡하고 오래 걸린다.」

| 물음 | 결정 |
|---|---|
| 「그 사람 계정이 올린 것처럼」 | 주인(`userId`)은 **그 사람**이다 — 현황·병합·이력이 그 사람이 낸 것으로 읽는다. 쓴 사람(`editedById`)과 `origin = 'lead_entry'`가 **같은 행에** 붙는다(TACP-18 v1.17) |
| 누구를 대신 쓰나 | **이번 주에 아무 판도 없는 같은 부서 부서원**만. 낸 사람의 것은 [고치기](TACP-22) |
| 마감 | 보지 않는다. 마감 열기(DM-20)와는 별개다 |
| 병합 뒤라면 | **병합본 맨 뒤에 붙인다** — 이미 있는 행은 한 글자도 건드리지 않고, 다시 병합하지 않는다 |
| 승인 | 붙이기는 **승인이 아니다**. 승인한 판이 바뀌면 부서장에게 NT-52 「다시 승인」이 간다 |
| 본부본·전사본 | 손대지 않는다 — 단위본이 바뀌면 기존 자동 재결합(ADR-0015·0021)이 따라간다 |
| 병합 뒤에 **고쳐 낸** 사람 | 붙이지 않는다(앞서 들어간 줄과 겹친다) — 지금처럼 [다시 병합] |

## 1. 대신 쓰기

```
POST /api/submissions/proxy        (JSON)
{ "userId": "c…", "isoKey": "2026-W42", "achievements": [...], "plans": [...], "notes": [...] }
→ 200 { ok: true, id, version: 1, rows: { achievements, plans, notes } }
```

본문의 표는 웹 작성(`/api/submissions/compose`)·첨삭(`PUT /api/submissions/:id/content`)과 같은 모양이다(`DocInput`).

- LE-01 **누가**: `isManager`(자기 부서의 lead·head) — 게이트 `requireProxyTarget(scope, userId)`. member·coordinator·타 부서 담당자·자기 부서의 lead·head가 아닌 운영자는 404(TACP-5)
- LE-02 **누구를**: **같은 부서 · 활성 · 본인이 아닌** 사람. 부서는 신원에서 나오고 대상은 사람 id뿐이다(TACP-6). 다른 부서의 사람·탈퇴자·없는 id·**자기 자신**은 404 — 존재 여부를 알리지 않는다
- LE-03 **언제**: 그 주차에 그 사람의 **판이 하나도 없을 때만**. 있으면 409 `already_submitted` — 낸 판을 새로 만드는 길이 되면 [고치기]의 「남의 것만 · 최신 판만」이 우회된다. 판단은 **트랜잭션 안**에서 한다(두 담당자가 동시에 눌러도 하나만 쓴다)
- LE-04 **어느 주차**: 본문 `isoKey`의 주차(수합 관리에서 보고 있는 주). 없는 주차는 404, `isoKey`가 없으면 422 `invalid_request`
- LE-05 **마감**: 보지 않는다(TACP-22와 같다). 쓴 사람이 담당자라는 것은 이름으로 남는다(LE-07)
- LE-06 **문서 만들기**: 부서 양식 + `buildWorklogHwp`(웹 작성·첨삭과 **같은 길**) — 빈 내용은 422 `empty_content`, 칸이 길면 422 `cell_too_long`, 양식이 없으면 409 `no_template`. 판의 모습은 그 사람이 웹으로 낸 것과 구별되지 않는다
- LE-07 **기록**: 새 판 v1 — `userId` = 그 사람 · `origin = 'lead_entry'` · `editedById` = 쓴 사람 · `editedAt` = `uploadedAt` = 쓴 시각(「언제 냈나」는 쓴 시각 — 늦게 낸 것은 사실이다) · 파일 경로는 **그 사람 기준** 꼬리 `p<무작위 8자>`(동시 요청이 서로의 파일을 덮거나 지우지 않게)
- LE-08 **파일 먼저, DB 나중**(첨삭과 같다 — `reviseSubmission`의 근거): 트랜잭션이 실패하면(409 포함) 먼저 쓴 파일을 지운다. 남아도 되는 것은 가리키는 곳 없는 파일이지 파일 없는 레코드가 아니다
- LE-09 **감사**: `submission_proxy` — actor는 **쓴 사람**, 대상 사람·주차·판 번호가 `detail`(TACP-10)
- LE-10 **알림**: 대신 쓴 사람에게는 보내지 않는다(열면 보인다). 낸 사람이므로 이후 마감 알림 대상에서 빠진다(NT-31의 「제출」 판정이 그대로 — 최신 판이 있다)
- LE-11 **속도 제한**: `proxy:<이메일>` 30회/분 — 게이트 뒤에서 건다(권한 없는 요청이 제한을 먼저 소모하지 않게)
- LE-12 **본인에게 보이게**(TACP-9): 「담당자 대신 입력」을 이번 주 카드 · 지난 주 이력 · 제출물 드로어에 적는다. 열면 「○○ 입력 · 시각」. 표시의 근거는 판의 `origin`과 `editedById` 하나뿐이다
- LE-13 **본인이 나중에 낸다면**: 평소처럼 본인의 새 판(v2)이 된다 — 대신 쓴 판은 이력에 남는다. 담당자가 병합 뒤에 이 사람의 판이 바뀐 것을 보면 LE-31(고쳐 낸 사람)로 분류된다

## 2. 병합본 맨 뒤에 붙이기

```
POST /api/division/merged/append   (JSON)
{ "isoKey": "2026-W42", "runId": "c…", "sha256": "…" }   // runId·sha256 = 화면이 본 판 (GET merged/content가 준 그대로)
→ 200 { ok: true, appended: [{ name, achievements, plans, notes }], skipped: [{ name, reason }], rowCounts, runId, sha256 }
```

- LE-20 **문**: `requireOwnManager` — 병합본 수정(API-50)과 같은 칸이다. 새 권한이 아니다. 부서는 신원에서 나온다(본문에 부서 없음, TACP-6). 인증·역할 판정이 본문 검사보다 먼저다(API-50a)
- LE-21 **누구를 붙이나**(`splitLate`): 그 부서·주차의 **최신 제출** 중 `MergeRun.sourceIds`에 없는 것.
  - **늦게 낸 사람** — 그 사람의 어느 판도 `sourceIds`에 없다 → 붙인다
  - **고쳐 낸 사람** — 앞선 판이 `sourceIds`에 있는데 최신 판은 없다 → 붙이지 않는다(LE-31)
- LE-22 **줄 수집은 병합과 같다**: 표별 행을 읽고(`readWorklog`) 글로 적은 강조 표시를 뗀다(`stripEmphasisMarker` — HM-38). 사람 순서는 `orderPeople`(명단 순 — 병합과 같다). 읽을 수 없는 파일은 **그 사람만** 건너뛰고(경고 `skipped`) `sourceIds`에 넣지 않는다 — 다음에 다시 붙일 수 있다(HM-21과 같은 방침)
- LE-23 **붙는 자리**: 각 표의 **끝**. 구분 번호는 시스템이 다시 매긴다(ABS-5 — 기존 행의 번호는 그대로 `n-1…n-k`이므로 이어서 `n-(k+1)…`). 모델·분류·중복 묶기는 돌리지 않는다 — 「조정해 놓은 것이 흐트러진다」가 문제이므로
- LE-24 **같은 줄**: 기존 행과 **네 칸(내용·일자·장소·참석자)이 trim 뒤 모두 같으면** 새 줄을 만들지 않는다. 그 줄의 작성자(`rowAuthors`)에 이름만 더한다. 글자 하나라도 다르면 붙인다(HM-36의 「잃는 쪽이 늘 더 나쁘다」)
- LE-25 **기존 행 불변**: 지금 병합본 파일에서 읽은 행(+강조)을 그대로 양식에 다시 쓴다(`composeMergedHwp` — HM-27, 수정 저장과 같은 길). 쓰기 전에 기존 행만으로 만든 문서와 기존+신규로 만든 문서의 **앞부분이 같은지** `worklogRows`로 다시 읽어 확인하고, 다르면 쓰지 않는다(500 `append_failed`). 담당자가 순서를 바꾸고 문장을 고친 것이 그대로 남는다는 약속이다
- LE-26 **강조**: 기존 행의 강조(파란색)는 그대로, 붙는 행의 강조는 그 제출의 강조 서식 또는 글로 적은 표시(`stripEmphasisMarker`)를 따른다
- LE-27 **기록**: `MergeRun`에
  - `sourceIds` ← 기존 ∪ 붙인 판 id (LE-29가 이것 하나로 풀린다)
  - `rowCounts` · `outputSha` · `finishedAt` ← 새 파일 기준(HM-56e)
  - `reviewJson.rowAuthors[표]` 끝에 `{ c, a: [이름] }` · `reviewJson.missing`에서 붙인 사람 제거 · `reviewJson.appended` ← `{ at, people: [이름], rows }`(기록용)
  - `reviewJson.edits`에 한 줄 — `{ by: 쓴 사람, role: unitEditorRole(scope), at, places: 붙인 행 수 }`. `places > 0`이므로 [다시 병합]은 HM-49가 먼저 묻는다
- LE-28 **잠금·판**: `withUnitLock` 안에서 최신 성공 실행을 다시 읽고 `requireViewedVersion`(409 `merged_changed`)으로 **화면이 본 판**을 확인한다 — 연 뒤에 누가 저장·병합했으면 붙이지 않는다. 병합 작업이 줄에 있거나 돌고 있으면(`activeMergeJob`) 409 `merging`(곧 새 병합본이 된다)
- LE-29 **「늦게 낸 n명」이 풀린다**: `sourceIds`가 늘었으므로 HM-34 늦은 제출 세기·NT-40/51/52·merge-batch·수합 관리의 `sourceCount`·`lateSinceApproval`이 같은 기록을 보고 같이 풀린다 — 따로 고칠 곳이 없다
- LE-30 **승인이 아니다**: head가 붙여도 `MergeReview`를 만들지 않는다(HM-47 「저장 = 승인」과 다르다 — 수정 저장은 검토한 것이고, 붙이기는 기계가 더한 것이다). 잠금 밖에서 `onUnitVersionChanged(…, { reason: { kind: 'append', people: n } })` — 이유 문구는 「늦게 낸 n명이 맨 뒤에 붙었어요」. 승인한 판이 있고 기한 전이면 부서장에게 NT-52 「다시 승인해 주세요」(붙인 사람이 head 본인이면 그 사람은 제외 — 알릴 필요가 없다. 받을 사람이 없으면 알림 기록도 남기지 않는다). 기한 뒤이거나 부서장이 없는 단위는 기존 규칙대로 단위본이 따라 올라간다(RU-72 · ADR-0021)
- LE-31 **고쳐 낸 사람**은 붙이지 않는다. 앞서 들어간 그 사람의 줄과 겹쳐 같은 일이 두 번 나온다. 화면은 「고쳐 낸 n명은 다시 병합해야 해요」로 따로 알린다(CP-135). 후보가 없고 고쳐 낸 사람만 있으면 409 `nothing_to_append`가 아니라 같은 코드에 `detail.revised`를 싣는다
- LE-32 **본부·전사본**: 이 요청은 단위본만 고친다. 위 문서는 단위본을 이어 붙여 만든 것(ADR-0015)이므로 새 경로도 새 읽기도 없다(TACP-14 · 15). 붙은 줄은 그 단위 구간의 끝에 놓인다
- LE-33 **감사**: `merge` / `detail.action = 'append'` — 붙은 사람 수·행 수. 이름은 담지 않는다(감사 로그는 운영자가 본다 — 이미 `submission_proxy`에 있다)
- LE-34 **속도 제한**: `merged-append:<이메일>` 20회/분(게이트 뒤, 본문 앞)

## 3. 화면

- LE-40 **수합 관리 · 제출 현황**(CP-131): 미제출 행에 [대신 쓰기](`canProxy` — 서버가 내려준 값, `canProxySubmit`과 같은 식). 누르면 오른쪽 서랍(CP-132)에 **빈 작성 화면**이 열린다 — 이름이 머리에 있고 「○○님 대신 입력」이라 적힌다. 저장하면 행이 제출로 바뀐다
- LE-41 **서랍의 작성기**(CP-133): 웹 작성 화면(`SubmissionEditor`)을 그대로 쓴다. 저장 엔드포인트와 버튼 문구만 다르다(`proxy` 모드 — [대신 입력 저장]). 낸 사람의 [고치기]와 한 부품이다 — 두 곳이 따로 만들면 칸 규칙(HM-39·42)이 갈라진다
- LE-42 **병합 패널**(CP-134): 병합본이 있고 늦게 낸 사람이 있으면 「늦게 낸 n명」 안내와 [맨 뒤에 붙이기] — 누른 뒤 무엇이 붙었는지(이름·표별 줄 수)를 한 줄로 알리고, 병합본 보기가 갱신된다. 문구는 「다시 병합하면 손본 곳이 사라지니 **맨 뒤에 붙입니다**」를 먼저 말한다(두 길 중 안전한 쪽이 앞)
- LE-43 **고쳐 낸 사람**(CP-135): 같은 자리에 「고쳐 낸 n명은 다시 병합해야 해요」 — [다시 병합]은 그대로(HM-49 확인 포함)
- LE-44 **본인 화면 셋**(CP-136): 이번 주 카드 · 지난 주 이력 · 제출물 드로어의 머리에 「담당자 대신 입력」. 근거는 `origin === 'lead_entry'` 하나
- LE-45 **버튼은 서버와 같은 식으로**: [대신 쓰기]·[맨 뒤에 붙이기]의 노출은 `canProxySubmit`·`requireOwnManager`와 같은 판정이다(TACP-9). 화면이 보이는데 저장이 404인 일이 없다

## 4. 하지 않는 것

- 낸 사람의 판을 대신 쓰기로 덮어쓰지 않는다 — [고치기]다
- 붙이는 줄을 모델로 묶거나 분류하지 않는다 — 끝에 붙인다. 필요하면 담당자가 수정 저장(HM-47)에서 옮긴다
- 대신 쓴 사람에게 알림을 보내지 않는다
- 위 문서(본부·전사)에 따로 붙이지 않는다
- 승인을 대신하지 않는다
