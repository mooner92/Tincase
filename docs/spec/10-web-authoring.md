# S-10. 웹에서 작성·수정·제출 — **Phase 2 이후**

> 상태: **구현됨 (v1.5.0).** 제출 경로 완성. 서버 초안(WA-03)과 이전 주차 불러오기(WA-07)는 미구현 —
> 지금은 브라우저에 임시 보관만 한다 (새로고침으로 잃지 않는 수준).
> 사용자 요구 (2026-08-14): *"사이트에서 수정하고 보고 제출하고 이런 게 됐으면 좋겠고."*

---

## 1. 무엇이 바뀌나

현재(v1.x)는 **파일 왕복**이다. 이 스펙은 그걸 **웹 작성**으로 대체한다.

| | 지금 (v1.x) | 목표 (S-10) |
|---|---|---|
| 작성 | 양식 다운로드 → 한글에서 작성 → 업로드 | 웹 표에 직접 입력 |
| 수정 | 파일 고쳐서 재업로드 (v2) | 화면에서 고치고 저장 |
| 확인 | 담당자가 드로어로 열람 | 동일 (이미 구현됨) |
| 제출물 | 사람이 만든 hwp | **시스템이 생성한 hwp** |

핵심: 드로어(읽기)는 **이미 있다.** 여기에 쓰기를 붙이면 웹 작성이 된다.

## 2. 의존성 — 왜 지금 못 하나 ★

웹 입력을 hwp로 만들려면 **writer가 필요하다**. writer는 Phase 2이고,
Phase 2는 [Q-01](../../OPEN-QUESTIONS.md)(생성한 hwp가 한글에서 정상적으로 열리는가)에 걸려 있다.

```
Q-01 확인 ──► writer (M12) ──► 병합 (M13~15) ──► S-10 웹 작성
                  └────────────────────────────────┘
                     같은 엔진. 병합이 "여러 명 → 1개"라면
                     웹 작성은 "폼 입력 → 1개"다
```

즉 **웹 작성은 병합의 부산물**이다. 병합 엔진이 서면 웹 작성은 대부분 이미 만들어진 것이다.

## 3. 요구사항

### WA-01 — 입력 모델은 기존 도메인 모델 그대로

`WorklogData { achievements, plans, notes }` (HM-14). 새 모델을 만들지 않는다.
드로어가 읽는 구조와 폼이 쓰는 구조가 같아야 왕복이 성립한다.

### WA-02 — 두 경로를 모두 유지한다 ★

> **2026-10-07 개정 — 업로드는 단계적으로 닫는다 (아래 WA-30~34 · [ADR-0014](../adr/0014-web-only-submission.md)).**
> 아래 표는 「업로드를 왜 바로 지우지 않고 스위치로 닫는가」의 근거로 남는다 — 특히 장애 시 폴백.

웹 작성이 생겨도 **파일 업로드를 없애지 않는다.**

| 이유 |
|---|
| 한글에서 표·서식을 쓰는 사람이 있다 (그림·강조 등 폼으로 표현 못 하는 것) |
| 장애 시 폴백 (OPS-18) |
| 기존 사용자의 습관을 강제로 바꾸지 않는다 |

부서원은 매주 둘 중 하나를 고른다: **[웹에서 작성]** 또는 **[파일 업로드]**.

### WA-03 — 저장은 초안(draft)과 제출(submit)을 분리

| 상태 | 의미 | 마감 영향 |
|---|---|---|
| `draft` | 작성 중. 언제든 수정 | 마감 후 수정 불가 |
| `submitted` | 제출됨. hwp 생성 완료 | 기존 Submission과 동일 (v1, v2…) |

초안은 자동 저장(디바운스 2초). "쓰다가 브라우저를 닫았다"로 잃지 않게.

### WA-04 — 제출 시 hwp를 생성해 기존 파이프라인에 태운다

```
폼 입력 → WorklogData → writer(부서 active 양식 기반) → hwp bytes
        → 기존 uploadSubmission()과 동일 경로로 저장 (검증·버전·감사 로그)
```

**결과물이 업로드된 파일과 구별되지 않아야 한다** — 담당자 화면·zip·병합이 그대로 동작.
`Submission`에 `origin: 'upload' | 'web'` 만 추가한다 (통계·디버깅용).

### WA-05 — 생성물도 자체 검증을 통과해야 한다

writer 출력을 **우리 reader로 다시 읽어** 입력과 일치하는지 확인한 뒤에만 저장한다 (HM-22 재사용).
불일치면 저장하지 않고 오류 — 조용한 손실을 만들지 않는다.

### WA-06 — 표 편집 UI

- 행 추가/삭제/순서 이동
- 열은 고정 5개 (구분은 자동 채번 — ABS-5)
- 셀 안 줄바꿈 허용 (HM-13이 이미 지원)
- 붙여넣기: 엑셀/한글 표에서 복사한 TSV를 여러 행으로 인식

### WA-07 — 이전 주차 불러오기

"지난주 계획을 이번주 실적으로" 가 실제 업무 패턴이다 (R-001 §5.3에서 확인).
**[지난주 계획 불러오기]** 버튼으로 `plans → achievements` 복사.

> 이 기능 하나가 웹 작성의 가장 큰 시간 절감일 가능성이 높다.
> 파일 왕복으로는 불가능하고, 웹에서만 되는 일이다.

### WA-10~13 — 「지난번에 낸 것」 패널 ★ (WA-07의 구현)

WA-07이 말한 「지난주 계획 불러오기」를 실제로 붙이면서 셋이 갈라져 나왔다.

| ID | 요구사항 |
|---|---|
| WA-10 | **「지난주」가 아니라 「지난번」**이다. 휴가로 걸렀으면 그 전 것을 보여준다 |
| WA-11 | 보여주기만 하면 절반이다 — **옮기는 버튼**까지 둔다 (줄마다 `＋`, 계획 전체 → 실적) |
| WA-12 | **주차를 고를 수 있다.** 목록은 미리 받고 **파일은 고른 한 건만** 읽는다 |
| WA-13 | 기본 **펼침**, 위치는 **본문 맨 위**, 모양은 **카드** |
| WA-14 | **직전 3주까지만**. 이번이 N주차면 N-1 · N-2 · N-3 |
| WA-15 | 줄마다 **넣을 곳을 고른다** — `+실적` / `+계획` |

**WA-12가 필요한 이유** — 「바로 전 주」 하나로는 세 경우에 무너진다:
휴가로 한 주 걸렀을 때 · 그 달 마지막 주(월간은 한 달치를 정리한다, WS-14) ·
몇 주 전 표현을 그대로 다시 쓰는 상시 반복 업무.

**WA-13은 두 번 틀리고 나온 것이다.**

처음에는 접어서 안내 띠들 사이에 뒀다. 근거는 「펼쳐 두면 쓸 칸이 아래로 밀린다」였는데,
실제 반응은 이랬다:

> 「가독성이 너무 떨어져서 이런게 있는지도 잘 모르겠어 … 디폴트로 접혀있어서 확인도 어려워」

접힌 것만 문제가 아니었다. 이 드로어 위쪽에는 띠가 연달아 셋 있다 —
붙여넣기 안내(초록) · 작성 안내(회색) · 그리고 이것(회색). 셋이 같은 모양이면
눈이 「또 안내문」으로 읽고 건너뛴다. 그래서 **카드**로 바꿨다:
흰 바탕 + 테두리 하나면 평평한 띠들 사이에서 저절로 도드라지고,
색을 더 쓰지 않으므로 정작 써야 할 표보다 시끄러워지지 않는다.

그런데 카드를 머리 영역에 두면 원래 걱정이 그대로 남는다 — 그 높이만큼 **쓸 칸이 영영 밀린다.**
**본문 맨 위**로 옮기면 둘 다 풀린다: 열자마자 제일 먼저 보이고, 쓰기 시작하면 스크롤로 비켜난다.
고정 자리를 차지하지 않으므로 펼쳐 둬도 값을 치르지 않는다.

주된 동선(계획 → 이번 주 실적)은 **채운 버튼**이라야 눈이 멈춘다.
테두리만 있는 버튼은 옆의 글자와 섞여서 안 보였다.

> **2026-10-07 개정 (CP-99 · PG-12).** 채운 검정 버튼이 드로어의 주 버튼인 [제출]과 무게를 다퉜다 —
> 한 화면에 채운 버튼이 둘이면 둘 다 주가 아니다. 그래서 표준 보조 버튼(`btn-secondary`)으로 둔다.
> 「섞여서 안 보였다」던 옛 테두리 버튼은 옅은 선(`hairline`)·작은 글자였다. 지금 보조 버튼은 조작 경계 색
> (`border-strong`, 약 3:1)에 36px 높이라 옆 글자와 섞이지 않는다. 패널은 그대로 **펼침 · 본문 맨 위**다(WA-13).
> 대신 그 위의 띠 둘을 걷었다: 붙여넣기 안내는 머리 한 줄과 첫 칸 안내 문구로, 작성 안내는 접기(「부서 작성 안내 N줄」)로.
> 표가 시작하는 높이가 약 100px 올라간다.

**WA-14 — 왜 3주인가.** 참고의 값은 최근일수록 크고, 칩이 늘어나면 고르는 일 자체가 일이 된다.
더 뒤는 「내 이력」에서 본다.

「최근 제출 3건」이 아니라 **「직전 3주」**다. 구현에서도 **주차를 먼저 정하고** 그 안에서
제출을 찾는다 — 제출을 먼저 3건 집으면 한 주 걸렀을 때 두 달 전 것이 딸려 올라온다.
거른 주는 그냥 빈다. 3주 창이면 한 주쯤 건너뛴 경우는 창 안에서 흡수된다.

**WA-15 — 왜 넣을 곳을 고르게 하는가.** 처음에는 `+` 하나로 **같은 표**에 넣었다.
그런데 지난주 계획을 다시 계획에 넣는 건 대개 뜻이 안 맞고, 실제로는 셋 다 일어난다:

| 상황 | 어디서 | 어디로 |
|---|---|---|
| 지난주 계획대로 했다 (제일 흔하다) | 계획 | **실적** |
| 지난주에 못 끝냈다 | 계획 | **계획** |
| 지난주 실적인데 보강한다 | 실적 | **계획** |

어느 쪽이 맞는지는 **적는 사람만 안다.** 기계가 고르면 절반은 틀리고, 틀린 줄을 지우는
수고가 직접 적는 것보다 크다.

**버튼 두 개이지 메뉴가 아니다.** 한 줄 옮기는 데 두 번 누르게 하면 손으로 적는 편이 빠르고,
그러면 이 기능을 안 쓴다. 특이사항은 넣을 곳으로 두지 않았다 — 휴가·출장이라 지난주 것을
그대로 옮길 일이 없다.

### WA-35 — 「다시 작성」은 **지금 낸 판에서** 시작한다 (2026-10-08)

예전에는 빈 표로 열렸다(`initial`을 넘기는 곳이 없었다). 날짜 하나를 고치려 해도 일곱 줄과 「공유」 표시를
처음부터 다시 적어야 해서, 그냥 두거나 담당자에게 고쳐 달라고 했다 — 담당자 일이 늘고, 담당자 자신의 제출물은
첨삭(WA-20) 대상도 아니다. 「지난번에 낸 것」(WA-10)은 지난 주차만 보여 주므로 이번 주에 낸 것은 거기서도 못 가져온다.

| ID | 요구사항 |
|---|---|
| WA-35 | 이번 주에 낸 판이 있으면 [다시 작성 (새 버전)]이 그 판의 표(`/api/submissions/:id/preview`의 `rowsByTable` — 「공유」 포함)로 연다. 표마다 이어 적을 빈 줄 하나를 붙이고, 위에 한 줄: 「지금 낸 v2에서 시작합니다」 |
| WA-35a | 같은 주차의 **저장 안 한 임시본**(브라우저, 내용이 한 줄이라도 있는 것)이 있으면 그것이 먼저다 — 적던 것을 지우지 않는다. 그때는 「저장하지 않은 임시본에서 이어 씁니다」와 [지금 낸 v2로 다시 시작](묻고 나서 임시본을 지운다) |
| WA-35b | 임시본은 **사람이 고친 뒤에만** 쓴다. 연 것만으로 쓰면 빈 표나 옛 판이 임시본이 되어 다음에 지금 낸 판을 가린다 |
| WA-35c | 낸 판을 못 불러오면 빈 표로 열되 그렇다고 말한다. 제출 뒤 문구는 「제출되었습니다 (v3).」 — 「다시 열면 빈 화면으로 시작합니다」는 지웠다 |

**알려진 한계** — 내용 칸은 한 줄 입력칸이라, 한글에서 한 칸에 두 줄로 적어 낸 것은 화면에서 붙어 보인다.
그 칸을 건드리지 않으면 줄바꿈은 그대로 나가고, 고치면 보이는 대로(한 줄로) 나간다.

### WA-36 — 「공유」 칸에 이름과 뜻을 단다 · 일자 예시는 이번 주 날짜 (2026-10-08)

| ID | 요구사항 |
|---|---|
| WA-36 | 표 머리글에 「공유」(파란 점)를 둔다. 표 아래 한 줄: 「공유 — 전 직원에게 전할 주요 사항에 누릅니다. 병합본에 파란색으로 나갑니다」 (HM-37). 뜻이 툴팁에만 있으면 터치·좁은 화면에서는 아무도 못 본다 — 「이 줄을 남에게 공유」로 읽어 안 누르거나, 전부 눌러 병합본이 온통 파래진다 |
| WA-36a | 일자 칸 예시는 **이번 주** 화요일 `M/D`, 계획 표는 다음 주 화요일. 고정 예시 `8/20`은 10월엔 낡은 날짜다 |

### WA-08 — 마감 규칙은 동일

`isLocked` 판정을 그대로 쓴다 (WS-06). 마감 후 초안 수정·제출 불가.
작성 중 마감이 지나면 저장 시 409 — 업로드와 동일하게 명시적으로 알린다 (PG-16).

### WA-20 — 담당자 첨삭 ★ (2026-10-07, TACP-22 · ADR-0013)

담당자·부서장이 수합 관리에서 부서원 제출물을 열고 [고치기] → 웹 작성과 같은 표로 고친다 → [고쳐서 저장].

- 결과는 **그 사람의 새 판**(v+1, `origin: "lead_edit"`, `editedById`). 원래 판은 그대로 남는다
- 만드는 길은 웹 작성(WA-04)과 **같다** — 부서 양식으로 만들고, 같은 자체 검증(WA-05)을 통과해야 저장된다
- **최신 판만** 고친다. 마감과 상관없다. 저장하면 「[다시 병합]을 눌러야 병합본에 들어간다」를 바로 알린다
- **남의 것만** 고친다 — 자기 제출물은 404 (마감을 비켜 가는 길이 되므로, TACP-22)
- 새 판의 `uploadedAt`은 **그 사람이 원래 낸 시각**을 잇고, 고친 시각은 `editedAt`에 따로 남는다 —
  현황·감사 문서가 고친 시각을 제출 시각으로 읽지 않게
- 판 목록·[내 이력]에 「담당자 ○○ 고침 · HH:MM」이 보인다
- 한 칸의 줄바꿈은 그대로 남는다(편집 칸은 textarea). 500자를 넘는 칸은 자르지 않고 422
- 파일을 **먼저** 쓰고 DB를 커밋한다 — 쓰기가 실패하면 새 판도 없다(「파일 없는 최신 판」을 만들지 않는다)
- 고치는 중에는 드로어의 ←→·판 선택을 숨기고, 저장하지 않은 수정이 있으면 닫기 전에 묻는다

### WA-30~34 — HWP 업로드를 단계적으로 닫는다 ★ (2026-10-07, ADR-0014)

> 사용자 결정 (2026-10-07): 「테스트버전에서는 hwp업로드 기능을 삭제하고 제출에서는 웹에서 작성만 남겨줘
> 이것도 장기적으로 제거하기로 했어」

운영에는 아직 hwp를 올려 내는 부서가 있다. 그래서 코드를 지우지 않고 **서버 스위치로 닫는다** —
테스트 서버 먼저 닫고, 운영은 나중에 닫고, 그다음에 코드를 지운다 (ADR-0014).

| ID | 요구사항 |
|---|---|
| WA-30 | 스위치 `SUBMIT_HWP_UPLOAD` = `on`(기본) · `off`. 읽는 곳은 **`src/server/submit-mode.ts` 하나** — 라우트·페이지가 `env`를 직접 보지 않는다. 기본이 `on`인 이유: 운영은 지금 동작 그대로여야 한다. 테스트 서버(`docker-compose.test.yml`)만 `off` |
| WA-31 | `off`면 `POST /api/submissions`는 **410 `upload_closed`** 「HWP 업로드는 닫혔습니다 — 웹에서 작성해 주세요.」 판정은 신원 확인 직후, **파일을 읽기 전에** — 파일도 DB 행도 생기지 않는다 (API-54 · ST-08) |
| WA-32 | `off`면 부서원 화면은 **웹에서 작성 하나만** 그린다 — 「파일 올리기」 탭·드롭존·「양식 받기」 카드(빈 양식·지난번 hwp 받기)가 없고, 안내 문구에도 업로드 이야기가 없다. 사용 안내(`/guide`)도 업로드 단계를 빼고 번호를 다시 붙인다. 업로드 화면이 찍혀 있는 시연(웹 작성·제출 취소)은 다시 녹화하기 전까지 글만 보인다 (PG-11 · TACP-9) |
| WA-33 | 닫는 것은 **「새 hwp를 올려 제출하는 길」 하나**다. 그대로인 것: 이미 올린 제출물 열기·받기·병합 · 웹 작성(WA-04) · 담당자 첨삭(WA-20) · 부서 양식 등록(웹 작성이 이 양식으로 hwp를 만든다) · `GET /api/template`(담당자의 「현재 양식 받기」) · 총괄의 전사 섹션 파일 올리기(RU-60·65 — **취합**이지 제출이 아니다) |
| WA-34 | 스위치는 **문(HTTP 라우트)에 건다.** `uploadSubmission()`에는 걸지 않는다 — 웹 작성도 같은 함수로 저장하고(WA-04), 테스트 데이터 스크립트(`scripts/seed-fake-submissions.ts`)도 이 함수를 부른다 |

**왜 410인가.** 404(TACP-5)는 「권한 없음」을 숨기는 표현인데, 이것은 권한이 아니라 **누구에게나 닫힌 길**이라
숨길 것이 없다. 422는 「보낸 파일이 잘못됐다」로 읽혀서 파일을 고쳐 다시 올리게 만든다.
410 Gone이 「이 길은 없어졌다」를 그대로 말한다. 이 응답을 실제로 받는 사람은 **스위치를 끄기 전에 띄워 둔
화면**에서 올리는 사람이고, 드롭존이 서버 문구를 그대로 보여준다(CP-28).

**되살리기** — `SUBMIT_HWP_UPLOAD=on`으로 바꾸고 재기동하면 끝이다. WA-02가 업로드를 남긴 이유(장애 시 폴백)는
코드를 지우기 전까지 이 한 줄로 유지된다.

## 4. 데이터 모델 추가

```prisma
model Draft {
  id         String   @id @default(cuid())
  divisionId String                       // 격리 축 (DM-12와 동일 원칙)
  userId     String
  weekSlotId String
  content    String                       // JSON: WorklogData
  updatedAt  DateTime @updatedAt
  @@unique([userId, weekSlotId])
  @@index([divisionId, weekSlotId])
}
```

`Submission`에 `origin String @default("upload")` 추가.
