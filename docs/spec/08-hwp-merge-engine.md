# S-08. HWP 병합 엔진 — **Phase 2**

> **착수 조건: 사용자의 명시적 지시.** Phase 1 안정화 전에는 구현하지 않는다.
> 단, **파서(읽기)는 Phase 1에 포함**된다 — 업로드 검증(ST-07)에 필요하기 때문이다.
>
> 모든 설계 근거: [R-001 실측 조사](../research/001-hwp-format-findings.md)

구현: `src/lib/hwp/**` · TypeScript 단일 런타임 ([ADR-0002](../adr/0002-typescript-single-runtime.md))

## 1. 접근 방식

### HM-01 — 원 스펙의 `pyhwpx` 방안은 폐기한다

스펙 §6은 `pyhwpx` (win32com) 기반 흐름을 제시했으나 **실행 불가능**하다.

| 이유 | 근거 |
|---|---|
| Windows + 한글 프로그램 필수 | 배포 대상은 리눅스 컨테이너 (스펙 §8) |
| `.hwpx` 순수 파이썬 라이브러리도 무용 | **실제 파일이 `.hwp` 바이너리** (R-001 §1) |
| 누름틀(`put_field_text`) 방안도 무용 | **필드가 하나도 없음** (R-001 §1) |

### HM-02 — 자체 레코드 엔진을 만든다

HWP 5.0 레코드 스트림을 직접 다룬다. **실측으로 검증된 방식이다.**

```
.hwp (OLE)
  └ BodyText/Section0  ── raw inflate ──► 레코드 스트림
                                              │
                                    파싱 → 표 모델
                                              │
                                    변형 (행 복제/삭제, 텍스트 치환)
                                              │
                                    직렬화 → raw deflate → OLE 재작성
```

### HM-03 — 핵심 안전 원리: **합성하지 말고 복제하라** ★

새 행을 만들 때 레코드를 처음부터 만들지 않는다.
**마스터 양식의 기존 데이터 행 바이트를 그대로 복사**한 뒤 최소 필드만 고친다.

| 복제로 자동 보존되는 것 | 우리가 고치는 것 |
|---|---|
| 테두리·배경 (`borderFillID`) | `LIST_HEADER.rowAddr` |
| 열 너비 · 셀 높이 | `PARA_TEXT` 내용 |
| 셀 여백 | `PARA_HEADER.nChars` |
| 글자모양 (`PARA_CHAR_SHAPE`) | `TABLE.nRows`, `TABLE.rowSize[]` |
| 문단모양 (`paraShapeID`) | |

> **이것이 "표가 안 깨진다"의 보증 메커니즘이다.**
> 서식 정보를 우리가 만들지 않으므로 잘못 만들 수가 없다.
> 여기에 왕복 바이트 동일성(R-001 §6 실험 1)이 더해져, **손대지 않은 것은 절대 변하지 않는다**가 성립한다.

## 2. 계층 구조

```
src/lib/hwp/
├── ole.ts        L0  OLE 컨테이너 (cfb 래핑)
├── record.ts     L1  레코드 파싱/직렬화  ← 왕복 동일성 보증 지점
├── model.ts      L2  표/셀 도메인 모델
├── reader.ts     L3  .hwp → WorklogData   (Phase 1에서 검증용으로도 사용)
├── writer.ts     L3  WorklogData → .hwp   (Phase 2)
├── rule.ts       L4  부서 규칙 파서 (HM-18)
└── merge.ts      L4  병합 정책
```

**아래 계층은 위 계층을 모른다.** `record.ts`는 표를 모르고, `model.ts`는 업무일지를 모른다.

## 3. L1 — 레코드 계층

### HM-04 — 왕복 동일성 불변식 ★

```
serialize(parse(bytes)) === bytes        // 바이트 단위 완전 일치
```

실측 검증 완료 (R-001 §6):

| 파일 | 레코드 수 | 결과 |
|---|---|---|
| `master-template.hwp` | 552 | ✔ SHA-256 일치 |
| `sample-filled-w1.hwp` | 655 | ✔ |
| `sample-filled-w2.hwp` | 466 | ✔ |
| `DocInfo` (3파일) | 122~126 | ✔ |

**이 불변식이 깨지면 다른 모든 테스트는 무의미하다.** CI 최우선 테스트로 둔다.

```ts
export interface HwpRecord {
  tag: number;
  level: number;
  data: Buffer;
  extended: boolean;    // 0xFFF 확장 길이였는지 — 왕복 동일성에 필요
}
export function parseRecords(buf: Buffer): HwpRecord[];
export function serializeRecords(recs: HwpRecord[]): Buffer;
```

| ID | 요구사항 |
|---|---|
| HM-05 | `extended` 플래그 보존. 원본이 확장 길이면 크기가 작아져도 확장 형식 유지 |
| HM-06 | 크기 ≥ 0xFFF면 자동 확장 형식 |
| HM-07 | 압축은 **raw deflate** (`inflateRawSync`/`deflateRawSync`) |
| HM-08 | `FileHeader[36] & 0x01`로 압축 여부 판정. 하드코딩 금지 |
| HM-08a | **`cfb` 센티널 스트림 대응** — 아래 참조 |

### HM-08a — `cfb`의 `\x01Sh33tJ5` 센티널 ★

`CFB.write()`는 출력에 4바이트 표식 스트림을 **무조건 추가**한다 (원본 9개 → 출력 10개).
쓰기 전에 제거해도 다시 주입되므로 라이브러리 옵션으로는 막을 수 없다 (실측 확인).

- HWP 리더는 스트림을 이름으로 조회하므로 무시될 가능성이 높다
- SheetJS가 만든 XLS/DOC도 동일한 스트림을 갖고 MS Office에서 정상 동작한다

**판정은 [Q-01](../../OPEN-QUESTIONS.md)에서 함께 이뤄진다** —
`fixtures/verify-write-test.hwp`에 이 센티널이 이미 포함되어 있다.

문제가 되면: ① 쓰기 후 디렉터리 엔트리 무효화 ② 최소 CFB 라이터 자체 구현.
②는 스트림 9개·수십 KB 규모라 난도가 낮다.

| ID | 요구사항 |
|---|---|
| HM-T18 | 출력 파일의 스트림 목록에 원본 9개가 **전부 존재**하고 내용이 의도대로인지 |

## 4. L2 — 표 모델

### HM-09 — 표 파싱

```ts
export interface HwpTable {
  recordIndex: number;      // TABLE 레코드 위치
  rows: number;
  cols: number;             // 실측 전부 5
  cells: HwpCell[][];       // [row][col]
}
export interface HwpCell {
  row: number; col: number;
  colSpan: number; rowSpan: number;   // 실측 전부 1
  text: string;
  listHeaderIndex: number;
  paraIndices: number[];
}
```

### 바이트 오프셋 (실측 확정)

**`TABLE` (tag 77)**

| offset | 필드 |
|---|---|
| 4 | `nRows` (UINT16) |
| 6 | `nCols` (UINT16) |
| 18 | `rowSize[nRows]` (UINT16 배열) |
| 18+2n | `borderFillID` (UINT16) |
| 20+2n | `validZoneInfo` 개수 — 실측 **0** |

**`LIST_HEADER` (tag 72)**

| offset | 필드 |
|---|---|
| 8 | `colAddr` (UINT16) |
| 10 | `rowAddr` (UINT16) |
| 12 | `colSpan` (UINT16) |
| 14 | `rowSpan` (UINT16) |

**`PARA_HEADER` (tag 66)**

| offset | 필드 |
|---|---|
| 0 | `nChars` — ⚠ **상위 비트 0x80000000은 플래그** |

### HM-10 — `nChars` 갱신식 ★

```ts
const flag = original.readUInt32LE(0) & 0x80000000;
buf.writeUInt32LE((flag | (textBuf.length / 2)) >>> 0, 0);
```

실측: 원본 `0x8000000B` = 플래그 + 11자.
**플래그를 지우면 문서가 깨진다.** 실험 2에서 발견한 함정 (R-001 §4.5).

### HM-11 — `PARA_TEXT` 규칙

- UTF-16LE
- **문단 끝 `0x000D`(CR) 포함**
- `nChars`는 CR을 **포함**한 값
- 텍스트 교체 시 기존 꼬리 컨트롤 문자를 보존한다

```ts
const tail = old.slice(plainLength);          // CR 등
const next = Buffer.from(newText + tail, 'ucs2');
```

### HM-11a — 빈 셀에는 PARA_TEXT를 두지 않는다 ★ (한글 실측)

**빈 칸에 글자 레코드를 만들면 한글이 문서를 손상으로 판정한다.**

원본 양식 실측: 빈 셀 20개 전부 `LIST_HEADER > PARA_HEADER > PARA_CHAR_SHAPE > PARA_LINE_SEG`
구성이고 `PARA_TEXT`가 **없다**. 글자 수는 1이다 (문단끝 몫).

| 쓰려는 글자 | 해야 할 일 | 글자 수 |
|---|---|---|
| 빈 문자열 | PARA_TEXT를 **만들지 않는다.** 있으면 **지운다** | 1 |
| 글자 있음 | 없으면 만들고, 있으면 본문만 교체 (문단끝 표시 보존) | 글자+1 |

**왜 게이트인가** — 이 실수는 우리 도구로 안 잡힌다. 자체 리더도 LibreOffice도 빈 레코드를
그대로 읽는다. 실제로 한글 확인을 여섯 번 왕복한 끝에야 원인이 잡혔다:

```
행만 늘림(20행)        → 열림      글자만 교체        → 열림
빈 칸에 글자 넣기      → 열림      행 줄이기          → 열림
행 늘림 + 글자 채움    → 손상  ←  빈 칸에 '빈 글자'를 쓰는 경로만 시험된 적이 없었다
```

> **검증 원칙 갱신**: LibreOffice 개봉은 **통과 근거가 아니다.** 깨진 파일도 열어준다.
> 대신 **원본 양식과 레코드 구성을 대조**한다 (HM-T30~34).

### HM-12 — 셀 순서

셀은 **좌→우, 상→하로 평탄하게** 나열된다. 행 구분 레코드는 없다.
`LIST_HEADER` 블록 하나 = 셀 하나. 한 행 = 연속된 `nCols`개 블록.

### HM-13 — 다중 문단 셀

`LIST_HEADER[0..3]`(문단 수)이 1보다 크면 셀 안에 줄바꿈이 있다.

- **읽기**: 문단들을 `\n`으로 join
- **쓰기**: 문단 1개로 정규화 (여러 문단 생성은 지원하지 않음)

> 제출자가 셀 안에서 Enter를 칠 수 있다. 읽기는 반드시 대응해야 한다 ([R-001 V-5](../research/001-hwp-format-findings.md)).

## 5. L3 — 업무일지 도메인

### HM-14 — 문서 모델

```ts
export interface WorklogRow {
  content: string;    // 업무실적 내용
  date: string;       // 일자   "8/12" | ""
  place: string;      // 장소
  attendee: string;   // 참석자
}
export interface WorklogData {
  achievements: WorklogRow[];   // 1. 주요 업무실적
  plans:        WorklogRow[];   // 2. 주요 업무계획
  notes:        WorklogRow[];   // 3. 기타 특이사항
}
```

`구분` 열(`1-1`, `2-3`)은 **모델에 담지 않는다.** 항상 위치에서 재생성한다.

### HM-15 — 읽기 규칙

| ID | 규칙 |
|---|---|
| HM-15a | 표는 등장 순서대로 1·2·3번에 대응 |
| HM-15b | **표가 2개면** 3번(기타 특이사항)이 삭제된 것 → `notes = []` (실측: 실제 취합본 2개 모두 해당) |
| HM-15c | 첫 행은 헤더 → 건너뜀 |
| HM-15d | `구분` 열 값은 무시 |
| HM-15e | 나머지 4열이 **전부 공백인 행은 제외** |
| HM-15f | 각 셀 값은 `trim()` |
| HM-15g | 자리표시자 `OO/OO`는 빈 값으로 취급 |

### HM-16 — 쓰기 규칙

| ID | 규칙 |
|---|---|
| HM-16a | **부서 active 양식**을 기반으로 시작 (DM-14) |
| HM-16b | 필요한 행 수에 맞춰 데이터 행을 복제/삭제 (HM-03) |
| HM-16c | `구분` = `{표번호}-{행번호}` 재생성 |
| HM-16d | 데이터가 0건인 표는 **표 전체를 삭제** (HM-15b의 역연산) |
| HM-16e | 최소 행 수 유지 — 아래 참조 |

### HM-17 — 최소 행 수 정책

실측상 꼬리 빈 행은 조직 관례로 허용된다 (`8월_2주차`의 `2-8`).

```
표 1 (실적)  : max(데이터 수, 8)
표 2 (계획)  : max(데이터 수, 8)
표 3 (특이)  : 데이터 0건이면 표 삭제, 아니면 max(데이터 수, 4)
```

기본 하한 = **그 부서 양식의 행 수** (AI홍보전략실 양식은 8/8/4).
부서 규칙 `빈행유지:`로 조정 가능하되, 절대 규칙에는 저촉되지 않는 범위(0 이상 정수)다.

## 6. L4 — 병합 정책 (v2: 부서 규칙 + 절대 규칙)

### HM-ABS — 절대 규칙 ★ (어떤 부서 규칙도 이것을 넘지 못한다)

시스템 불변식. 규칙 텍스트로 표현 자체가 불가능하게 설계한다 —
규칙 파서에 이를 건드리는 지시어가 **존재하지 않는다**.

| # | 불변식 | 집행 지점 |
|---|---|---|
| ABS-1 | 표 규격 보존 — 열 수·테두리·너비·글자모양은 양식의 것. 행 복제 원리(HM-03)로만 생성 | writer |
| ABS-2 | 내용 무손실 — 입력의 모든 비어있지 않은 행이 출력에 존재 | HM-22.4 자체 점검 |
| ABS-3 | 원본 불변 — 제출 파일은 읽기만 (HM-20) | 코드 계층 (쓰기 API 없음) |
| ABS-4 | 출력 재파싱 가능 — 우리 reader로 다시 읽혀야 저장 | HM-22.1 |
| ABS-5 | `구분` 채번 연속성 — `1-1…` 재생성, 수동 지정 불가 | writer |
| ABS-6 | 개인 행 내부 순서 보존 — 작성자가 정한 순서를 규칙이 섞을 수 없다 | merge |

### HM-18 — 부서 병합 규칙 ★ (v3 전면 개정 — 문법을 없앤다)

초안에는 `순서:` `빈행유지:` `특이사항:` 지시어 문법이 있었다. **폐기한다.**

실제로 AI홍보전략실이 부서원에게 보낸 규칙 전문은 이것이다:

> 주간 업무 실적 및 계획 앞으로 작성 참고 차 송부드립니다.
> * 순서: AI-홍보(정간물 포함)-시스템-도서관
> * 날짜: 저는 상시업무들은 공란으로 두고 특정되는 업무만 작성해두었습니다.

두 줄이고, **권장이지 의무가 아니다.** 여기에 배워야 하고 틀릴 수도 있는 문법을 씌울
이유가 없다. 30개 부서 중 규칙 문법을 쓴 곳은 0곳이었다 (기능을 만들기 전에 확인했어야 했다).

남은 것은 **설정 3개 + 자연어 1개**다. 전부 부서 설정 화면의 입력란이다.

| 필드 | 형태 | 기본값 | 의미 |
|---|---|---|---|
| `mergeCategories` | 한 줄 | 빈값 | 분류 순서. `AI-홍보-시스템-도서관` |
| `mergeDedupe` | 체크박스 | 켬 | 중복 묶기 |
| `mergeDropNotes` | 체크박스 | 켬 | 특이사항이 비면 3번 표 삭제 |
| `mergeRuleText` | 여러 줄 | 빈값 | 자연어 지침 — 모델에 그대로 전달 |

- 구분자는 쉼표·가운뎃점·하이픈·슬래시 **아무거나** 받는다. 부서가 보낸 원문이
  하이픈이었다 — 사람에게 구분자를 외우게 하지 않는다
- 잘못된 입력으로 **막지 않는다.** 빈 항목·중복은 조용히 정리한다.
  권장 규칙에 파서 오류를 띄우는 건 과하다
- **제출자 순서는 규칙에 없다.** `/ops` 인원관리의 `sortOrder`가 정본이다 (TACP-3).
  두 곳에 적으면 반드시 어긋난다

### HM-27 — 분류 정렬 ★ (v3 신설)

"순서: AI-홍보-시스템-도서관"은 **사람 순서가 아니라 업무 분류 순서**다.
그래서 병합본은 사람별 블록이 아니라 **주제별로 묶인다** — 읽는 사람에게 훨씬 낫다.

각 행이 어느 분류인지는 판단이라 모델이 맡는다. 안전한 이유는 명확하다:
**분류는 재배치만 시킬 뿐 글자를 건드리지 않는다.** 최악의 경우가 "엉뚱한 묶음에 들어감"이고,
사라지거나 바뀌는 건 없다. 분류 이름은 문서에 나타나지도 않는다 — 순서에만 쓰인다.

| 하네스 | 내용 |
|---|---|
| 출력 | `{"assign":{"1":"AI","2":"기타"}}` — id → 분류 이름뿐 |
| 모르는 분류 | `기타`로 접는다 (새 분류를 만들지 못한다) |
| 빠진 id | `기타`. **전체를 폐기하지 않는다** — 정렬에만 쓰이므로 손실이 없다 |
| 모델 실패 | 제출자 순서 그대로. 경고만 남긴다 |
| 같은 분류 안 | **원래 순서 유지** (ABS-6) |
| `기타` 위치 | 언제나 맨 뒤 |

실측 (제출물 2건 22행 → 중복 3건 묶고 19행):
`AI 1 · 홍보 8 · 시스템 3 · 기타 7`, 판정 19/19, 12.8초.

> **ABS-6 해석 갱신** — "작성자가 정한 순서를 규칙이 섞을 수 없다"는 **분류 안에서** 유효하다.
> 분류 사이의 재배치는 부서가 명시적으로 요청한 것이므로 허용된다.

### HM-19 — 병합 절차### HM-19 — 병합 절차

```
1. 부서·슬롯의 isLatest 제출물 전부 로드 (스코프: divisionId — AU-13)
2. 각각 reader로 WorklogData 추출        (실패해도 중단하지 않음 — HM-21)
3. 부서 설정 → 실행 계획 (HM-18)
4. 제출자 정렬 = sortOrder (TACP-3 — 명단은 운영자 소관)
5. achievements / plans / notes 각각 순서대로 concat
5b. 중복 묶기 (결정론 + 모델, HM-24) → 분류 정렬 (HM-27)
6. 부서 active 양식 로드 (Template.isActive — DM-14)
7. 표별 행 수 조정 + 텍스트 채우기 + 구분 재생성 (ABS-1·5)
8. 특이사항 정책 적용 (비면 삭제 등)
9. HM-22 자체 점검 → divisions/{slug}/merged/{연도}/{주차}/ 저장
10. MergeRun 기록 (ruleSnapshot 포함 — DM-13)
```

### HM-20 — 원본 불변 (ABS-3)

병합은 제출 파일을 **읽기만** 한다. 어떤 경우에도 수정·삭제하지 않는다 (API-31).

### HM-21 — 부분 실패 허용 ★

한 사람의 파일이 깨져도 **나머지로 병합을 완료**한다.

```jsonc
{ "status": "succeeded",
  "warnings": ["김OO: 표를 찾을 수 없어 제외했습니다 (submission c…)"] }
```

> 마감 직후 부서원 12명 중 1명 파일이 이상하다고 전체가 실패하면,
> 담당자는 결국 전부 손으로 여는 원래 상태로 돌아간다.
> **11명치라도 병합해 주는 편이 압도적으로 낫다.**
> 경고는 화면 상단에 눈에 띄게 띄우고, 해당 인원은 수동 처리하면 된다.

### HM-22 — 결과 검증 (자체 점검)

저장 전에 스스로 확인한다. 실패 시 저장하지 않고 `failed`.

```
1. 결과 파일을 다시 파싱할 수 있는가
2. 표 개수가 예상과 같은가
3. 각 표의 nRows가 의도한 값인가
4. 입력 행 텍스트가 전부 출력에 존재하는가   ← 유실 방지
5. 구분 열이 1-1, 1-2 … 순서대로인가
```

> 4번이 핵심이다. **누락은 조용히 일어나고 늦게 발견된다.**

### HM-24 — 모델 하네스 ★ (v3 신설)

병합에 로컬 모델을 쓴다. 다만 **모델이 문서 글자를 만들게 두지 않는다.**

8명치 업무일지를 LLM에 넣고 "병합해줘" 하면 반드시 요약하고 흘린다. 실장님께 올라가는
문서에서 누군가의 실적 한 줄이 사라지는 건 되돌릴 수 없다. ABS-2(내용 무손실)와
정면으로 충돌한다.

그래서 역할을 나눈다 — **모델은 판단만, 조립은 코드가.**

```
1. 코드   제출물 → 행 목록 추출, 행마다 id 부여              (결정론)
2. 모델   id만 보고 판단 → {"groups":[{"ids":[3,7],...}]}     ← 여기만 LLM
3. 코드   검증: 모든 id가 정확히 한 번 등장하는가
          아니면 → 모델 출력 폐기, 결정론 결과로 폴백
4. 코드   원본 셀 글자를 그대로 표에 조립                     (결정론)
```

모델은 **한 글자도 출력하지 않는다.** id 묶음만 낸다. 문서에 들어가는 글자는 전부
작성자가 쓴 원문 그대로다.

| 하네스 | 무엇을 막는가 |
|---|---|
| 모델은 id만 출력 | 요약·왜곡·환각 (텍스트를 만들 수 없다) |
| 응답 스키마 강제 (`format: json`) | 형식 파탄 |
| **행 보존 검증** — 모든 id가 정확히 한 번 | 누락·중복 |
| 결정론 결과로 폴백 | 모델 장애·타임아웃에도 병합본은 나온다 |
| `temperature 0` | 같은 입력 → 같은 출력 (재현·감사 가능) |
| 시간 상한 (기본 60초) | 마감 직후 지연 |

**모델이 맡는 일은 셋뿐이다**: ① 중복 업무 묶기 ② `구분` 분류 제안 ③ 관련 업무 인접 배치.
셋 다 "판단"이지 "작성"이 아니다.

**모델 없이도 병합은 완결된다.** 모델 층은 얹는 것이지 의존하는 것이 아니다 —
`MERGE_MODEL`이 비어 있으면 결정론 병합만 수행한다.

| 항목 | 값 |
|---|---|
| 실행 위치 | 같은 서버 ollama (`MERGE_MODEL_URL`, 기본 `http://127.0.0.1:11434`) |
| 기본 모델 | `Qwen2.5-14B-Instruct Q4_K_M` — 실측 warm 6.9초, GPU 상주 10.9GB |
| 외부 전송 | **없음.** 업무일지는 서버 밖으로 나가지 않는다 |

### HM-25 — 마감 자동 병합 ★ (v3 신설)

**병합은 버튼이 아니라 마감이 시킨다.**

담당자가 들어와서 버튼을 누르면 그때부터 기다려야 한다. 목표 시나리오는 그게 아니다 —
**목요일 14:10에 들어왔을 때 이미 되어 있어야** 한다.

```
목 14:00  마감 → 자동 병합 시작
목 14:01  완성 · 받기 버튼 활성
목 14:10  담당자 입장 → 받기 → 확인 → 취합게시판 제출
```

- 마감이 지난 주차에 대해 **부서별로 1회** 자동 실행 (`MergeRun`이 있으면 재실행 안 함)
- 수동 재실행은 언제든 가능 (규칙을 고쳤을 때). 새 `MergeRun`이 쌓이고 최신이 유효
- 자동 실행 실패는 화면에 남기고, 담당자가 원인을 보고 재실행할 수 있어야 한다
- 스케줄러는 **부서 없음·제출 0건이면 조용히 넘어간다** (빈 병합본을 만들지 않는다)

### HM-26 — 검토 화면은 "볼 곳"을 알려준다

"슥 보고 제출"이 되려면 전체를 다시 읽게 하면 안 된다.
**모델이 손댄 곳과 경고만** 표시하면, 나머지는 원문 그대로이므로 확인할 필요가 없다.

| 표시 | 내용 |
|---|---|
| 묶인 행 | 어느 행들이 왜 하나로 묶였는지 (원문 나란히) |
| 제외된 인원 | HM-21 부분 실패 경고 |
| 미제출자 | 마감 시점 기준 |
| 폴백 여부 | 모델 결과가 검증에서 떨어졌으면 명시 |

### HM-23 — `.hwpx` 미지원 (v2에서 종결)

접수 자체를 하지 않는다 (ST-05, 사용자 확정). `hwpx.ts` 모듈은 만들지 않는다.
읽기 코드는 `.hwp` 한 벌만 유지한다.

## 7. 테스트 전략

### 7.1 계층별

| 계층 | 방식 |
|---|---|
| L1 레코드 | 왕복 바이트 동일성 (HM-04) — **필수 게이트** |
| L2 모델 | 실제 픽스처의 표 구조 단언 |
| L3 읽기 | 픽스처 → 기대 `WorklogData` 골든 비교 |
| L3 쓰기 | 생성 → 재파싱 → 동등성 (라운드트립) |
| L4 병합 | 다인원 시나리오 |

### 7.2 픽스처

`fixtures/`에 실제 파일이 커밋되어 있다.

| 파일 | 구조 | 용도 |
|---|---|---|
| `master-template.hwp` | 표1 9행, 표2 9행, 표3 5행 | 기준 양식 |
| `sample-filled-w1.hwp` | 표1 14행, 표2 14행, **표3 없음** | 다행 케이스 |
| `sample-filled-w2.hwp` | 표1 10행, 표2 9행, **표3 없음** | 표3 삭제 정답 ★ |

### HM-24 — 표3 삭제 로직은 실제 정답 파일로 검증 ★

`sample-filled-w1/w2`는 **사람이 한글에서 표3을 삭제한 결과물**이다.
즉 "정답"이 이미 손에 있다.

```
검증: master-template에서 표3을 삭제한 우리 출력의 레코드 구조가
      sample-filled-w2의 해당 구간과 동형인가
```

이 비교로 삭제 시 남는 잔여 문단·컨트롤 처리를 **추측 없이** 맞출 수 있다.
(R-001 V-3 — 조사 과정에서 확보한 가장 운 좋은 자산)

### HM-25 — 한글 프로그램 육안 검증 (자동화 불가)

CI가 대신할 수 없는 유일한 부분.
