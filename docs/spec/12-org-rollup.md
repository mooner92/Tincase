# 12. 본부·전사 취합 (3단계 롤업)

상태: **초안 — 결정 필요 사항(§12) 확정 전** · 작성 2026-10-07 · 목표: **11/2(월) 운영회의 시연**
관련: [08 병합 엔진](08-hwp-merge-engine.md) · [TACP](../../TACP.md) · [02 주차](02-week-slot.md) · [06 화면](06-pages.md)

ID 접두사 `RU` (roll-up). 확정되면 상태를 「채택」으로 바꾸고 코드가 이 ID를 참조한다.

## 0. 요구 (2026-10-07 사용자 정리)

1. **6개 본부별로 운영한다.**
2. 실·팀 단계는 **지금과 같다** — 부서원 제출 → 자동 병합 → 실장 검토 → 담당자 제출.
3. 본부 단계 — 산하 실·팀이 **제출한 병합본을 정해진 순서로 이어 붙인다.** 실·팀 안의 내용
   위치는 바꾸지 않는다(일단 이어 붙이기로 만들고 피드백을 받는다). 본부장 검토 → 본부 담당자가
   **최종 제출 플래그**를 띄운다.
4. 전사 단계 — 총괄(기획조정실)이 본부들의 최종 제출본을 **한 번에 병합**해 끝낸다(NAMS 제출).
5. 본부 담당자와 총괄은 **자기 단계의 병합 순서(프롬프트)를 설정**한다.
6. 지난 주(또는 지난 달) 실·팀 제출 파일 전체로 **비슷한 결과가 나오는지** 테스트 서버(11112)에서 재현한다.
7. **다음 주(10/12 주)부터 전 부서 알림을 켠다.**
8. **11/2(월) 운영회의에서 큰 화면에 띄워 쓴다** — 시연 준비를 꼼꼼히.

## 1. 조직 — ERP 인원 현황 기준 (2026-10-06 갱신분)

`●` 업무일지를 내는 단위(취합게시판 확인) · `○` 내지 않는 단위(연구부서)

| 본부 단위 | 장 | 산하 실·팀 |
|---|---|---|
| **기획경영본부** ● (10명·담당 미지정) | 본부장 | ● AI홍보전략실 · ● 기획조정실 · ● 연구관리실 · ● 인사관리실 · ○ 경영지원실 |
| **국토환경연구본부** ● (1명·담당 있음) | 본부장 | ○ 국토관리연구실 · ○ 물관리연구실 · ○ 자연환경연구실 |
| **환경평가본부** ● (1명·담당 있음) | 본부장 | ○ 국토전략평가실 · ○ 기후에너지평가실 · ○ 사회기반평가실 · ○ 환경자원평가실 |
| **국가기후위기적응센터** ● (2명·담당 있음) | 센터장 | ○ 기후적응정책실 · ○ 기후적응협력실 |
| **기후대기전략연구본부** ○ (2명) | 본부장 | ○ 녹색경제연구실 · ○ 대기환경연구실 · ● 탄소중립에너지연구실 |
| **생활환경연구본부** ○ (1명) | 본부장 | ● 순환경제연구실 · ○ 환경보건연구실 · ○ 환경사회연구실 |
| 본부 밖 | | ● 글로벌대외협력단 · ● 임원실 · ○ 감사실 · ○ 국가지속가능발전연구센터 |

읽히는 것:

- **6개 본부 = 위의 여섯**(센터 포함)로 보인다 — §12 Q1로 확인한다
- **연구 본부(국토환경·환경평가·적응센터)는 산하 실이 쓰지 않고 본부가 직접 한 명이 쓴다.**
  이 본부들의 본부 단계는 「자기 문서 하나」다
- **기획경영본부는 산하 실들이 각자 쓴다.** 본부 단계가 실제로 「이어 붙이기」가 되는 곳이다
- **기후대기·생활환경 본부는 산하 실 하나씩만 쓴다** — 본부 자체는 쓰지 않는다
- **경영지원실**은 ERP상 기획경영본부 산하 실이다(AI홍보전략실의 형제, 소속 관계 아님).
  「본부 취급」이라는 말이 있어 Q2로 확인한다

## 2. 흐름

```
실·팀        부서원 제출 ─► 자동 병합(마감+1분) ─► 실장 검토 ─► 담당자 [본부에 제출] ●
                                                                      │
본부         산하 단위의 「제출된」 병합본을 순서대로 이어 붙임 ─► 본부장 검토 ─► 본부 담당자 [총괄에 제출] ●
                                                                      │
전사(총괄)    본부들의 「제출된」 본부본을 순서대로 이어 붙임 ─► 총괄 검토·수정 ─► hwp ─► NAMS
```

| ID | 요구 |
|---|---|
| RU-01 | **제출 플래그**를 둔다. 실·팀 담당자의 [본부에 제출], 본부 담당자의 [총괄에 제출]. 플래그는 **그 시점의 병합본 한 판**을 가리킨다 |
| RU-02 | 제출한 뒤 하위에서 다시 병합하면 플래그는 **옛 판을 계속 가리킨다.** 새 판을 올리려면 다시 제출한다 — 상위가 보고 있던 문서가 몰래 바뀌지 않는다(HM-44와 같은 이유) |
| RU-03 | 제출은 **철회**할 수 있다 — 상위가 아직 병합하지 않았을 때만 조용히, 이미 병합했으면 상위에 「바뀜」 표시 |
| RU-04 | 상위 병합은 **제출된 하위만** 쓴다. 미제출 하위는 화면에 「미제출」로 보이고 병합본에서는 빠진다(§12 Q4) |
| RU-05 | 본부 자체가 쓰는 문서가 있으면(연구 본부) 그것도 본부 단계의 한 단위로 들어간다 |
| RU-06 | 본부 밖 단위(글로벌대외협력단·임원실)는 전사 단계에 **직접** 제출한다 |

## 3. 이어 붙이기 규칙 (병합 엔진 L5)

| ID | 요구 |
|---|---|
| RU-10 | 출력은 **총괄 양식(원본) 위에** `[단위명] + 1·2·3 표` 블록을 순서대로 반복한다. 블록은 원본의 제목 문단과 표를 **복제**해 만든다 — HM-03 「합성하지 말고 복제하라」 |
| RU-11 | 단위 **안의** 행 순서·구분 번호·파란 「공유」 강조는 그대로 둔다. 바꾸는 것은 단위의 **순서**뿐이다 |
| RU-12 | 입력은 하위의 **제출된 병합본 파일**이다(readWorklog로 읽어 다시 쓴다). 파일을 바이트째 이어 붙이지 않는다 — 문서마다 서식 표(DocInfo)가 달라 섞으면 깨진다 |
| RU-13 | 실제 최종본(NAMS 제출본) 형식에 맞춘다 — **샘플을 받아 테스트 서버에서 대조**한다(§12 Q5). 블록 머리 형식·빈 표 처리·페이지 나눔은 그때 정한다 |
| RU-14 | 결과 검증(HM-22와 같은 원리) — 다시 읽어서 모든 단위의 행 수·강조 수가 입력과 같아야 한다 |
| RU-15 | 문단 자기 기술 불변식(HM-46) — 글자·서식 구간·줄 수가 모두 맞아야 한다. 한글이 「손상」으로 보는 지점이다 |

## 4. 순서 설정 (「병합 프롬프트」)

| ID | 요구 |
|---|---|
| RU-20 | 본부 담당자는 산하 단위 순서를, 총괄은 본부 순서를 **끌어서** 정한다. 정하지 않으면 ERP 순서 |
| RU-21 | 자유 글(지침)도 남길 수 있다 — v1은 사람이 읽는 메모이고 순서는 목록이 정한다. 모델에게 순서를 맡기지 않는다(같은 입력에 같은 순서가 나와야 한다) |
| RU-22 | 순서는 단위에 저장되고 다음 주에도 쓰인다 |

## 5. 데이터 모델 (초안)

```prisma
model Division {
  // … 기존 …
  parentId     String?   // ERP parentKo에서 연결 — 인원 갱신(RS) 때 같이 맞춘다
  rollupOrder  String    @default("[]")   // RU-20 — 하위 단위 id 순서 (JSON)
  rollupNote   String    @default("")     // RU-21
}

model ReportSubmission {          // RU-01 — 상위로 올린 플래그
  id          String   @id @default(cuid())
  divisionId  String              // 올린 단위
  weekSlotId  String
  mergeRunId  String              // 그 시점의 병합본 한 판 (RU-02)
  submittedBy String
  submittedAt DateTime @default(now())
  withdrawnAt DateTime?
  @@index([divisionId, weekSlotId])
}

model MergeRun {
  // … 기존 …
  level       String   @default("team")   // team | hq | org
  // hq·org의 sourceIds는 하위 ReportSubmission id들
}
```

전사(org) 단계의 주인은 가상의 루트 단위(「한국환경연구원」)로 둔다 — 총괄만 다룬다.

## 6. 권한 (TACP v1.6 개정 필요)

| | 실·팀 담당자·실장 | 본부 담당자·본부장 | 총괄 | 운영자 |
|---|:---:|:---:|:---:|:---:|
| [본부에 제출] (자기 실·팀) | write | | | |
| 산하 단위의 **제출된 병합본** 읽기 | | read | read | read |
| 산하 단위의 **개별 제출물** 읽기 | | — | read | read |
| 본부 병합·수정·순서·[총괄에 제출] | | write | | |
| 전사 병합·수정·순서 | | | write | |

- 본부 담당자 = 본부 단위의 `lead`, 본부장 = `head`. 새 Principal을 만들지 않는다 —
  「본부 단위의 담당자」라는 **위치**가 권한을 정한다
- 본부 쪽은 하위의 **병합본만** 본다. 개별 부서원의 제출물은 그 실·팀의 몫이다(TACP §3.2 원칙)

## 8. 알림 (2단계)

실·팀 제출 → 본부 담당자 · 본부 전원 제출 → 본부장(검토) · 본부 제출 → 총괄. 시각은 §12 Q6.
v1 시연에는 넣지 않고, 흐름이 확정된 뒤 붙인다.

## 12. 결정 필요

| Q | 질문 | 기본 가정(답이 없으면) |
|---|---|---|
| Q1 | 6개 본부 = 기획경영·국토환경·환경평가·기후대기전략·생활환경 + **국가기후위기적응센터**가 맞나 | 그렇다 |
| Q2 | **경영지원실**은 기획경영본부 산하로 두나, 본부와 같은 단계로 두나. 다음 주부터 쓰나 | 기획경영본부 산하 · 사용 |
| Q3 | 기획경영본부 **자체**(10명)도 업무일지를 따로 쓰나, 아니면 본부 담당자가 산하 실 것만 모으나. 본부 담당자는 누구인가(9/21 게시판 답변자가 있다) | 산하 실만 모은다 · 담당은 게시판 답변자 |
| Q4 | 미제출 단위는 상위 병합본에서 **뺄지**, 「미제출」로 자리를 남길지 | 뺀다(화면엔 미제출 표시) |
| Q5 | **실제 최종본**(NAMS 제출본) 샘플 — 받을 자료에 같이 부탁 | 받을 때까지 RU-10 형식 |
| Q6 | 본부 단계 마감 — 실·팀 14:00 이후 본부는 몇 시까지, 총괄은 몇 시까지 | 시연 전까지 시각 없이 플래그로만 |
