## 0. 요구 (2026-10-07 사용자 정리)

1. **6개 본부별로 운영한다.**
2. 실·팀 단계는 **지금과 같다** — 부서원 제출 → 자동 병합 → 실장 검토 → 담당자 제출.
3. 본부 단계 — 산하 실·팀이 **제출한 병합본을 정해진 순서로 이어 붙인다.** 실·팀 안의 내용
   위치는 바꾸지 않는다(일단 이어 붙이기로 만들고 피드백을 받는다). 본부장 검토 → 본부 담당자가
   **최종 제출 플래그**를 띄운다.
4. 전사 단계 — 총괄(기획조정실)이 본부들의 최종 제출본을 **한 번에 병합**해 끝낸다(NAMS 제출).
5. 본부 담당자와 총괄은 **자기 단계의 병합 순서(프롬프트)를 설정**한다.
6. 지난 주(또는 지난 달) 실·팀 제출 파일 전체로 **비슷한 결과가 나오는지** 테스트 서버(11112)에서 재현한다.
7. **다음 주(10/12 주)부터 전 부서 알림을 켠다.**
8. **11/2(월) 운영회의에서 큰 화면에 띄워 쓴다** — 시연 준비를 꼼꼼히.
9. **(2026-10-08 추가) 승인이 곧 제출이다.** 「실팀장 승인 후엔 사실 담당자가 고칠건 없다 … 본부 담당분이 할건 없고 본부장님이
   합쳐진거 바로 볼 수 있게 … 검토하면 바로 총괄로 제출하도록 … glue work 시간을 줄여야 해. 더 쉽게, 빠르게 정확하게.」
   → 3·4의 「담당자 제출」·「이어 붙인다」·「최종 제출 플래그」·「한 번에 병합」은 사람이 누르지 않는다(§2a).
   본부 담당자의 정해진 일은 없어지고(순서 설정은 남는다), 사람이 하는 일은 실·팀장 승인과 본부장 승인 둘이다

읽히는 것:

- **6개 본부 = 위의 여섯**(센터 포함)로 보인다 — §12 Q1로 확인한다
- **연구 본부(국토환경·환경평가·적응센터)는 산하 실이 쓰지 않고 본부가 직접 한 명이 쓴다.**
  이 본부들의 본부 단계는 「자기 문서 하나」다
- **기획경영본부는 산하 실들이 각자 쓴다.** 본부 단계가 실제로 「이어 붙이기」가 되는 곳이다
- **기후대기·생활환경 본부는 산하 실 하나씩만 쓴다** — 본부 자체는 쓰지 않는다
- **경영지원실**은 ERP상 기획경영본부 산하 실이다(AI홍보전략실의 형제, 소속 관계 아님).
  「본부 취급」이라는 말이 있어 Q2로 확인한다

### 1.1 단위 나무 (RU-09)

상하 관계는 새로 저장하지 않고 **`Division.parentKo`를 쓴다** — 인원 최신화(RS)가 ERP의 「상위부서」로
매주 맞춰 주는 값이다. 따로 두면 두 값이 갈라진다.

| 용어 | 정의 |
|---|---|
| **최상위 단위** | `parentKo`가 연구원(한국환경연구원)인 부서 — 본부 6곳 + 본부 밖 단위 |
| **쓰는 단위** | 켜진(`isActive`) 부서 — 실·팀 단계(제출 → 병합 → 검토)를 도는 곳 |
| **본부의 기여 단위** | 본부 자신(켜져 있고 `rollupSelf`) + 산하의 쓰는 단위. 순서는 `rollupOrder`, 없으면 ERP(등록) 순서 |
| **본부 단계가 있는 본부** | 기여 단위가 **둘 이상**인 본부 (RU-07) |

기본 순서가 등록 순서인 이유: 부서는 ERP 인원 현황 순서대로 등록됐고(임원실 → 감사실 → 글로벌대외협력단 →
기획경영본부 → 기획조정실 → 연구관리실 → …), 그게 조직도 순서다.

## 2a. 자동 진행 — 승인이 곧 제출 (RU-70~79, 2026-10-08) ★

결정 [ADR-0015](../adr/0015-approval-is-handoff.md) · 권한 [TACP-23](../../TACP.md) · 병합본 승인 [HM-47](08-hwp-merge-engine.md) · 알림 §8

2026-10-07판은 한 주를 끝내려면 버튼 다섯이 필요했다 — 담당자 [본부에 제출] · 본부 담당자 [이어 붙이기] · 본부장 [승인] ·
본부 담당자 [총괄에 제출] · 총괄 [전사 취합본 만들기]. 그중 **결정은 둘**(실·팀장 승인, 본부장 승인)이고 셋은 결정을 다음 사람에게
옮기는 일이었다. 옮기는 사람은 결정이 끝났는지 물어서 알아야 했다.

**같은 날 운영자 결정 a~f (2026-10-08 — 「더 쉽게, 빠르게, 정확하게」, 비상구는 최소로)** — 첫 구현을 점검하며 남은 틈을 닫는다.
a) 비상구는 「본부 → 총괄」 기한 + 24시간에 닫힌다(RU-77) · b) 부서장 없는 단위는 병합 결과와 **그 단위 lead의 저장**만 저절로 올린다(RU-71) ·
c) 병합의 파일 쓰기와 성공 기록을 승인·저장과 같은 잠금 안에(RU-75) · d) 본부본 다시 만들기가 실패해도(Qf) 마지막으로 만든 본부본은 승인할 수 있다(RU-55) ·
e) NT-52는 승인마다 한 번(§8) · f) 알림은 보내기 **전에** 기록을 잡는다(§8). 남은 위험은 이 절 끝 「남은 위험」.

| ID | 요구 |
|---|---|
| RU-70 | **사람의 결정은 둘이다** — 실·팀장 승인(HM-47 — [고칠 것 없음 · 승인] 또는 고쳐 저장)과 본부장 승인(RU-55). 위로 보내기·이어 붙이기·총괄로 보내기·전사본 만들기는 Tincase가 한다. **3단계가 꺼져 있으면(RU-52) 아무것도 저절로 가지 않는다**(RU-79) |
| RU-71 | **「있어야 할 상태」를 계산해 맞춘다.** 단계마다 지금 위에 올라가 있어야 할 것을 DB 기록만으로 계산하고, 다르면 맞춘다(reconcile). 맞추는 함수는 셋 — `syncUnit(부서, 주차)` · `syncHq(본부, 주차)` · `syncOrg(주차)` — 이고 `src/server/rollup/handoff.ts`(사본)·`auto.ts`(조립)에 산다. **보낼 판**: 부서장이 있는 단위는 **가장 최근 넘김 사건의 판** — 승인(그 불변 사본)과 비상구(RU-77) 중 나중 것. 맞추기는 「지금 사본보다 **나중에** 생긴 승인이 아직 안 넘어갔으면 넘긴다」이다(비상구로 올린 판을 그보다 앞선 승인으로 되돌리지 않는다). 부서장이 없는 단위는 **마감 뒤 최종본(HM-34)의 지금 파일 — 그 판을 마지막으로 쓴 것이 병합이거나 그 단위 lead의 수정 저장일 때만**(2026-10-08 결정 b — 운영자의 저장은 그 단위의 결정이 아니다, 아래 「부서장이 없는 단위」), 본부는 **가장 최근 본부장 승인이 붙은 본부본**(비상구와는 위와 같이 나중 것), 본부장이 없는 본부는 지금 본부본. 「부서장(본부장)이 있다」 = 그 부서에 켜진 계정 중 `divisionRole = head`가 있다 — 사건마다 다시 본다 |
| RU-72 | **시키는 곳** — 아래 표. 넘김(사본)은 **결정한 요청 안에서**, 조립은 그 요청의 `after()`에서, 놓친 것은 **화면을 여는 순간**(읽기 수리)이 따라잡는다. 스케줄러는 켜져 있을 때의 안전망일 뿐이다 — 스케줄러가 꺼진 테스트 서버(RU-41)에서도 흐름 전체가 돈다 |
| RU-73 | **정확성 — 자동 사본은 승인한 바이트다.** 실·팀: 승인 요청이 본 판(runId·sha, HM-47)을 확인한 **바로 그 메모리의 바이트**를 불변 파일로 쓰고(`MergeReview.filePath`) 사본은 그 파일이다 — 병합본 파일을 다시 읽지 않는다(그 파일은 다시 병합·수정 저장에 덮인다, HM-49). 본부: 본부본은 실행마다 따로 쓴 파일이라 덮이지 않는다 — 승인은 본 판(runId·sha)에만 붙고(RU-55), 사본은 그 실행 파일을 sha로 다시 확인해 쓴다. 쓰기 전·후에 sha가 승인 기록과 다르면 **넘기지 않고** 오류로 남긴다. 승인 뒤 바뀐 판은 다시 승인해야 올라간다 |
| RU-74 | **멱등 열쇠** — 아래 표. 같은 상태에서 몇 번을 맞춰도 행이 늘지 않는다. 그래서 시키는 곳이 여럿이어도 된다 |
| RU-75 | **동시성** — 아래 「동시성」. 같은 부서·주차의 승인·저장·비상구는 줄을 서고, 조립은 한 번에 하나(밀린 것은 한 번만 더), DB가 「가장 최근 승인만」을 한 번 더 막는다 |
| RU-76 | **실패** — 아래 표. 사본은 승인과 같이 성공하거나 같이 실패한다(반쪽 승인 없음). 조립 실패는 남기고 알리고, **그때만** [다시 시도]가 보인다 |
| RU-77 | **비상구 — 승인 없이 올리기.** 승인할 사람이 없으면(출장·휴가) 그 단계 기한 15분 전부터 **「본부 → 총괄」 기한 + 24시간까지** lead가 지금 판을 올린다(닫히는 시각은 2026-10-08 결정 a — 읽기 수리·스케줄러의 창 끝과 같다). 위에서는 주황 「부서장(본부장) 승인 없이」 — 아래 「비상구」 |
| RU-78 | **기록** — 사본은 결정한 사람(승인한 head·비상구를 쓴 lead) 이름으로, 조립과 부서장 없는 단위의 사본은 `system` + 일으킨 사건(`cause`)·사람(`causedBy`)으로 (TACP-23). 화면은 `system`을 「자동」으로 쓴다 |
| RU-79 | **켜기·끄기** — 꺼져 있으면 넘김·조립·3단계 알림이 없다(승인은 HM-47 그대로, 불변 사본은 남긴다). **켜는 순간** 이번 주를 맞춘다: 승인이 있는 실·팀은 그 승인의 불변 사본이(승인 뒤 바뀌었어도 — 승인한 것이 그것이다. 화면은 「승인 뒤 바뀜」), 부서장 없는 단위는 최종본이, 그 위로 본부본·전사본이. 기록은 `system` + 켠 사람. 지난 주의 실·팀 사본은 만들지 않는다. v1.7 전의 승인(불변 사본이 없다)은 그 실행의 파일이 **아직 승인한 sha와 같을 때만** 그때 사본을 떠서 올린다 — 다르면 승인한 바이트가 이미 사라졌으므로 올리지 않는다(승인 안 된 것을 승인한 것으로 보내지 않는다). 끄면 그때부터 아무것도 저절로 가지 않고, 이미 올라간 것은 그대로 남는다 |

### 멱등 열쇠 (RU-74)

| 맞추는 것 | 열쇠 | 같으면 |
|---|---|---|
| 실·팀 사본 | (부서, 주차, 보낼 판의 sha, 근거 `basis`) | 지금 사본과 sha·근거가 같으면 새 행을 만들지 않는다(RU-02). 승인 하나에 사본은 많아야 하나(`reviewId` 유일) |
| 본부본 | `inputKey` = sha256(JSON {판 1, 본부 id, 기여 단위 **순서대로** (부서 id, 지금 사본 id 또는 null), 쪽 나누기, 양식(부서 양식 id·판 / 표준 판)}) | 가장 최근 **성공한** 본부본 실행의 열쇠와 같으면 만들지 않는다 |
| 본부 사본 | (본부, 주차, 승인한 본부본의 sha, 근거) | 실·팀 사본과 같다 |
| 전사본 | `inputKey` = sha256(JSON {판 1, 섹션마다 `inputKey(s)`(orgrun.ts — 제목 포함), 쓴 양식 표지(RU-68)}) | 같으면 만들지 않는다 |

**본부본 열쇠에 섹션 제목을 넣지 않는다.** 넣으면 총괄이 섹션 제목을 고칠 때마다 모든 본부본이 다시 만들어지고 본부장 승인이
풀린다 — 내용은 그대로인데. 최종본은 언제나 지금 제목으로 만들어진다(전사는 본부본을 다시 읽지 않고 그 안의 사본을 쓴다, RU-60·67).
본부본은 다음에 다시 만들어질 때 새 제목을 받는다. 같은 이유로 본부 메모(RU-21)도 넣지 않는다.

### 동시성 (RU-75)

- **같은 (부서, 주차)의 승인·수정 저장·비상구는 줄을 선다** — 프로세스 안 열쇠 잠금 `unit:<부서>:<주차>`. 「본 판 확인 → 불변 사본 →
  (고쳐 저장이면) 병합본 쓰기 → 승인 기록·실·팀 사본(한 트랜잭션)」이 한 덩어리다. 지금도 있던 틈(둘이 같은 판을 보고 동시에 저장)이 함께 닫힌다
- **병합의 「파일 쓰기 → 성공 기록」도 같은 줄에 선다** (2026-10-08 결정 c) — 병합(제출물 읽기·모델 호출·조립)은 잠금 **밖에서** 바이트를 만들고,
  주차마다 같은 자리인 병합본 파일을 쓰고 `MergeRun`을 `succeeded`로 적는 짧은 두 걸음만 `unit:` 잠금 안에서 한다 — 잠금이 모델을 기다리면
  그동안 승인·저장이 1분씩 멈춘다. 전에는 그 두 걸음 사이에 수정 저장이 끼어 「새 실행이 가리키는 파일 = 담당자가 고친 바이트, 고친 기록은 옛 실행에」가
  되거나, 저장한 수정이 기록 없이 덮였다(HM-49가 지키지 못한다). 이제 저장은 병합의 쓰기·기록보다 앞이거나(병합이 나중 판이다 — 「저장 뒤 다시 병합」과
  같은 일, 고친 기록은 옛 실행에 남는다) 뒤다(새 실행을 보지 않았으니 409 — 다시 열어 고친다). 병합 뒤의 맞추기(`afterMerged`)는 잠금 밖에서 — 같은 잠금을 다시 쥔다
- **조립은 한 번에 하나, 밀린 것은 한 번만 더** (single-flight + dirty) — `hq:<본부>:<주차>`·`org:<주차>`. 돌고 있는데 또 시키면 표시만 하고,
  끝나면 열쇠를 다시 계산해 한 번 더 본다. 승인 다섯이 1분 안에 몰려도 본부본은 많아야 두 번 만들어지고 마지막 것이 마지막 입력을 담는다.
  읽기 수리는 돌고 있는 조립을 **기다렸다가** 그린다
- **본부장 승인·본부 비상구는 `hq:<본부>:<주차>` 안에서** — 조립과 엇갈리지 않는다. 승인 직전에 조립이 끝나 판이 바뀌었으면 409(본 판이 아니다)
- **DB가 한 번 더 막는다** (잠금이 프로세스 안이라서): 사본 만들기는 트랜잭션 안에서 「이 승인이 그 부서·주차의 **가장 최근** 승인인가」, 「지금 사본보다
  나중 것인가」(비상구 사본 포함), 「지금 사본의 sha·근거」를 다시 본다 — 늦게 도착한 옛 승인이 새 승인이나 그 뒤의 비상구를 덮지 않는다. `ReportSubmission.reviewId`는 유일하다
- **스케줄러 병합과 승인이 엇갈려도 정확하다** — 승인은 본 판의 바이트를 이미 들고 있다(RU-73). 병합이 뒤에 끝나면 「승인 뒤 바뀜」이 되고 NT-52가 간다
- **같은 판의 재승인이 새 결정일 때** (2026-10-08 검증): 같은 판(sha)을 이미 승인했어도, 그 승인 **뒤에** 그 승인과 다른 사본이 위에 가 있으면
  (비상구 — RU-77) 지금 [승인]·고쳐 저장은 「같은 일 두 번」이 아니라 승인한 판으로 되돌리는 새 결정이다 — 새 승인 기록과 사본(`supersededSince`).
  예: 실장 X 승인 → 담당자 Y로 고쳐 비상구 → 담당자 X로 되돌림 → 실장 X 승인. 예전 판정으로는 「이미 승인한 판」이라 위에 승인 없이 간 Y가 남고
  아무도 바꿀 수 없었다(RU-T131 · 본부는 RU-T134). 위의 사본이 이 판의 승인으로 간 것(따라잡기 포함)이면 새 결정이 아니다
- **같은 바이트의 새 실행을 승인하면** 새 사본은 없지만(RU-02) 응답 `handedOff`와 NT-46′은 「올라가 있음」이다 — 위에 이미 그 바이트가 승인으로 가 있다(RU-T132)
- `running`으로 남은 조립(프로세스가 죽음)은 10분이 지나면 실패로 보고 다시 만든다
- **한 프로세스가 전제다** (한 컨테이너 · SQLite — ADR-0003). 둘이 되면 잠금을 DB 임대로 바꾼다 — 그때도 위 DB 막이가 중복·뒤바뀜은 막는다.
  한 프로세스 안에서도 Next는 같은 파일을 번들 층마다(스케줄러 instrumentation · 라우트 처리기 · 서버 컴포넌트) 따로 실을 수 있어, 잠금 표는
  모듈 변수가 아니라 `globalThis`에 둔다 — 스케줄러의 맞추기와 승인 요청이 서로의 잠금을 본다(2026-10-08 검증)

### 실패 (RU-76)

| 실패 | 어떻게 되나 | 누가 아나 | 비상구 |
|---|---|---|---|
| 승인 요청 안에서 불변 사본 쓰기 실패 (디스크 등) | **승인째 실패**(500). 불변 파일을 **맨 먼저** 쓰므로(고쳐 저장이면 병합본을 덮기 전에, HM-47) 아무것도 바뀌지 않는다 — 사본 없는 승인도, 승인 없는 수정도 남지 않는다 | 누른 부서장 (화면) | 없음 — 다시 누른다 |
| 본부본 조립 실패 (양식 없음 · 사본 전부 손상) | 실행을 `failed` + 이유로 남긴다. **같은 열쇠로는 사건이 다시 몰아치지 않는다** — 스케줄러·읽기 수리는 HM-43처럼 1·5·15·30분 간격 | 본부 화면(이유) · 본부 담당자에게 한 번(RU-57b) | **[다시 시도]** — 실패 상태일 때만, 본부 lead·head |
| 사본 하나를 못 읽음 | 그 섹션 자리에 실패를 적고 나머지는 만든다(HM-21 · RU-19) — 실행은 성공, 「확인해 주세요」 | 본부 화면 | 그 실·팀이 다시 승인 |
| 전사본 조립 실패 | 본부본과 같다 | 「전사」 화면 · 총괄에게 한 번(RU-57b) | **[다시 시도]** — 실패 상태일 때만, 총괄·운영자 |
| 요청 뒤(`after()`) 조립 전에 프로세스 종료 | 사본은 이미 커밋됐다 | — | 필요 없다 — 화면 열기·스케줄러가 따라잡는다 |
| 알림 실패 | 넘김·조립은 그대로 (알림은 결과이지 조건이 아니다, HM-47) | 로그 | — |
| **승인할 사람이 없다** (출장·휴가) | 그 단계가 멈춘다 | 기한 15분 전 알림(RU-56·56a)이 막고 있는 사람에게 | **[승인 없이 올리기]** (RU-77) |

[다시 시도]는 **실패한 시도와 열쇠가 같아도**(기다리는 간격 RU-76을 건너뛰고) 한 번 더 만든다는 것만 다르다 — 입력은 고르지 못한다(TACP-23).
마지막이 **성공**이고 열쇠가 같으면 API로 불러도 아무것도 하지 않는다(RU-T106) — 그래야 본부 lead가 [다시 시도]로 본부장 승인을 풀 수 없다(조립 결과가
바이트 단위로 같다는 보장이 없으므로, 다시 만들면 sha가 바뀌어 승인이 풀릴 수 있다). **성공 상태에서는 그리지 않는다**:
들어온 것이 바뀌면 이미 다시 만들어지므로 누를 이유가 없고, 누를 이유가 없는 버튼은 「눌러야 하나?」를 만든다.

### 비상구 — 승인 없이 올리기 (RU-77)

예전에는 승인이 늦으면 담당자가 [제출]을 눌러 넘겼다(CP-99 — 보조 버튼). 그 길 하나를 좁혀 남긴다. 승인할 사람이 자리에 없는
날은 실제로 있다(HM-44의 2026-09-17 — 담당자 출장. 부서장도 같다).

- **누가**: 실·팀은 그 부서 lead, 본부는 그 본부 lead (`requireHandoffEscape`). head는 승인하면 되므로 없다.
  부서장(본부장)이 **없는** 단위·본부에는 비상구가 없다 — 저절로 올라가기 때문이다(409 `no_head`, 구현 2026-10-08)
- **언제**: 그 단계 기한 **15분 전부터** — 실·팀은 본부 단계가 있으면 「실·팀 → 본부」, 없으면 「본부 → 총괄」 기한, 본부는 「본부 → 총괄」(RU-51·59).
  기한은 주차 마감에서 계산하므로 마감을 옮기면(WS-19) 같이 옮겨진다. 그 전에는 그리지 않고 API는 409 `too_early`.
  일찍 열면 승인을 건너뛰는 버릇이 된다 — 승인 전에 보냈다가 실장이 고쳐 다시 내던 일(CP-99)이 그렇게 생겼다
- **언제까지** (2026-10-08 결정 a): **「본부 → 총괄」 기한 + 24시간까지** — 실·팀·본부 모두 같은 끝이고, 읽기 수리·스케줄러가 그 주를 맞추는 창의
  끝(`liveUntil` — 화면 열기의 `isLiveSlot`과 같은 계산)이다. 지나면(지난 주차 포함) 링크를 그리지 않고 API는 409 `too_late`.
  그 주의 보고는 이미 총괄을 지나 NAMS로 갔다 — 그 뒤에 승인 없는 판을 올려 받은 전사본을 바꾸는 길은 남기지 않는다. 승인은 막지 않는다
  (부서장이 늦게라도 승인하면 그 판이 대신한다 — 사람의 결정이다). 이번 주라도 창이 지나면 닫힌다: 읽기 수리는 이번 주를 계속 맞추지만 그것은
  이미 내린 결정의 결과일 뿐이고, 비상구는 결정 없이 올리는 길이라 더 좁게 둔다
- **무엇을**: 지금 판이 **승인되지 않았을 때만**(승인 전 · 승인 뒤 바뀜). 실·팀은 병합본의 지금 파일(마감 뒤 최종본이어야 한다 —
  미리보기는 409 `not_final`), 본부는 지금 본부본. 그 순간의 바이트를 불변 사본으로. 지금 판이 이미 올라가 있으면 409 `already_sent` —
  「이미 올라가 있다」 = 위의 사본이 지금 판이거나, 지금 판의 승인이 위의 사본보다 나중이다. 지금 판을 예전에 승인했어도 그 뒤 다른 판(비상구)이
  위에 가 있으면 올라가 있지 않다(2026-10-08 검증 — 예전에는 거짓 409로 막혔다)
- **보이게**: 사본 `basis = unapproved`. 위의 모든 화면(본부 산하 현황·본부본 결과·「전사」 표)에 주황 「부서장 승인 없이」·「본부장 승인 없이」,
  기록에 누른 사람(TACP-23)
- **그다음**: 부서장(본부장)이 나중에 승인하면 승인한 판이 대신한다 — 같은 판이어도 근거가 바뀌므로 새 사본 행(앞의 것은 이력)
- **화면**: 그 단계 카드 끝의 글자 링크 「부서장 승인 없이 올리기」. 누르면 그 자리에서 한 번 더 묻는다
  (「○○ 실장 승인 없이 기획경영본부에 올립니다 — 위에서는 주황으로 보입니다」)

### 상태 기계 — 실·팀 (부서 D · 주차 W · 3단계 켜짐 · D가 기여 단위)

읽는 것: 최신 병합본의 판(runId·sha)과 마감 뒤 최종본인지(HM-34) · 가장 최근 승인 A(불변 사본·sha) · 지금 사본 S(sha·근거) · 부서장이 있나.

- **마감 전 미리보기를 승인해도 올라간다** (U0 → U2). 승인한 것이 그것이기 때문이다 — HM-44로 자동 병합을 멈춘 주에 실제로 그렇게 냈다.
  14:01 최종본이 판을 바꾸면 U3 + NT-52 — 부서장이 다시 승인하면 최종본이 올라간다
- **HM-49와 만날 때**: 고쳐 저장(= 승인)한 최종본은 마감 열기가 닫혀도 다시 병합되지 않는다 — 올라간 것도 그대로다. 담당자가 늦게 낸 사람을
  넣으려고 [다시 병합](덮기)을 고르면 판이 바뀌어 U3이 되고, 부서장이 다시 승인해야 올라간다. 고치지 않고 [고칠 것 없음 · 승인]만 한 최종본은
  닫힌 뒤 저절로 다시 병합된다(HM-49 대상 아님) — 역시 U3 + NT-52
- **부서장 승인 뒤 담당자가 고치려고 병합본을 열면** 수정 칸 맨 위에 한 줄: 「고쳐 저장하면 부서장이 다시 승인해야 올라갑니다」

| H2 운영자가 고친 판 · 안 올라감 | 마감 뒤 최종본의 지금 판을 마지막으로 쓴 것이 그 단위 lead가 아닌 사람(운영자)의 수정 저장, S.sha ≠ 지금 sha (2026-10-08 결정 b) | 주황 「운영자가 고친 판은 아직 안 올라감 — 담당자가 확인해 저장하거나 다시 병합하면 올라갑니다 · 지금 ○○에는 14:01 판」 |

마감 뒤 병합 성공·**그 단위 lead의** 고쳐 저장(마감 뒤 최종본) → `syncUnit`(`system`, `basis=no_head`) → H1. 마감 전 미리보기는 올리지 않는다.
**운영자의 저장은 올리지 않는다** (2026-10-08 결정 b). 부서장이 없으면 그 단위의 마지막 판단은 그 단위 lead의 것이다 — 운영자는 시스템 소유자이지
그 부서의 결정권자가 아니다(TACP-3 「문서는 부서가」). 운영자가 고친 판은 H2로 남고, 다음 병합(그 실행에는 고친 기록이 없다)이나 lead의 저장이
그때의 판을 올린다 — lead가 그 위에 고쳐 저장하면 운영자가 고친 곳까지 lead가 보고 낸 것이다. 판정은 상태로 한다: `syncUnit`이 그 실행의
`reviewJson.edits` 마지막 줄(`role` — `head`·`lead`·`operator`)을 본다(스키마는 그대로). 그래서 요청이 아닌 맞추기(스케줄러·켜기·읽기 수리)도
운영자의 판을 올리지 않는다. 바뀐 곳이 없는 저장도 바이트가 바뀌었으면 한 줄을 남긴다(`places: 0` — HM-49의 「고친 곳」에는 세지 않는다).
lead가 운영자의 판을 그대로 받아들여 바꾼 것 없이 저장해도 한 줄을 남기고 올린다.
**왜 기한까지 기다리지 않나**: 부서장이 없으면 담당자의 저장이 그 단위의 마지막 판단이다. 기한(15:00)까지 묵히면 본부장이 볼 시간이 그만큼 줄고,
그 시각을 맞추려면 스케줄러가 있어야 한다(테스트 서버에서 멈춘다). 담당자가 뒤에 고치면 고친 것이 곧 올라가고, 본부장이 이미 승인했으면 승인이
풀려 그 사실이 보인다(RU-55a) — 조용히 바뀌는 곳이 없다. 부서장 계정이 생기면 그 뒤로는 승인이 있어야 바뀐다(이미 올라간 것은 그대로).

- **본부장이 일부만 모인 본부본을 승인할 수 있다** — 늦게 온 단위가 붙으면 Q3이 되고 다시 승인한다. 화면은 승인 버튼 옆에 「아직 ○○ 미제출 —
  승인 뒤에 올라오면 다시 승인해야 합니다」
- **다시 이어 붙이기가 실패해도(Qf) 마지막으로 만든 본부본은 승인할 수 있다** (2026-10-08 결정 d). 실패는 대개 양식·사본 하나의 문제라 고치는 데
  시간이 걸리고, 그동안 본부장이 아무것도 못 하면 기한에 본부가 통째로 빈다(비상구는 lead의 것이다). 승인은 언제나 **본 판**(runId·sha, RU-55)에만 —
  화면이 그린 그 마지막 본부본이다. 새로 올라온 것이 그 판에 없다는 것은 실패 줄(「아래는 그 전에 이어 붙인 본부본」)과 승인 버튼 옆 한 줄
  (「승인하면 이 판이 총괄로 갑니다 — 새로 올라온 것은 빠져 있어요」)이 말한다. 고친 뒤 다시 만들어지면 판이 바뀌어 Q3 — 다시 승인한다
- **승인 뒤 바뀌면 총괄에는 승인한 판이 남는다** (§12 Q10). 빼면 16:00에 그 본부 섹션이 비고, 새 판을 두면 승인 안 된 것이 간다.
  「전사」 표는 그 섹션을 「본부장 재승인 대기」로 보인다(RU-83). 「옛 판」은 **내용(sha)으로** 본다 — 비상구 사본을 부서장이 같은 바이트로 뒤늦게
  승인하면 사본 행은 새것이지만 본부본은 같은 바이트로 다시 만들어지고 본부장 승인은 그대로다(Q2). 행 id로 보면 할 일이 없는 본부장을 가리킨다(RU-T133)
- **본부장이 없는 본부**는 Q1이 곧 넘김이다 — 다시 만들어질 때마다 본부 사본 `basis=no_head`(`system`)
- **본부 자신의 문서**(rollupSelf)는 실·팀 단계를 그대로 돈다 — 본부장의 병합본 승인(HM-47, `UNIT_REVIEW`)이 그 사본을 만들고, 본부본 승인
  (`hq_approve`)은 따로다. 둘은 서로를 승인으로 세지 않는다(HM-47 `UNIT_REVIEW`)

모두 **더하기만** 한다 — 운영 DB에 `prisma db push`해도 기존 값이 바뀌지 않는다.

```prisma
model Division {
  // … 기존 …
  rollupOrder     String  @default("[]")  // RU-20 — 기여 단위 id 순서 (JSON)
  rollupNote      String  @default("")    // RU-21
  rollupPageBreak Boolean @default(true)  // RU-18
  rollupSelf      Boolean @default(true)  // RU-08

model RollupRun        { level "hq"|"org", divisionId?(org는 null), weekSlotId, status, outputPath, inputIds(JSON, 붙인 순서), unitsJson, warnings, errorText, createdBy }
model OrgRollupSetting { id "org", order(JSON), note, pageBreak }

// 2026-10-08 자동 진행(§2a)이 더하는 것 — 모두 비어 있어도 되는 칸이라 옛 행은 그대로 읽힌다
model MergeReview      { … filePath String? }        // RU-73 · HM-47 — 승인한 판의 불변 사본 (본부 승인은 그 본부본 실행 파일). v1.7 전 행은 null
model ReportSubmission { … reviewId String? @unique  // RU-74 — 이 사본을 낳은 승인. 승인 하나에 사본은 많아야 하나
                           basis    String  @default("manual") // RU-77·78 — approved | no_head | unapproved | manual(v1.7 전의 [제출]) · 적재본은 origin=import

model RollupRun        { … inputKey String?          // RU-74 — 같은 열쇠면 다시 만들지 않는다
```

`ReportSubmission.submittedBy`·`RollupRun.createdBy`에는 사람 id 대신 **`'system'`**이 들어갈 수 있다(RU-78). 이름을 찾는 곳은 그것을
「자동」으로 쓴다 — 지금처럼 「알 수 없음」이 되지 않게.

- **상위 관계는 저장하지 않는다** — `parentKo` (§1.1)
- 본부·전사 결과를 `MergeRun`에 넣지 않는다 — 연구 본부처럼 같은 부서가 실·팀 병합과 본부 병합을 둘 다 가질 수 있다
- 「지금 제출된 것」 = (부서·주차·level)의 가장 최근 **취소되지 않은** 행 (취소는 v1.7부터 생기지 않는다 — RU-03)

## 6. 권한 — [TACP-21](../../TACP.md) · [TACP-23](../../TACP.md)

- 실·팀 사본: **그 부서 head의 승인이 만든다**(RU-70). [제출]·취소는 없다. lead는 비상구 「승인 없이 올리기」만(RU-77)
- 본부: 순서·쪽 나누기·자기 문서 포함은 **본부 단계가 있는 본부**의 lead·head. 이어 붙이기는 자동. **본부본 승인 = 총괄로 제출**은 그 본부의 head만
  (`requireHqReviewer`, 본 판에만). lead는 비상구 「승인 없이 총괄로」만. 실패 때 [다시 시도]는 lead·head. 산하의 **보낸 사본**만 읽는다
- 전사: 전사본은 자동. 섹션 구성·본부 순서·섹션 파일 올리기, 실패 때 [다시 시도]는 coordinator·operator
- 총괄이 올린 섹션 파일 내려받기: 전사 취합의 문(`canOpenOrgDesk`)과 같은 사람 — 판정·기록은 `findReadableSectionUpload` 하나(취소한 파일은 404, 받으면 `download` 기록)
- coordinator·operator는 남의 단위를 **대신 제출·승인하지 않는다** — 빠진 곳은 「미제출」로 보인다. 자동 조립(`system`)도 무엇을 붙일지
  요청에서 받지 않는다 — 나무와 받은 사본이 정한다(TACP-23)
- 실·팀 lead·head는 **내 사본의 행방**(본부 도착 · 본부장 승인 · 총괄 도착 시각)을 본다 — 본부본의 내용·다른 단위는 아니다(TACP-21 v1.7)

## 8. 단계 일정과 알림 (RU-50~58)

운영자 요청(2026-10-07): 「총괄은 이번 주처럼 휴일 때문에 하루 짧아질 때 이걸 지정할 수 있게, 알림도 그에 맞춰
당겨지게」. 그래서 **3단계의 모든 시각은 그 주의 부서 마감 하나에서 계산한다** — 총괄이 공지를 붙여넣어
마감을 옮기면(WS-19) 실·팀 → 본부 → 총괄의 기한과 알림이 **한꺼번에 같은 간격으로** 옮겨진다.

**기록을 먼저 잡고 보낸다 (2026-10-08 결정 f).** 같은 알림을 두 곳이 판정한다 — RU-54는 「다 모인 순간」(조립 직후)과 「실·팀 → 본부」 기한(스케줄러),
RU-57도 같다. 전에는 보낸 **뒤에** 기록을 넣어서, 둘이 같은 순간에 돌면 둘 다 「아직 안 보냄」을 보고 본부장에게 같은 알림이 두 번 갔다.
이제 보내기 **전에** (부서·주차·종류) 유일 키로 `NotifyLog`를 넣고, 넣은 쪽만 보낸다. 다 보낸 뒤 받은 사람·걸러진 사람을 그 줄에 적는다.
아무에게도 나가지 않았으면(대상 0명·전송 실패) 잡은 줄을 지운다 — 「실제로 나간 것만 기록한다」(메신저가 꺼진 동안의 「보냄」이 남지 않는다)는 그대로다.
NT-52(`merge_reapprove`)도 같은 방식이다.
**잡기에 진 「다 모인 순간」은 잡힌 줄을 다시 읽는다** (2026-10-08 검증). 기한 판정이 일부(1/2)를 보고 먼저 잡았는데 다 모인 순간의 판정이 그보다
앞서 「아직 안 보냄」을 봤으면, 진 쪽이 그대로 물러날 때 본부장(총괄)은 「1/2 준비」만 받고 「다 모였어요」(`ru_hq_complete`·`ru_org_complete`)를
끝내 못 받는다. 진 쪽은 그 줄을 다시 읽어 일부(`complete: false`)였으면 「다 모였어요」를 보낸다 — 순서대로 돌았을 때와 같은 두 통이다.

**(2026-10-08) 언제 판정하나.** 사건 알림(RU-54의 「다 모임」·55a·57의 「모두 들어옴」·57a·57b)은 그 사건을 맞춘 `sync`의 끝(`after()`)에서
바로 판정한다 — 스케줄러를 기다리지 않는다. 시각 알림(RU-54·57의 기한분, RU-56·56a)은 지금처럼 스케줄러(`runDueRollupNotices`)가 판정한다.

테스트 서버는 메신저가 꺼져 있어(RU-41) 아무것도 나가지 않고 `NotifyLog`도 남지 않는다 — 흐름은 그대로 끝까지 간다.

### RU-63 정규화 규칙 (2026-10-07 실제 최종본 검증 반영)

9월 4주차 **실제 최종 취합본**을 섹션별로 쪼개 엔진에 다시 넣어 봤다(원본은 로컬에만 — 실명·업무 내용 포함).
구조 검사는 모두 통과했지만 정규화가 **멀쩡한 데이터를 바꾼** 곳이 있었다 — 칸 수로 행 종류를 가르고, 열 수만으로
표 종류를 가른 탓이다. 그래서 판정을 **머리행 글자와 번호 칸**으로 한다. 원칙: **알아보지 못한 표·행은 건드리지 않는다**
(고칠 기회를 놓치는 것은 경고로 남지만, 잘못 고친 것은 아무도 모른 채 최종본에 들어간다).

| 규칙 | 내용 | 실측 사례 (구조만) |
|---|---|---|
| R1 업무 표(실형 5열) | **5열 + 머리행 1열 「구분」 + 3열이 일자 칸(「일자」·「업무 기간」)**. 이 표만 빈 줄 삭제·번호 다시 매김·「특이사항 없음」·일자 경고를 한다 | — |
| R2 집계표는 업무 표가 아니다 | 본부·센터의 「※ 자문회의 실적」 표(`구분 \| 자문회의 \| 전문가 세미나 \| …`)도 5열·「구분」으로 시작한다. 실마다 「-」뿐인 줄이 **정상**이다 — 지우면 그 실이 표에서 사라진다. 손대지 않고 일자 경고도 내지 않는다 | 「-」 줄이 지워지고 「1건」이 일자 경고로 뜸 |
| R3 본부형 과제 표 | **6열 이상 + 머리행 「구분 \| 유형」**. 7열은 일자 칸이 두 칸 병합된 변형이다 — 같은 규칙으로 고친다 | 7열 표가 정규화되지 않음 |
| R4 항목 행 = 번호 칸으로 | 2열(번호 칸)이 `n-n`이면 **항목 행**, 유형 단어(기본·수탁·일반…)면 **과제 행**(손대지 않는다). 번호 칸이 비었으면 과제명 칸이 책임자 칸 바로 앞까지 병합되지 않은(= 항목 꼴) 줄만 항목 행으로 본다. **칸 수로 가르지 않는다** — 1열 「구분」(실 이름)이 여러 줄 병합되면 그 아래 항목 행은 5칸·3칸이 된다. 번호는 표 전체 연속(Q7) | 병합 아래 항목 행을 건너뛰어 올바른 `1-1…1-5`가 중복 번호로 바뀜 |
| R5 머리행 이름 | 「업무 기간」→「일자」, 「업무 담당 또는 참석자」·「업무 담당 또는 참석 인원」→「참석자」 (빈칸·한 문단 안 줄바꿈은 무시하고 비교). **글자 든 문단이 둘 이상인 칸(Enter로 나눈 것)은 건드리지 않는다** — 칸 글자 바꾸기는 첫 문단만 바꿔 「참석자⏎참석 인원」이 된다 | 「참석 인원」 꼴이 통일되지 않음 |
| R6 일자 표기 경고 | 일자 뒤의 **시각**(`10/1 14:00`, `14:00~16:00`)은 떼고 본다 — 시각을 적는 것은 정상이다 | `10/1 14:00`이 경고로 뜸 |
| R7 뺀 것 기록 | 본문 앞의 빨간 `※ … 작성 必`도 「제목」이 아니라 **「안내문」**으로 적는다 — 총괄이 「무엇을 뺐나」를 보고 판단한다 | 안내문이 「제목 …」으로 기록됨 |

테스트: `tests/normalize.test.ts` RU-T60~68(RU-T61b·67b 포함) — 실제 파일 없이 **합성한 표**로 R1~R6을 하나씩 본다(CI에서도 돈다).
