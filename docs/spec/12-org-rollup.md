## 0. 요구 (2026-10-07 사용자 정리)

1. **6개 본부별로 운영한다.**
2. 실·팀 단계는 **지금과 같다** — 부서원 제출 → 자동 병합 → 실장 검토 → 담당자 제출.
3. 본부 단계 — 산하 실·팀이 **제출한 병합본을 정해진 순서로 이어 붙인다.** 실·팀 안의 내용
   위치는 바꾸지 않는다(일단 이어 붙이기로 만들고 피드백을 받는다). 본부장 검토 → 본부 담당자가
   **최종 제출 플래그**를 띄운다.
4. 전사 단계 — 총괄(기획조정실)이 본부들의 최종 제출본을 **한 번에 병합**해 끝낸다(NAMS 제출).
5. 본부 담당자와 총괄은 **자기 단계의 병합 순서(프롬프트)를 설정**한다.
6. 지난 주(또는 지난 달) 실·팀 제출 파일 전체로 **비슷한 결과가 나오는지** 테스트 서버(11112)에서 재현한다.
7. **다음 주(10/12 주)부터 전 부서 알림을 켠다.**
8. **11/2(월) 운영회의에서 큰 화면에 띄워 쓴다** — 시연 준비를 꼼꼼히.

읽히는 것:

- **6개 본부 = 위의 여섯**(센터 포함)로 보인다 — §12 Q1로 확인한다
- **연구 본부(국토환경·환경평가·적응센터)는 산하 실이 쓰지 않고 본부가 직접 한 명이 쓴다.**
  이 본부들의 본부 단계는 「자기 문서 하나」다
- **기획경영본부는 산하 실들이 각자 쓴다.** 본부 단계가 실제로 「이어 붙이기」가 되는 곳이다
- **기후대기·생활환경 본부는 산하 실 하나씩만 쓴다** — 본부 자체는 쓰지 않는다
- **경영지원실**은 ERP상 기획경영본부 산하 실이다(AI홍보전략실의 형제, 소속 관계 아님).
  「본부 취급」이라는 말이 있어 Q2로 확인한다

### 1.1 단위 나무 (RU-09)

상하 관계는 새로 저장하지 않고 **`Division.parentKo`를 쓴다** — 인원 최신화(RS)가 ERP의 「상위부서」로
매주 맞춰 주는 값이다. 따로 두면 두 값이 갈라진다.

| 용어 | 정의 |
|---|---|
| **최상위 단위** | `parentKo`가 연구원(한국환경연구원)인 부서 — 본부 6곳 + 본부 밖 단위 |
| **쓰는 단위** | 켜진(`isActive`) 부서 — 실·팀 단계(제출 → 병합 → 검토)를 도는 곳 |
| **본부의 기여 단위** | 본부 자신(켜져 있고 `rollupSelf`) + 산하의 쓰는 단위. 순서는 `rollupOrder`, 없으면 ERP(등록) 순서 |
| **본부 단계가 있는 본부** | 기여 단위가 **둘 이상**인 본부 (RU-07) |

기본 순서가 등록 순서인 이유: 부서는 ERP 인원 현황 순서대로 등록됐고(임원실 → 감사실 → 글로벌대외협력단 →
기획경영본부 → 기획조정실 → 연구관리실 → …), 그게 조직도 순서다.

## 2. 흐름

```
실·팀        부서원 제출 ─► 자동 병합(마감+1분) ─► 실장 검토 ─► 담당자 [본부에 제출] ●
                                                                      │
본부         산하 단위의 「제출된」 병합본을 순서대로 이어 붙임 ─► 본부장 검토 ─► 본부 담당자 [총괄에 제출] ●
                                                                      │
전사(총괄)    본부들의 「제출된」 본부본을 순서대로 이어 붙임 ─► 총괄 검토·수정 ─► hwp ─► NAMS
```

| ID | 요구 |
|---|---|
| RU-01 | **제출**을 둔다. 실·팀 담당자·실장의 [본부에 제출], 본부 담당자·본부장의 [총괄에 제출]. 제출은 **그 순간 병합본의 사본**을 만든다 (`ReportSubmission`) |
| RU-02 | 제출한 뒤 하위에서 다시 병합·수정해도 사본은 **그대로다.** 새 판을 올리려면 다시 제출한다 — 상위가 보고 있던 문서가 몰래 바뀌지 않는다(HM-44와 같은 이유). 화면은 「제출 뒤 병합본이 바뀌었어요 — 다시 제출」을 띄운다. 「바뀜」은 **내용(sha256)**으로 판정한다 — 다시 병합해 같은 파일이 나오면 바뀐 것이 아니다(본부본도 같다) |
| RU-03 | 제출은 **취소**할 수 있다. 상위가 이미 이어 붙였으면 상위 화면에 「바뀜 — 다시 이어 붙이세요」가 뜬다(상위 결과의 입력 목록과 지금 제출된 것을 비교한다) |
| RU-04 | 상위 이어 붙이기는 **제출된 하위만** 쓴다. 미제출 하위는 화면에 「미제출」로 보이고 결과에서는 빠진다(§12 Q4) |
| RU-05 | 본부 자체가 쓰는 문서가 있으면 그것도 본부 단계의 한 단위로 들어간다 — 기본 맨 앞 |
| RU-06 | 본부 밖 단위(글로벌대외협력단·임원실)는 전사 단계에 **직접** 제출한다 |
| RU-07 | **기여 단위가 하나뿐인 본부는 본부 단계가 없다.** 그 단위의 [제출]이 곧 총괄로 간다(버튼도 [총괄에 제출]). 연구 본부(본부가 직접 씀)·기후대기·생활환경(산하 실 하나가 씀)이 여기에 든다 — 지금도 그 단위가 게시판에 바로 올린다 |
| RU-08 | 본부 자기 문서를 넣을지는 본부 설정(`rollupSelf`)이다. 본부 담당자가 산하 실 것만 모으는 본부는 끈다(§12 Q3). 끄면 산하가 하나만 남아 본부 단계가 사라지는 경우(RU-07)는 **받지 않는다**(422) — 본부 화면이 닫혀 다시 켤 곳이 없어진다 |

## 3. 이어 붙이기 규칙 (병합 엔진 L5)

> **2026-10-07 중복 제거** — 본부 단계도 전사 취합과 **같은 엔진**(RU-62)으로 섹션을 원래 꼴 그대로 옮긴다.
> 실형 5열 표를 데이터로 다시 그리던 처음 엔진은 지웠다(아래 「뺀 것」). RU-10·11·12·14·16·17·18을 그에 맞춰 고치고 RU-19(결과 화면)를 더했다.

| ID | 요구 |
|---|---|
| RU-10 | 출력은 **양식 위에** `[섹션 제목] + 원본 본문` 블록을 정한 순서대로 잇는다. 기여 단위가 [본부에 제출]한 **사본 하나가 섹션 하나**다. 조립은 전사 취합과 같은 엔진이다(RU-62 — 섹션 블록을 레코드째 **복제**하고 서식 번호만 대상 문서에 맞게 옮겨 적는다, HM-03 「합성하지 말고 복제하라」). **다시 그리지 않는다.** 섹션 제목은 전사 섹션 설정의 그 부서 제목(RU-61, `기획경영본부(기획조정실)`), 섹션이 없는 부서는 부서 이름 |
| RU-11 | 단위 **안의** 행 순서·구분 번호·파란 「공유」 강조·표 밖의 글은 원래 꼴 그대로 옮긴다. 바꾸는 것은 단위의 **순서**, 그리고 전사와 같은 **정규화**(RU-63 — 어긋난 번호 다시 매김·번호만 남은 빈 줄 삭제·빈 3번 표에 「특이사항 없음」·빨간 안내문 제거)뿐이다. 본부에서도 정규화하는 이유: 전사 취합본은 본부본에 든 실·팀 사본을 같은 엔진으로 다시 조립한다(RU-60) — **본부장이 검토한 꼴이 최종본의 꼴과 같아야 한다** |
| RU-12 | 입력은 하위의 **제출된 사본 파일**이다. 파일을 바이트째 이어 붙이지 않는다 — 문서마다 서식 표(DocInfo)가 달라 섞으면 깨진다. 그래서 본문이 가리키는 서식 번호를 대상 DocInfo로 옮겨 적는다(RU-62) |
| RU-13 | 실제 최종본(NAMS 제출본) 형식에 맞춘다 — **샘플을 받아 테스트 서버에서 대조**한다(§12 Q5). 블록 머리 형식·빈 표 처리·페이지 나눔은 그때 정한다 |
| RU-14 | 결과 검증 — 본문이 가리키는 서식 번호가 **모두 DocInfo 범위 안**이어야 한다(RU-62 `checkReferences`, 어기면 실행을 실패로 남긴다). 다시 읽어 행·구분 번호·강조가 넣은 그대로인지는 테스트(RU-T10)가 본다 — 표를 다시 그리지 않으므로 실행마다 맞춰 볼 변환이 없다 |
| RU-15 | 문단 자기 기술 불변식(HM-46) — 글자·서식 구간·줄 수가 모두 맞아야 한다. 한글이 「손상」으로 보는 지점이다 |
| RU-16 | 단위로 읽기(`readUnits`) — **조립에는 쓰지 않는다.** 결과 화면의 행·「공유」 수(RU-19)와 지난 자료 적재(RU-44)에 쓴다. 규칙: 「업무실적」 제목이 새 단위를 연다. 단위명은 그 앞의 마지막 글 문단(없으면 부서명). 표는 직전 제목의 자리로. 표 밖의 글은 세지 않고 경고한다 — 조용히 버리지 않는다 |
| RU-17 | 같은 입력이면 같은 파일 — 표 인스턴스 ID도 결정적으로 매긴다(같은 양식에서 온 겹치는 값만 새로). RU-02 「바뀜」을 내용(sha256)으로 판정하기 때문이다 |
| RU-18 | 둘째 섹션부터 **새 쪽**에서 시작한다(제목 문단 머리의 쪽 나누기). 본부 설정(`rollupPageBreak`)으로 끌 수 있다. 전사 최종본은 언제나 켠다(분석 §3.1) |
| RU-19 | 결과 화면 — 단위(섹션)마다 실적·계획·특이 행 수와 「공유」 수를 **보낸 사본에서** 센다(정규화가 넣은 「특이사항 없음」은 세지 않는다). 섹션 결과 중 경고·뺀 것·실패는 섹션 제목을 앞에 붙여 「확인해 주세요」(주황)에 보인다. **자동 수정(RU-63)은 화면에 보이지 않는다** — 엔진이 이미 고친 것이라 할 일이 없는데 주황 상자에 넣으면 본부장이 [승인] 앞에서 「무엇을 확인하라는 거지?」로 멈춘다(2026-10-08). 같은 날 처음에는 「자동으로 고친 것 n건」으로 접어 두었다가, 전사 카드의 「섹션별 처리」와 함께 걷었다(2026-10-08 사용자: 주석 걷기 — 「이게 뭐야」). 기록은 그대로 남는다(단위마다 `RolledUnit.fixed`). 사본 맨 위의 부서명 줄을 뺀 것은 알리지 않는다 — 생성한 제목으로 바꾼 것이라 매번 뜨면 소음이다. 사본 하나를 못 읽으면 그 자리에 실패를 적고 나머지는 만든다(HM-21) |

구현 (2026-10-07 중복 제거): 조립기는 `src/lib/hwp/orgdoc.ts`의 `composeOrgDocument` **하나**다(옵션 `pageBreak`, 기본 켬).
본부 실행은 `src/server/rollup/run.ts` `runHqRollup`, 섹션 제목은 `src/server/rollup/sections.ts` `sectionTitles` —
섹션 목록을 **만들지 않고 읽기만** 한다(본부 실행이 총괄의 설정 화면 상태를 바꾸면 안 된다). 목록이 아직 비어 있으면
기본 13개를 부서 이름으로 맞춘다 — 총괄이 처음 열 때 만들어질 제목과 같다. `src/lib/hwp/rollup.ts`에는 읽기
(`readUnits`·`titleBucket`)만 남았다. **한글로 열어 보는 확인은 RU-62와 함께 남아 있다.**

**뺀 것 (2026-10-07, 중복 제거)**: 처음 구현(`composeRollupHwp`·`verifyRollup`)은 양식의 「첫 문단(부서명) + 1·2·3 표」 꼴을
단위 수만큼 복제하고 실형 5열 표를 데이터로 **다시 그렸다.** 전사 취합이 RU-62 엔진으로 간 뒤 같은 일을 하는 엔진이
둘이 되었고, 본부 단계만 꼴이 달랐다 — 본부·센터형 6열·환경평가형 원본이 망가지고, 표 밖의 글이 빠지고, 정규화가
없었다. 본부장이 검토한 꼴과 최종본의 꼴이 갈라지는 구조라 지웠다. 테스트 RU-T10~19는 새 엔진으로 옮겼고,
RU-T14(본부본 → 전사에서 단위 펼치기)는 뺐다 — 전사는 본부본을 다시 읽지 않고 본부본에 든 실·팀 사본을 쓴다(§11a RU-60).

## 5. 데이터 모델

모두 **더하기만** 한다 — 운영 DB에 `prisma db push`해도 기존 값이 바뀌지 않는다.

```prisma
model Division {
  // … 기존 …
  rollupOrder     String  @default("[]")  // RU-20 — 기여 단위 id 순서 (JSON)
  rollupNote      String  @default("")    // RU-21
  rollupPageBreak Boolean @default(true)  // RU-18
  rollupSelf      Boolean @default(true)  // RU-08
}
model ReportSubmission { level "unit"|"hq", divisionId, weekSlotId, filePath(사본), sha256, sourceRunId, origin "app"|"import", submittedBy, submittedAt, withdrawnAt, withdrawnBy }
model RollupRun        { level "hq"|"org", divisionId?(org는 null), weekSlotId, status, outputPath, inputIds(JSON, 붙인 순서), unitsJson, warnings, errorText, createdBy }
model OrgRollupSetting { id "org", order(JSON), note, pageBreak }
```

- **상위 관계는 저장하지 않는다** — `parentKo` (§1.1)
- 본부·전사 결과를 `MergeRun`에 넣지 않는다 — 연구 본부처럼 같은 부서가 실·팀 병합과 본부 병합을 둘 다 가질 수 있다
- 「지금 제출된 것」 = (부서·주차·level)의 가장 최근 **취소되지 않은** 행

## 6. 권한 — [TACP-21](../../TACP.md)

- 실·팀 [제출]·취소: 그 부서의 lead·head
- 본부 이어 붙이기·순서·[총괄에 제출]: **본부 단계가 있는 본부**의 lead·head. 산하의 **보낸 사본**만 읽는다
- 전사 이어 붙이기·본부 순서: coordinator·operator
- 총괄이 올린 섹션 파일 내려받기: 전사 취합의 문(`canOpenOrgDesk`)과 같은 사람 — 판정·기록은 `findReadableSectionUpload` 하나(취소한 파일은 404, 받으면 `download` 기록)
- coordinator·operator는 남의 단위를 **대신 제출하지 않는다** — 빠진 곳은 「미제출」로 보인다

## 8. 단계 일정과 알림 (RU-50~58)

운영자 요청(2026-10-07): 「총괄은 이번 주처럼 휴일 때문에 하루 짧아질 때 이걸 지정할 수 있게, 알림도 그에 맞춰
당겨지게」. 그래서 **3단계의 모든 시각은 그 주의 부서 마감 하나에서 계산한다** — 총괄이 공지를 붙여넣어
마감을 옮기면(WS-19) 실·팀 → 본부 → 총괄의 기한과 알림이 **한꺼번에 같은 간격으로** 옮겨진다.

| ID | 요구 |
|---|---|
| RU-50 | **기준 시각 D** = 그 주 켜진 부서들의 부서 마감 중 가장 이른 것 (WS-18 예외 반영 — 「전사」 머리글 주차 줄의 부서 마감과 같은 계산) |
| RU-51 | **실·팀 → 본부 기한** = D + `unitDueMinutes`(기본 60 — 지금의 대외 마감 15:00) · **본부 → 총괄 기한** = D + `hqDueMinutes`(기본 120 — 16:00). 본부 단계가 없는 단위(RU-07)는 바로 총괄에 내므로 본부 → 총괄 기한을 따른다. 총괄이 「전사」 화면 [일정 바꾸기]로 연 칸의 마지막 줄 「3단계 취합 … [간격 바꾸기]」에서 바꾼다(간격 이름은 「+1시간」 꼴) — 부서 마감을 옮기는 자리와 같은 곳이다(§12 Q6 확정 전 기본값, WS-19l) |
| RU-52 | **3단계 사용 스위치**(`enabled`, 기본 꺼짐, 화면 낱말 「켜짐/꺼짐」) — 같은 줄에 있다. 꺼져 있으면 [제출] 카드·본부 취합 메뉴·「전사」 화면의 취합 부분(최종본 열·만들기·섹션 구성 편집)·아래 알림이 총괄에게 **하나도 나타나지 않는다**(「전사」 화면 자체는 제출 열만으로 선다 — PG-51d) — 운영에 먼저 올려 두고 시작하는 날 켠다. 꺼져 있는 동안 스위치는 운영자에게만 보인다(`canOpenOrgDesk`). 끄기는 그 자리에서 한 번 더 묻는다(「끄면 단계 제출·최종본 열이 사라집니다 [끄기] [아니오]」) — 끈 총괄은 다시 켤 수 없다 |

| RU-54 | 실·팀 → 본부 기한에 **본부 담당자**에게: 「산하 n/m 제출 · 미제출 ○○ — 이어 붙여 본부장 검토를 받아 주세요」 |
| RU-55 | **본부장 승인** — 본부 화면의 [검토 완료 · 승인](head만, HM-47과 같은 규칙). 누르는 순간 본부 담당자에게 「본부장 승인 완료」. 승인 뒤 다시 이어 붙이면 「승인 뒤 바뀜」 |
| RU-56 | 본부 → 총괄 기한 15분 전, 아직 [총괄에 제출] 안 한 본부 담당자에게 「15분 남았어요」 |

| RU-58 | 「전사」 머리글의 다가올 주차 줄(WS-19l)에 실·팀·본부 제출 기한이 부서 마감과 **같은 줄에** 보이고, 마감 바꾸기 미리보기도 **같은 꼴 한 줄**(새 부서 마감에서 센 두 기한 — `planDeadline().stages`)로 보인다 — 옮기기 전에 무엇이 언제로 가는지 안다. 알림 시각 표는 화면에 그리지 않는다(2026-10-08) — 이미 지나 안 나가는 알림은 미리보기 경고가 말하고, 시각 목록은 응답(`plan.schedule`)에 남는다 |
| RU-59 | **두 기한의 이름은 어디서나 한 쌍이다 — 「실·팀 → 본부」·「본부 → 총괄」**(받는 쪽을 화살표로). 「전사」 머리글 주차 줄과 3단계 줄, `/hq` 머리, 마감 바꾸기 미리보기, 알림 문구가 모두 이 말을 쓴다(`src/lib/rollup-stages.ts`). 같은 16:00이 화면마다 「본부 기한」·「본부 제출」·「총괄 기한」으로 불려 서로 다른 시각처럼 들렸다(2026-10-08) |

알림은 모두 한 주차·한 종류에 한 번(NT-42), 지난 알림은 소급하지 않는다(NT-43), 본인 알림 설정(NT-20)·사번(NT-01)을 따른다.

기획경영본부는 `rollupSelf=false`(Q3 기본 가정). 본부 단계 시험용 계정은 테스트 DB에만 있다
(`docs/private/test-accounts.md`). 운영 DB에는 아무것도 바뀌지 않았다.

| ID | 요구 |
|---|---|
| RU-60 | **전사 섹션 목록**(13개, 순서 고정, 설정 가능) — 섹션마다 출처: Tincase 부서(실·팀 제출 또는 본부 제출) / **총괄이 올린 파일**(게시판으로 받은 곳) / 미제출. 기본 순서는 9월 4주차 실제 순서. **한 부서는 한 섹션에만** — 켜진 섹션 둘이 같은 부서를 가리키면 저장을 받지 않는다(422, 어느 부서·어느 섹션인지 말한다) — 받으면 같은 사본이 최종본에 두 번 들어간다. 꺼진 섹션은 세지 않는다 |
| RU-60a | **게시판 hwp [올리기]는 hwp 스위치(WA-30)를 따른다** (2026-10-08 — 사용자: 「전사에서 [올리기]를 누르면 파일 업로드가 나오는데 이거 왜 필요하지? 전부 웹에서 진행되는데」). [올리기]는 부서원 제출 길이 아니다 — Tincase를 쓰지 않는 섹션(「Tincase 밖」)의 hwp를 총괄이 취합게시판으로 받아 전사본 자리에 넣는 길이다. 그래도 웹만 받는 서버(`SUBMIT_HWP_UPLOAD=off` — 테스트·시연 서버)에서는 그리지 않는다: 페이지가 `hwpUploadOpen()`(submit-mode 하나에서 읽는다, WA-T33)으로 `canUpload = 취합의 문 && 스위치`를 정해 넘기고, `POST /api/rollup/org/sections/upload`는 `requireOrgRollup`(밖이면 404) **다음**, 파일을 읽기 **전에** `assertHwpUploadOpen()` — 닫혀 있으면 410 `upload_closed`. [받기]와 [올린 것 취소](`DELETE`)·받기(`[id]` GET)는 스위치와 상관없다 — 이미 올라온 것을 꺼내고 치우는 일이다. **그 결과** 스위치가 꺼진 서버에서 Tincase 밖 섹션은 전사본에 늘 「미제출」로 들어간다. 운영(기본 `on`)은 그대로다. **결정 필요**: ADR-0014는 부서원 제출을 닫는 스위치다 — 운영에서 끄는 날 총괄은 Tincase 밖 섹션을 넣을 길을 잃는다. 그 단계 전에 이 길을 따로 둘지 정한다 (§12 Q8) |

### RU-63 정규화 규칙 (2026-10-07 실제 최종본 검증 반영)

9월 4주차 **실제 최종 취합본**을 섹션별로 쪼개 엔진에 다시 넣어 봤다(원본은 로컬에만 — 실명·업무 내용 포함).
구조 검사는 모두 통과했지만 정규화가 **멀쩡한 데이터를 바꾼** 곳이 있었다 — 칸 수로 행 종류를 가르고, 열 수만으로
표 종류를 가른 탓이다. 그래서 판정을 **머리행 글자와 번호 칸**으로 한다. 원칙: **알아보지 못한 표·행은 건드리지 않는다**
(고칠 기회를 놓치는 것은 경고로 남지만, 잘못 고친 것은 아무도 모른 채 최종본에 들어간다).

| 규칙 | 내용 | 실측 사례 (구조만) |
|---|---|---|
| R1 업무 표(실형 5열) | **5열 + 머리행 1열 「구분」 + 3열이 일자 칸(「일자」·「업무 기간」)**. 이 표만 빈 줄 삭제·번호 다시 매김·「특이사항 없음」·일자 경고를 한다 | — |
| R2 집계표는 업무 표가 아니다 | 본부·센터의 「※ 자문회의 실적」 표(`구분 \| 자문회의 \| 전문가 세미나 \| …`)도 5열·「구분」으로 시작한다. 실마다 「-」뿐인 줄이 **정상**이다 — 지우면 그 실이 표에서 사라진다. 손대지 않고 일자 경고도 내지 않는다 | 「-」 줄이 지워지고 「1건」이 일자 경고로 뜸 |
| R3 본부형 과제 표 | **6열 이상 + 머리행 「구분 \| 유형」**. 7열은 일자 칸이 두 칸 병합된 변형이다 — 같은 규칙으로 고친다 | 7열 표가 정규화되지 않음 |
| R4 항목 행 = 번호 칸으로 | 2열(번호 칸)이 `n-n`이면 **항목 행**, 유형 단어(기본·수탁·일반…)면 **과제 행**(손대지 않는다). 번호 칸이 비었으면 과제명 칸이 책임자 칸 바로 앞까지 병합되지 않은(= 항목 꼴) 줄만 항목 행으로 본다. **칸 수로 가르지 않는다** — 1열 「구분」(실 이름)이 여러 줄 병합되면 그 아래 항목 행은 5칸·3칸이 된다. 번호는 표 전체 연속(Q7) | 병합 아래 항목 행을 건너뛰어 올바른 `1-1…1-5`가 중복 번호로 바뀜 |
| R5 머리행 이름 | 「업무 기간」→「일자」, 「업무 담당 또는 참석자」·「업무 담당 또는 참석 인원」→「참석자」 (빈칸·한 문단 안 줄바꿈은 무시하고 비교). **글자 든 문단이 둘 이상인 칸(Enter로 나눈 것)은 건드리지 않는다** — 칸 글자 바꾸기는 첫 문단만 바꿔 「참석자⏎참석 인원」이 된다 | 「참석 인원」 꼴이 통일되지 않음 |
| R6 일자 표기 경고 | 일자 뒤의 **시각**(`10/1 14:00`, `14:00~16:00`)은 떼고 본다 — 시각을 적는 것은 정상이다 | `10/1 14:00`이 경고로 뜸 |
| R7 뺀 것 기록 | 본문 앞의 빨간 `※ … 작성 必`도 「제목」이 아니라 **「안내문」**으로 적는다 — 총괄이 「무엇을 뺐나」를 보고 판단한다 | 안내문이 「제목 …」으로 기록됨 |

테스트: `tests/normalize.test.ts` RU-T60~68(RU-T61b·67b 포함) — 실제 파일 없이 **합성한 표**로 R1~R6을 하나씩 본다(CI에서도 돈다).
R7은 `tests/docmerge.test.ts` RU-T69(양식 픽스처가 있을 때만).
