# v2 알림 — 운영에서 나갈 수 있는 쪽지 전부

> 대상: 문구와 받는 사람을 **실제 사람이 받기 전에** 검토할 사람(운영자).
> 기준: `feat/org-rollup` (2026-10-09) 코드에서 옮겨 적었다 — 정본은 코드다: `src/server/notify/**` · `src/server/rollup/notices.ts` ·
> `src/server/merge/review.ts` · `src/app/api/forgot` · `src/app/api/ops/setup-link`. 설계는 [messenger.md](integrations/messenger.md) §4~4-3 · [12 §8](spec/12-org-rollup.md).
> ⚠ **운영 메신저는 켜져 있다.** 아래 쪽지는 실제 사람 화면에 팝업으로 뜨고, 한 번 나가면 되돌릴 수 없다.
> 함께: [LAUNCH-v2.md](LAUNCH-v2.md)(월요일 순서) · [ANNOUNCE-v2.md](ANNOUNCE-v2.md)(부서 안내문)

## 1. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 보내는 이 | 시스템 이름 `Tincase`, 보낸 이 `업무일지 수합` (`MESSENGER_SYSTEM_NAME`·`MESSENGER_SENDER_NAME` 기본값) |
| 링크 | `URL` 필드 하나 — 알림·제목을 누르면 열린다. `{링크}` = `MESSENGER_LINK_BASE` + 경로. **본문은 평문이고 본문의 주소는 눌리지 않는다**(messenger.md §7) |
| 한 사람에 한 통 | 이름이 들어가므로 여럿을 한 쪽지에 묶지 않는다. 첫 줄은 `[{사번}]{이름}님` (설정 링크·비밀번호 찾기만 `{이름}님,`) |
| 받는 조건 (모두) | `MESSENGER_URL` 있음 · 사번이 `MESSENGER_ALLOWLIST`에 있음(`*`면 전원) · 계정 활성 · 본인 알림 켜짐(`User.notifyEnabled` — 운영자 인원 드로어, NT-22) · 사번 있음 · **그리고 종류별 스위치**(아래 표의 「스위치」) |
| 한 번만 | `NotifyLog`의 (부서, 주차, 종류) 유일 키. 여러 번 생길 수 있는 알림은 종류 뒤에 승인 id·사람 id·시각을 붙인다. 아무에게도 안 나갔으면 기록하지 않는다(다음 판정이 다시 보낸다) |
| 지난 창은 소급하지 않는다 | 시각 알림은 그 시각부터 **12분**(10분 전 알림만 **3분**) 안에서만. 그때 컨테이너가 꺼져 있었으면 그 통은 가지 않는다 |
| 표기 | `{주차}` = WeekSlot 이름(「○월 ○주차」) · `{주간}` = 「주간」, 그 달 마지막 주는 「월간」 · `{마감}` = 「10월 15일(목) 14:00」 꼴 · `{HH:MM}` = 시각 · `{기한}` = 마감과 같은 날이면 「15:00」, 아니면 날짜까지 · **D** = 그 주 켜진 부서 마감 중 가장 이른 것 |

**스위치** — 어떤 알림이 무엇을 따르나:

| 스위치 | 어디서 | 멈추는 것 |
|---|---|---|
| 부서 알림 `Division.notifyEnabled` | SQL만 (화면 없음) | 그 부서 부서원·담당자·부서장에게 가는 것 전부: 마감 전 · 병합 뒤 · 승인 · 다시 승인 · 실·팀 기한 15분 전 |
| 3단계 `OrgRollupSetting.enabled` | 「전사」 [일정 바꾸기] → 「3단계 취합」 | `ru_*` 전부 · `merge_reapprove` · 3단계용 문구(꺼지면 v1.39 문구로) |
| 병합 일시정지 `MERGE_PAUSE_UNTIL` | compose (OPS-16a) | 병합 · 병합 뒤 안내 · 「병합 점검」. 마감 전 알림·3단계 알림은 계속 간다 |
| `MERGE_SCHEDULER=off` | compose — **운영에는 두지 않는다** | 시각 알림 전부(사건 알림은 남는다) |
| `MESSENGER_URL` 비우기 | `.env.production` → 재기동 | 전부 (설정 링크·비밀번호 찾기 포함) |

## 2. 한 주에 누가 무엇을 받나 (기본: 목 14:00 마감 · 3단계 켬 · 기한 +60/+120분)

| 시각 | 종류 | 받는 사람 | v1.39 대비 |
|---|---|---|---|
| 수 11:45 | `deadline_1d` 마감이 내일 | 알림 켠 부서의 미제출 부서원 | 그대로 |
| ~~목 09:00~~ | ~~`deadline_day`~~ | — | **없어짐**(R13) |
| 목 13:00 | `deadline_1h` 1시간 전 | 〃 | 그대로 |
| 목 13:50 | `deadline_10m` 10분 전 | 〃 | 그대로 |
| 목 14:01 | (자동 병합 — 쪽지 없음) | — | 줄로 바뀜(HM-59) |
| 줄이 빈 순간, 늦어도 14:15 | `merge_batch` 병합 점검 | 운영자 · 기획조정실 담당 | **새로** |
| 14:10~ (병합이 늦으면 끝난 때부터) | `merge_review` 검토 부탁 / `merge_missing` 병합본 없음 | 부서장 / 담당자 | 바뀜(링크·조건) |
| 부서장이 승인한 순간 | `merge_approved` 승인 완료 | 담당자 | 바뀜(3단계 끝 줄) |
| 승인 뒤 판이 바뀐 순간 | `merge_reapprove` 다시 승인 | 부서장 | **새로**(3단계) |
| 14:30~ | `merge_done` 최종 안내 (할 일이 있을 때만) | 담당자 | 바뀜(3단계 문구 셋) |
| 14:45 | `ru_unit_due_soon` 「실·팀 → 본부」 15분 전 | 본부로 가는 실의 부서장(승인 전일 때) | **새로** |
| 산하가 다 모인 순간, 아니면 15:00 | `ru_hq_ready` (+ `ru_hq_complete`) 본부본 준비 | 본부장 | **새로** |
| 본부 승인 뒤 본부본이 바뀐 순간 | `ru_hq_reapprove` | 본부장 | **새로** |
| 15:45 | `ru_hq_due_soon` 「본부 → 총괄」 15분 전 | 본부장(승인 전일 때) | **새로** |
| 15:45 | `ru_unit_due_soon` 「본부 → 총괄」 15분 전 | 바로 총괄로 가는 부서의 부서장(승인 전일 때) | **새로** |
| 모든 섹션이 들어온 순간, 아니면 16:00 | `ru_org_ready` (+ `ru_org_complete`) 전사본 준비 | 총괄 각자 | **새로** |
| 받은 전사본이 바뀐 순간 | `ru_org_changed` | 그 전사본을 받은 총괄 | **새로** |
| 본부본·전사본 만들기 실패 | `ru_hq_failed` / `ru_org_failed` | 본부 담당자 / 총괄 | **새로** |
| 마감 열기가 닫혔는데 고친 병합본이 있을 때 | `merge_held` | 담당자 | 그대로 |
| 운영자가 보낼 때 / 본인이 요청할 때 | `setup_link` / `forgot` | 그 사람 | 그대로 |

2026-10-12 주(W42)에 켜질 받는 곳: 「본부로 가는 실」 = 기획경영본부 산하(기획조정실·연구관리실·AI홍보전략실·인사관리실·경영지원실),
「본부장」 = 기획경영본부 본부장, 그 밖의 부서는 바로 총괄로 간다.

## 3. 종류별 — 언제 · 누구에게 · 문구

문구는 코드 그대로다. `{…}`가 자리표시자, `←` 뒤는 설명(쪽지에는 없다). 빈 줄은 쪽지의 빈 줄이다.

### 3.1 마감 전 — 미제출자 (NT-10 · 41 · 42)

| | |
|---|---|
| 받는 사람 | `isActive`·`notifyEnabled`인 부서의 **명단 안(onRoster) 미제출자** — 부서장·휴직자는 명단 밖이라 받지 않는다(DM-16) |
| 스위치 | 부서 알림 |
| 한 번 | (부서, 주차, 종류) — 그 부서에 한 번 돌면 끝 |
| 링크 | `{링크}/{부서-slug}` (홈) |

**`deadline_1d`** — 마감 전날 11:45 (달력으로 하루 앞, 창 12분)

```
제목: [Tincase] {주차} {주간} 업무일지 마감이 내일이에요

[{사번}]{이름}님 업무일지 마감이 내일이에요.

{마감}까지 Tincase에서 제출해주세요.
이번 주는 한 달치를 정리하는 월간이에요.        ← 월간 주에만

미리 알려드려요. 마감 1시간 전에 한 번 더 알려드릴게요.
```

**`deadline_1h`** — 마감 60분 전 (창 12분)

```
제목: [Tincase] {주차} {주간} 업무일지 마감 1시간 전이에요

[{사번}]{이름}님 아직 업무일지가 제출되지 않았어요.
Tincase에서 {마감} 전에 제출해주세요.
이번 주는 한 달치를 정리하는 월간이에요.        ← 월간 주에만
```

**`deadline_10m`** — 마감 10분 전 (창 **3분** — 마감을 넘겨 나가지 않게)

```
제목: [Tincase] {주차} 업무일지 마감 10분 전입니다

[{사번}]{이름}님 10분 뒤 마감입니다.

아직 제출되지 않았어요. 지금 Tincase에서 제출해주세요.

마감 뒤에는 부서 담당자에게 말씀하셔야 낼 수 있습니다.
```

### 3.2 마감 뒤 — 부서장 · 담당자 (NT-40 · 47 · 47′ · 51)

| | |
|---|---|
| 스위치 | 부서 알림 · 병합 일시정지 |
| 한 번 | (부서, 주차, 종류). `merge_held`만 닫힘마다(`merge_held:<닫힌 시각 ms>`) |
| 링크 | 모두 `{링크}/{부서-slug}/manage` (수합 관리 — v1.39의 `merge_review`는 `/archive`였다. 옛 주소는 2026-12-31까지 수합 관리로 보낸다) |
| 창 | `max(마감 + n분, 마지막 병합이 끝난 시각)`부터 12분. **마감 +60분이 지나 끝난 병합에는 보내지 않는다**(HM-50). 줄에 서 있거나 병합 중이면 기다린다 |

**`merge_review`** → 부서장 — +10분, 최종본(마감 뒤 시작한 성공 병합)이 있고 그 판에 유효한 승인이 없을 때.
가장 최근 승인에 대해 `merge_reapprove`를 이미 보냈으면 건너뛴다(같은 할 일을 두 번 보내지 않는다).

```
제목: [Tincase] {주차} {주간} 병합본 검토 부탁드려요

[{사번}]{이름}님 {주차} {주간} 업무일지 병합본이 준비됐어요.

제출 {n}건 → 실적 {a} · 계획 {b} · 특이 {c}        ← 특이 0이면 「· 특이」 없음

병합한 뒤에 {k}명이 더 냈어요 — 이 병합본에는 빠져 있어요.   ← 늦게 낸 사람이 있을 때만
담당자에게 다시 병합을 요청해주세요.                          ←  〃

확인이 필요한 내용이 {m}건 있어요.                            ← 「없음」 같은 줄이 있을 때만
· {실적|계획|특이사항} {번호} {작성자} 「{내용}」             ← 3줄까지, 넘으면 「· 외 {x}건」

Tincase에서 내용을 확인하고 고칠 부분을 알려주세요.
각 항목을 누가 냈는지도 함께 보입니다.
```

**`merge_missing`** → 담당자 — +10분, 최종본이 없고 줄에도 없을 때(아무도 안 냈거나 실패).

```
제목: [Tincase] {주차} 병합본이 아직 없어요

[{사번}]{이름}님 {주차} 병합본이 만들어지지 않았어요.

제출된 파일이 없거나 병합에 실패했을 수 있어요.
Tincase 수합 관리에서 확인하고 [지금 병합]을 눌러주세요.
```

**`merge_done`** → 담당자 — +30분. 문구가 넷이다:

① 병합본이 없을 때 (3단계와 상관없이)

```
제목: [Tincase] {주차} 병합본을 확인해주세요

[{사번}]{이름}님 {주차} 병합본이 아직 없어요.

대외업무 마감이 얼마 남지 않았어요.
Tincase 수합 관리에서 [지금 병합]을 눌러주세요.
```

② 3단계 꺼짐 (또는 이 부서가 3단계 기여 단위가 아님) — **v1.39 그대로**

```
제목: [Tincase] {주차} {주간} 병합본 제출해주세요

[{사번}]{이름}님 {주차} {주간} 병합본이 준비됐어요.

제출 {n}건 → 실적 {a} · 계획 {b} · 특이 {c}

{승인자 이름 직책}님 승인 완료 ({HH:MM} · {바뀐 곳 요약})     ← 승인했을 때
{승인자 이름 직책}님이 승인한 뒤 병합본이 바뀌었어요 — 다시 확인을 받아주세요.   ← 승인 뒤 바뀜
아직 부서장 승인 전이에요 — 확인한 뒤 제출해주세요.           ← 부서장이 있는데 승인 전 (부서장 없는 부서는 이 줄 없음)

병합한 뒤에 {k}명이 더 냈어요 — 이 병합본에는 빠져 있어요.   ← 있을 때만
Tincase 수합 관리에서 [다시 병합]을 눌러주세요.

확인이 필요한 내용이 {m}건 있어요.                            ← 있을 때만
· …

Tincase에서 hwp로 받아 취합게시판에 올리고
웹디스크에 업로드해주세요.
```

③ 3단계 켬 · 부서장 있음 — **승인돼 이미 올라갔으면 보내지 않는다**(승인 순간 `merge_approved`가 말했다)

```
제목: [Tincase] {주차} {주간} 병합본 — 부서장 승인을 기다려요

[{사번}]{이름}님 {주차} {주간} 병합본이 준비됐어요.

제출 {n}건 → 실적 {a} · 계획 {b} · 특이 {c}
(늦게 낸 사람 · 확인할 내용 줄 — ②와 같다)

아직 부서장 승인 전이에요 — 승인되면 저절로 {받는 곳}에 올라갑니다(기한 {기한}).
  또는
부서장이 승인한 뒤 병합본이 바뀌었어요 — 다시 승인되면 저절로 {받는 곳}에 올라갑니다(기한 {기한}).
```

④ 3단계 켬 · 부서장 없음 (마감 뒤 병합본이 저절로 올라간다 — RU-71)

```
제목: [Tincase] {주차} {주간} 병합본이 {받는 곳}에 올라갔어요

[{사번}]{이름}님 {주차} {주간} 병합본이 준비됐어요.

제출 {n}건 → 실적 {a} · 계획 {b} · 특이 {c}
(늦게 낸 사람 · 확인할 내용 줄 — ②와 같다)

병합본이 {받는 곳}에 올라갔어요 — 고칠 곳은 고쳐 저장하면 다시 올라갑니다.
```

`{받는 곳}` = 「기획경영본부」(산하 실) 또는 「총괄」 · `{기한}` = 본부로 가면 D+60(15:00), 총괄로 가면 D+120(16:00).

**`merge_held:<닫힌 시각>`** → 담당자 — 담당자가 연 「마감 열기」가 닫혀 자동 재병합 차례인데, 최종본에 사람이 고친 곳이 있고 늦게 낸 사람이 있을 때. 닫힘마다 한 번. v1.39 그대로.

```
제목: [Tincase] {주차} {주간} 병합본에 늦게 낸 {k}명이 빠져 있어요

[{사번}]{이름}님 마감 열기가 끝났어요. 병합본을 만든 뒤에 {k}명이 더 냈는데 지금 병합본에는 빠져 있어요.
{고친 사람 이름, …}님이 병합본을 {p}곳 고쳐서 자동으로 다시 병합하지 않았어요.      ← 이름을 모르면 「누군가」

넣으려면 Tincase 수합 관리에서 [다시 병합]을 눌러주세요.
다시 병합하면 고친 내용은 사라져요.
```

### 3.3 승인 — 담당자 · 부서장 (NT-46 · 46′ · 52)

**`merge_approved:<승인 id>`** → 그 부서 담당자 전원 — 부서장이 [고칠 것 없음 · 승인]을 누르거나 고쳐 저장한 순간. 승인마다 한 번(같은 판을 두 번 승인하지는 못한다).
스위치: 부서 알림. 링크 `/{부서-slug}/manage`.

```
제목: [Tincase] {주차} {주간} 병합본 — {승인자 이름 직책}님 승인 완료

[{사번}]{이름}님 {승인자 이름 직책}님이 {HH:MM}에 {주차} {주간} 병합본 검토를 마쳤어요 — 승인 완료.

바뀐 곳: {표별 요약 — 「실적 2줄 고침 · 계획 1줄 뺌」 꼴}       ← 고친 게 없으면 「고친 곳 없이 승인했어요.」
· {실적|계획|특이사항} 「{전}」 → 「{후}」                        ← 4줄까지, 넘으면 「· 외 {x}곳」

Tincase에서 받아 취합게시판에 올려주세요.        ← 3단계 꺼짐 (v1.39 그대로)
{받는 곳}에 자동으로 올라갔어요.                  ← 3단계 켬 (새 끝 줄)
```

`{승인자 이름 직책}` = ERP 직책(DM-19), 없으면 「부서장」.

**`merge_reapprove:<승인 id>`** → 그 부서 부서장 — **새로 · 3단계에서만.** 승인한 뒤 판(sha)이 바뀐 순간(담당자가 고쳐 저장 · 다시 병합).
승인마다 한 번 — 그 사이 여러 번 바뀌어도 할 일은 「다시 승인」 하나다. 스위치: 부서 알림 + 3단계. 보내기 전에 기록을 잡는다.

```
제목: [Tincase] {주차} {주간} 병합본 — 다시 승인해 주세요

[{사번}]{이름}님 담당자가 승인 뒤 병합본을 {p}곳 고쳤어요.
  또는
[{사번}]{이름}님 승인 뒤 병합본이 다시 병합됐어요(늦게 낸 {k}명 포함).        ← k=0이면 괄호 없음
{받는 곳}에는 승인한 판이 그대로 있어요.

Tincase 수합 관리에서 확인하고 다시 승인하면 바로 {받는 곳}에 올라갑니다.
```

### 3.4 병합 점검 — 운영자 · 기획조정실 담당 (HM-54 · NT-60 · TACP-30) — **새로**

| | |
|---|---|
| 받는 사람 | 운영자(`isOperator`) + **총괄이 있는 부서의 담당자(lead) 전원** — 지금은 기획조정실 담당 |
| 언제 | 같은 마감을 쓰는 부서 묶음마다: **줄이 빈 순간, 늦어도 마감 +15분**에 첫 통(마감 +60분이 지나면 첫 통을 보내지 않는다). 그때 남은 곳이 있었으면 다 끝나는 순간 「완료」 한 통(마감 +24시간까지) |
| 스위치 | 병합 일시정지만. **부서 알림 스위치를 보지 않는다** — 켜진 부서 전부를 센다(알림 끈 기획경영본부도 「제출 없음」으로 들어간다) |
| 한 번 | 사람마다 · 마감 시각마다 첫 통 1 + 완료 1 (`merge_batch:<마감 ms>:<사람 id>` · `merge_batch_done:…`). 보내기 전에 기록을 잡는다 |
| 링크 | 운영자만 `{링크}/ops`(「병합 줄」 카드). 기획조정실 담당은 그 화면을 못 열어 링크 없음 |
| 담는 것 | 부서 이름과 상태뿐 — **사람 이름·문서 내용은 없다** |

```
제목: [Tincase] 병합 점검 {HH:MM} · {끝}/{전체} 끝 · {남은}곳 남음        ← 남은 곳이 없으면 「· n곳 남음」 없음
제목: [Tincase] 병합 점검 완료 {HH:MM} · {끝}/{전체} 끝                     ← 「완료」 통

[{사번}]{이름}님 {주차} {주간} 마감 병합 점검 ({HH:MM})

{끝}/{전체} 끝 · 모델 사용 {u} · 모델 못 씀 {f} · 실패 {x} · 보류 {h} · 대기 {w} · 제출 없음 {n}   ← 제출 없음 0이면 그 칸 없음
마지막 끝 {HH:MM:SS}             ← 끝난 부서가 있으면
예상 끝 {HH:MM}                  ← 남은 부서가 있으면

· {부서} — {문제}                 ← 문제 있는 부서만, 12줄까지, 넘으면 「· 외 {x}건」
```

`{문제}`의 꼴: `병합 중` · `대기 {n}번째` · `{표} 중복 묶기 못 함({시간 초과|연결 실패|모델 서버 오류|시간 예산 초과|모델 답 오류})` · `분류 못 함(…)` ·
`파일이 기록과 다름` · `파일 없음` · `늦게 낸 {n}명 빠짐` · `마감 열림(~{HH:MM})` · `보류 — 병합하는 동안 고친 판을 덮지 않음` · `보류 — 사람이 고친 병합본` ·
`실패 — 다음 재시도 {HH:MM} ({오류})` · `아직 시작 안 함` · `확인 못 함`.

### 3.5 3단계 — 본부장 · 실·팀장 · 총괄 (RU-53~57b · ADR-0015) — **모두 새로**

공통: 스위치는 **3단계**. 실·팀장에게 가는 `ru_unit_due_soon`만 부서 알림도 따른다. 본부·총괄 사람에게 가는 것은 **부서 알림 스위치를 보지 않는다**
(기획경영본부의 부서 알림을 꺼도 본부장은 받는다). 「막고 있는 사람에게만」 — 넘길 일이 없는 사람(본부 담당자 등)에게는 가지 않는다.
모두 보내기 전에 기록을 잡는다(사건과 시각이 같은 순간에 판정해도 한 번).

**`ru_unit_due_soon`** → 실·팀장 — 그 단위 기한 15분 전(본부로: D+45 = 14:45 · 총괄로: D+105 = 15:45), 마감 뒤 병합본이 있는데 승인 전·승인 뒤 바뀜일 때. 부서·주차에 한 번. 링크 `/{부서-slug}/manage`.
같은 시각부터 담당자의 비상구 「승인 없이 올리기」가 열린다(RU-77).

```
제목: [Tincase] {주차} 「실·팀 → 본부」 기한 15분 전이에요        ← 바로 총괄로 가는 부서는 「본부 → 총괄」

[{사번}]{이름}님 {HH:MM}까지 병합본 승인이 필요해요 — 15분 남았어요.

Tincase 수합 관리에서 병합본을 승인하면 바로 {받는 곳}에 올라갑니다.
```

**`ru_hq_ready` · `ru_hq_complete`** → 본부장 — 산하가 **다 모여** 본부본이 만들어진 순간(승인 전일 때), 아니면 「실·팀 → 본부」 기한(D+60 = 15:00)에 하나라도 와 있고 승인을 기다리면 그때 — **둘 중 먼저 한 번.**
기한에 일부로 보냈는데 뒤에 다 모이면(아직 승인 전) `ru_hq_complete` 한 번. 본부·주차에 한 번씩. 링크 `{링크}/hq`.

```
제목: [Tincase] {본부} 본부본이 준비됐어요 — 산하 {a}/{n}곳

[{사번}]{이름}님 {주차} {주간} 산하 {a}/{n}곳이 올라와 본부본이 준비됐어요.
아직 {m}곳: {실·실}                ← 일부일 때만

Tincase 본부 취합에서 검토하고 [검토 완료 · 승인]을 누르면 바로 총괄로 갑니다.
```

```
제목: [Tincase] {본부} 산하 {n}곳이 다 모였어요 — 본부본 검토

[{사번}]{이름}님 {주차} {주간} 산하 {n}곳이 다 올라와 본부본을 다시 이어 붙였어요.

Tincase 본부 취합에서 검토하고 [검토 완료 · 승인]을 누르면 바로 총괄로 갑니다.
```

**`ru_hq_reapprove:<승인 id>`** → 본부장 — 본부장이 승인한 뒤 본부본이 다시 만들어져 **판(sha)이 바뀐** 순간. 풀린 승인마다 한 번. 같은 바이트로 다시 만들어지면 보내지 않는다. 링크 `/hq`.

```
제목: [Tincase] {본부} 본부본이 바뀌었어요 — 다시 승인해 주세요

[{사번}]{이름}님 {주차} {주간} {이유} 승인한 뒤 본부본이 다시 이어 붙었어요.      ← 이유를 모르면 그 칸 없음
총괄에는 {HH:MM}에 승인한 판이 있어요.

Tincase 본부 취합에서 확인하고 다시 [검토 완료 · 승인]을 눌러 주세요.
```

`{이유}` = 「{부서} 승인으로」 · 「{부서} 승인 없이 올려서」 · 「{부서} 병합본이 올라와서」 · 「순서를 바꿔서」 · 「양식이 바뀌어서」 · 「조직이 바뀌어서」 · 「섹션 구성이 바뀌어서」 · 「섹션 파일이 바뀌어서」 · 「다시 시도해서」 · 「3단계를 켜서」.

**`ru_hq_due_soon`** → 본부장 — 「본부 → 총괄」 기한 15분 전(D+105 = 15:45), 본부본이 승인 전·승인 뒤 바뀜일 때. 본부·주차에 한 번. 링크 `/hq`.

```
제목: [Tincase] {주차} 「본부 → 총괄」 기한 15분 전이에요

[{사번}]{이름}님 {HH:MM}까지 본부본 승인이 필요해요 — 15분 남았어요.

Tincase 본부 취합에서 검토하고 승인하면 바로 총괄로 갑니다.
```

**`ru_org_ready:<사람>` · `ru_org_complete:<사람>`** → 총괄(`isCoordinator`) **각자** — 켜진 섹션이 **모두** 들어와 전사본이 만들어진 순간, 아니면 「본부 → 총괄」 기한(D+120 = 16:00) — 둘 중 먼저 한 번.
기한에 일부로 보냈는데 뒤에 다 들어오면 `ru_org_complete` 한 번. 총괄·주차에 한 번씩. 링크 `{링크}/org`.

```
제목: [Tincase] {주차} {a}/{n}곳 도착 — 전사본이 준비돼 있어요

[{사번}]{이름}님 {주차} 전사본이 준비돼 있어요.

도착 {a}곳: {이름·이름·…}
아직 {m}곳: {이름·…}               ← 일부일 때만

Tincase 「전사」에서 전사본을 받으세요.
```

```
제목: [Tincase] {주차} {n}곳이 다 들어왔어요 — 전사본

[{사번}]{이름}님 {주차} {n}곳이 다 들어와 전사본을 다시 만들었어요.

도착 {n}곳: {이름·이름·…}

Tincase 「전사」에서 전사본을 받으세요.
```

**`ru_org_changed:<받은 실행 id>:<사람>`** → 그 전사본을 **받은** 총괄만 — 받은 뒤 전사본이 다시 만들어져 바이트가 다를 때. 받은 판마다 한 번. 링크 `/org`.

```
제목: [Tincase] {주차} 받은 전사본이 바뀌었어요

[{사번}]{이름}님 {HH:MM}에 받은 전사본이 바뀌었어요({이유}).        ← 이유를 모르면 괄호 없음

이미 올렸다면 Tincase 「전사」에서 다시 받아 바꿔 주세요.
```

**`ru_hq_failed:<열쇠>` · `ru_org_failed:<열쇠>`** → 본부본은 **본부 담당자**, 전사본은 **총괄** — 자동 조립이 실패한 순간. 실패한 입력(열쇠)마다 한 번. 본부장에게는 보내지 않는다(고칠 수 없다). 링크 `/hq` · `/org`.

```
제목: [Tincase] {주차} {본부} 본부본을 만들지 못했어요        ← 전사본이면 「전사본을 만들지 못했어요」

[{사번}]{이름}님 {주차} {본부} 본부본을 자동으로 만들지 못했어요.

이유: {오류 문구}

고친 뒤 Tincase에서 [다시 시도]를 눌러 주세요.
```

### 3.6 계정 (AU-30 · AU-32) — 그대로

| 가지 않게 된 것 (설계 단계에만 있던 것) | 본부 담당자 「이어 붙이세요」(`ru_hq_collect`) · 「승인 완료 — [총괄에 제출]」(`hq_approved`) · 본부 담당자의 15분 전 — 넘길 일이 없어졌다(ADR-0015) |
| 그대로 | `deadline_1d`·`deadline_1h`·`deadline_10m`·`merge_missing`(문구)·`merge_held`·`setup_link`·`forgot` |

진짜 메신저가 받는 요청은 v1.39와 같다(폼 16개 필드). 종류 머리 `x-tincase-kind`는 가짜 알림 수신함으로 갈 때만 붙는다 — 운영에서는 붙지 않는다.

## 5. 검토할 점 — 실제 사람이 받기 전에

코드는 고치지 않았다(문서만). 고칠지 고르면 대부분 문구 한두 줄이다.

1. **설정 링크의 주소가 눌리지 않을 수 있다** (`setup_link`·`forgot`). 주소가 본문에만 있고 `URL` 필드가 없다 — messenger.md §7의 실측은
   「본문의 주소는 클릭되지 않는다」였다. 월요일에 처음 쓰는 사람 거의 전부(~100명)가 이 쪽지로 들어온다. **월요일에 자신에게 먼저 한 통 보내 본다**(LAUNCH-v2 ⑪).
   안 눌리면 안내문에 「쪽지의 주소를 복사해 주소창에 붙여 넣으세요」를 넣는다(ANNOUNCE-v2 「공통」에 이미 그렇게 적었다). 코드로는 같은 주소를 `URL` 필드에도 싣는 한 줄.
2. **3단계에서 `merge_review`가 「승인 = 위로」를 말하지 않는다.** 「고칠 부분을 알려주세요」는 담당자에게 말하라는 뜻으로 읽힌다 — 3단계에서는 부서장이
   직접 고쳐 저장하거나 승인하고, 그것이 곧 제출이다. 3단계 문구 후보: 「Tincase 수합 관리에서 확인하고 승인하면 바로 {받는 곳}에 올라갑니다(기한 {기한}).」
3. **`ru_hq_reapprove`의 첫 줄이 어색하다** — 이유가 「기획조정실 승인으로」면 「… 기획조정실 승인으로 승인한 뒤 본부본이 다시 이어 붙었어요.」가 된다.
   12 §8 RU-55a의 의도는 「기획조정실이 다시 올려 본부본이 바뀌었어요 — 다시 승인해 주세요」였다.
4. **총괄의 「전사본 준비」가 언제 가느냐에 따라 세는 단위가 다르다.** 모두 들어온 순간(사건)에는 **섹션 제목**(「기획경영본부(기획조정실)」…, 13곳)을,
   16:00 기한에는 **최상위 단위 이름**(「기획경영본부」·「탄소중립에너지연구실」…, 섹션보다 적다)을 센다. 같은 총괄이 16:00에 「8/9곳 도착」을 받고 뒤에
   「13곳이 다 들어왔어요」를 받을 수 있다.
5. **v1 시절 낱말이 남은 문구** — `merge_missing`의 「제출된 파일이 없거나」(이제 파일을 올리지 않는다 — 「제출이 없거나」), `merge_done` ①의
   「대외업무 마감이 얼마 남지 않았어요」(3단계에서는 「실·팀 → 본부」 15:00 · 「본부 → 총괄」 16:00 기한이다).
6. **`deadline_1h`만 빈 줄이 없다** — 다른 마감 알림은 첫 줄 뒤에 빈 줄이 있다(빈 줄을 모두 거르는 코드). 모양만의 일.
7. **「병합 점검」은 기획조정실의 담당자(lead) 전원**에게 간다 — 총괄 본인이 담당자가 아니면 총괄은 받지 않고, 기획조정실 담당이 여럿이면 모두 받는다(TACP-30). 의도대로인지.
8. **양.** 알림 켠 12개 부서의 미제출 부서원에게 한 주 최대 세 통(수 11:45 · 목 13:00 · 13:50). 수 11:45에는 거의 전원이 한꺼번에 받는다 — 6절로 미리 센다.

## 6. 받는 사람 수 미리 보기 — 이름 없이

화면에만 띄우고 저장하지 않는다. 수신 허용 목록(`MESSENGER_ALLOWLIST`)으로 걸러지는 것은 여기 반영되지 않는다 — 기동 로그 `[알림] 켜짐 (수신 허용: …)`를 함께 본다.

```bash
sudo docker exec repman sqlite3 -header -column /data/db/worklog.db "
SELECT '마감 전 (부서원)' AS 무엇, COUNT(*) AS 사람 FROM User u JOIN Division d ON d.id = u.divisionId
 WHERE d.isActive = 1 AND d.notifyEnabled = 1 AND u.isActive = 1 AND u.onRoster = 1 AND u.notifyEnabled = 1 AND u.employeeNo IS NOT NULL
UNION ALL SELECT '담당자', COUNT(*) FROM User u JOIN Division d ON d.id = u.divisionId
 WHERE d.isActive = 1 AND d.notifyEnabled = 1 AND u.isActive = 1 AND u.divisionRole = 'lead' AND u.notifyEnabled = 1 AND u.employeeNo IS NOT NULL
UNION ALL SELECT '부서장', COUNT(*) FROM User u JOIN Division d ON d.id = u.divisionId
 WHERE d.isActive = 1 AND d.notifyEnabled = 1 AND u.isActive = 1 AND u.divisionRole = 'head' AND u.notifyEnabled = 1 AND u.employeeNo IS NOT NULL
UNION ALL SELECT '본부장 (3단계)', COUNT(*) FROM User u JOIN Division d ON d.id = u.divisionId
 WHERE d.nameKo = '기획경영본부' AND d.isActive = 1 AND u.isActive = 1 AND u.divisionRole = 'head' AND u.notifyEnabled = 1 AND u.employeeNo IS NOT NULL
UNION ALL SELECT '총괄 (3단계)', COUNT(*) FROM User
 WHERE isActive = 1 AND isCoordinator = 1 AND notifyEnabled = 1 AND employeeNo IS NOT NULL
UNION ALL SELECT '병합 점검', COUNT(*) FROM User
 WHERE isActive = 1 AND notifyEnabled = 1 AND employeeNo IS NOT NULL
   AND (isOperator = 1 OR (divisionRole = 'lead' AND divisionId IN (SELECT divisionId FROM User WHERE isCoordinator = 1 AND isActive = 1)));"
```

나간 뒤 — 이번 주에 무엇이 몇 통 나갔나:

```bash
sudo docker exec repman sqlite3 -header -column /data/db/worklog.db "
SELECT CASE WHEN instr(n.kind, ':') > 0 THEN substr(n.kind, 1, instr(n.kind, ':') - 1) ELSE n.kind END AS 종류,
       COUNT(*) AS 기록, SUM(json_array_length(n.recipients)) AS 받은_사번
FROM NotifyLog n JOIN WeekSlot w ON w.id = n.weekSlotId
WHERE w.isoKey = '2026-W42' GROUP BY 1 ORDER BY 1;"
```
