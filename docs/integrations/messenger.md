# 사내 메신저(UCWare) 알림 연동

> **이 문서의 API 주소는 자리표시자다.** 저장소가 public이므로 실제 호스트를 적지 않는다.
> 실제 값은 `MESSENGER_URL` 환경변수로 주고, 사내 문서(`docs/private/`)에만 둔다.
>
> ```
> 문서 표기   http://messenger.example.com:12555
> 실제 값     MESSENGER_URL 환경변수 (사내망 주소:12555)
> ```

## 1. 프로토콜 요약

| 항목 | 값 |
|---|---|
| Method | `POST` |
| Path | `/` (포트 `12555`) |
| Content-Type | `application/x-www-form-urlencoded; charset=UTF-8` |
| 응답 | **HTML 문자열** (JSON 아님) → 성공 판정은 HTTP 200으로 |
| 방화벽 | 앱 서버 → 메신저 서버 `12555/TCP` Outbound 허용 필요 |

### 파라미터 (CMD=ALERT)

| 필드 | 필수 | 설명 |
|---|:---:|---|
| `CMD` · `Action` | Y | 둘 다 `ALERT` |
| `SystemName` | Y | 발송 시스템명 — 팝업 상단에 표시 |
| `SendID` · `SendName` | Y | 발송자 사번·표시 이름 |
| `RecvId` | Y | **수신자 사번.** 여러 명은 콤마 (`21963,10196`) — 공백 금지 |
| `Subject` · `Contents` | Y | 제목·본문 (본문은 `\n` 줄바꿈 지원) |
| `URL` | N | 누르면 열릴 주소. 없으면 메신저 보관함이 열린다 |
| `Option` | N | `WB=NEW,WA=EDGE` (사내 샘플 값) |

### ★ 인코딩 — 가장 자주 틀리는 곳

텍스트 필드는 **값과 인코딩을 쌍으로** 보내야 한글이 깨지지 않는다.

```
SystemName → SystemName_Encode = "UTF-8"
SendName   → SendName_Encode   = "UTF-8"
Subject    → Subject_Encode    = "UTF-8"
Contents   → Contents_Encode   = "UTF-8"
URL        → URL_Encode        = "UTF-8"
```

구현(`src/server/messenger.ts`)에서는 `appendEncoded()`가 이 쌍을 강제해,
필드를 추가할 때 인코딩을 빠뜨릴 수 없게 했다.

## 2. 이메일이 아니라 **사번**이다

메신저는 사번(`RecvId`)으로만 사람을 찾는다. 그래서 `User.employeeNo`를 두었다.
**사번이 없는 사람에게는 알림이 가지 않는다** — 조용히 빠지지 않도록 로그에 남긴다.

사번의 원천은 인사 명단 엑셀이다 (`docs/private/인사명단.md` — 개인정보라 커밋 제외).
등록은 `scripts/import-employee-no.ts`가 «부서 + 이름»으로 잇는다 —
이름만으로 이으면 동명이인에게 알림이 가고, 알림은 잘못 가면 되돌릴 수 없다.

## 3. 안전장치 — 「닫혀 있음」이 기본값

이 API는 **실제로 사람 화면에 팝업을 띄운다.** 실수는 늘 «열려 있을 때» 난다.

| 환경변수 | 없을 때 |
|---|---|
| `MESSENGER_URL` | 알림 기능 **전체가 꺼짐** |
| `MESSENGER_ALLOWLIST` | **아무에게도 안 감** (비어 있음 = 전원 차단) |

```bash
MESSENGER_ALLOWLIST="21963"   # 테스트 — 나에게만
MESSENGER_ALLOWLIST="*"       # 전원 발송 (의도적으로 켤 때만)
```

허용 목록 밖으로 걸러진 대상은 **로그에 남는다.** 조용히 사라지면
"왜 안 왔지"를 나중에 풀 수 없다.

## 4. 지금 쓰는 곳 — 마감 1시간 전 알림 (NT-10)

마감 1시간 전(AI홍보전략실 기준 **목 13:00**), 그 주에 아직 내지 않은 사람에게 한 번.

- 5분 주기 스케줄러가 `[48분, 60분]` 창을 반드시 한 번 지난다
- **집계 대상(`onRoster`)만** — 부서장·휴직자에게 독촉하지 않는다 (DM-16)
- `NotifyLog`에 `(부서, 주차, 종류)` 유니크로 기록 → **두 번 가지 않는다**
- 알림이 실패해도 자동 병합은 그대로 돈다 (따로 감싼다)

```bash
npx tsx scripts/notify-test.ts             # 설정·상태만 출력
npx tsx scripts/notify-test.ts --send      # 허용 목록에 실제 발송
npx tsx scripts/notify-test.ts --reminder  # 마감 전 알림 경로를 지금 실행
```

## 4-2. 마감 뒤 알림 — 부서장 검토 → 담당자 제출 (NT-40~48)

대외업무 마감이 **15:00**, 부서 마감이 **14:00**이다. 그 한 시간이 검토에 쓸 수 있는 전부다.
그래서 한 번에 몰지 않고 **받는 사람마다 할 일이 생기는 순간**에 나눠 보낸다.

```
14:00  마감 → 자동 병합
14:10  부서장(head): 「병합본 준비됐어요, 검토 부탁드려요」   [성공했을 때만]
       ↳ 실패면 대신 담당자(lead)에게: 「병합본이 아직 없어요」
14:30  담당자(lead): 「최종 확인하고 제출해주세요」
15:00  대외업무 마감
```

- **왜 실패는 부서장에게 안 보내는가.** 부서장은 병합 실패를 고칠 수 없다 —
  [지금 병합]을 누르는 사람은 담당자다. 고칠 수 없는 사람에게 가는 실패 통지는 소음이고,
  소음이 쌓이면 정작 중요한 알림도 안 읽힌다. **예외가 조용해지는 게 아니라 받는 사람이 바뀐다**
- **왜 +10분인가.** 병합은 모델 호출까지 수십 초~수 분 걸린다. 더 이르면 «아직 병합 중»에 걸린다
- **왜 +30분인가.** 부서장이 볼 20분을 준 뒤다. 담당자는 반영해서 15:00까지 30분 여유가 남는다
- `NotifyLog`에 `(부서, 주차, 종류)` 유니크 → 종류마다 **한 주차에 한 번만** 간다
- **병합이 늦게 끝나면 창도 늦게 연다** (HM-50) — 창의 시작은 `max(마감+n분, 병합이 끝난 시각)`.
  부서 하나를 병합할 때마다 다시 판정하므로, 13개 부서가 줄을 서도 먼저 끝난 부서는 기다리지 않는다.
  대외 마감(+60분)이 지나서 끝난 병합에는 보내지 않는다
- **자동 재병합을 멈췄을 때** (NT-51 · HM-49) — 마감 열기가 닫혔는데 병합본에 사람이 고친 곳이 있으면 다시 병합하지 않고,
  열린 동안 더 낸 사람이 있을 때만 담당자에게 「[다시 병합]하면 고친 내용은 사라져요」를 보낸다. 닫힘마다 한 번
  (`NotifyLog.kind = merge_held:<닫힌 시각>`)
- 부서장 알림에는 **「각 항목을 누가 냈는지도 보입니다」**를 덧붙인다 (TACP-17).
  검토하다 잘못된 행을 찾으면 다음 행동은 그 사람과 이야기하는 것이기 때문이다
- **NT-53 (2026-10-08) — 링크(`URL` 필드)는 알림 종류와 상관없이 `{MESSENGER_LINK_BASE}/{slug}/manage`다.** 예전에는 부서장 검토
  요청(`merge_review`)만 보관함(`/{slug}/archive`)으로 갔는데, 보관함은 홈의 지난 주차로 합쳐졌고 홈의 [병합본]은 읽기 전용이다
  — 부서장이 고치고 승인하는 곳은 수합 관리다(PG-70 · CP-114). 이미 나간 옛 링크는 그 주소의 보내기 페이지가 수합 관리로 받는다.
  시험 `[NT-T66]`(`tests/messenger.test.ts`)

```bash
npx tsx scripts/notify-test.ts --who      # 지금 보내면 누구에게 갈지만 (발송 없음)
npx tsx scripts/notify-test.ts --notices  # 마감 뒤 알림 경로를 지금 실행
```

`--who`를 만든 이유: 대상이 맞는지 확인할 방법이 «실제로 보내 보는 것»뿐이면
**확인하려다 알림을 보내게 된다.**

## 4-3. 3단계 자동 진행 알림 — 막고 있는 사람에게만 (2026-10-08 · [12 §8](../spec/12-org-rollup.md) RU-53~57b · ADR-0015)

3단계에서 승인이 곧 제출이 되면서(RU-70) **넘기는 사람에게 가던 알림이 없어진다** — 넘길 일이 없기 때문이다.
남는 알림은 둘 중 하나다: 「당신의 결정을 기다리는 것이 준비됐다」(사건 — 그 순간), 「기한이 15분 남았는데 당신이 막고 있다」(시각).

```
14:01  자동 병합
14:10  실장: 「검토 부탁드려요」                                     (NT-40, 그대로)
14:12  실장 [승인] ══► 본부로 올라감
       담당자: 「승인 완료 — 기획경영본부에 자동으로 올라갔어요」    (NT-46′ — 그 순간, 하나로)
14:30  담당자: 승인됐으면 없음 / 승인 전이면 「승인되면 저절로 올라가요」 (NT-47′)
14:40  산하가 다 모여 본부본이 저절로 이어 붙음
       본부장: 「본부본이 준비됐어요 — 승인하면 바로 총괄로」         (RU-54 — 다 모인 순간, 아니면 15:00에 일부로)
14:45  아직 승인 안 한 다른 실장에게만: 「15분 남았어요」             (RU-56a)
15:20  본부장 [승인] ══► 총괄로 감 (본부 담당자에게는 안 간다)
15:45  아직 승인 안 한 본부장에게만: 「15분 남았어요」 — 이 예에서는 안 간다 (RU-56)
       모든 섹션이 들어온 순간 총괄 각자: 「전사본이 준비됐어요」      (RU-57 — 아니면 16:00에 일부로)
```

| 종류 (`NotifyLog.kind`) | 받는 사람 | 언제 | 한 번의 단위 |
|---|---|---|---|
| `merge_approved:<승인 id>` (NT-46′) | 실·팀 담당자 | 승인 순간 | 승인마다 (그대로) |
| `merge_reapprove:<승인 id>` (NT-52) | 실·팀장 | 승인 뒤 병합본이 바뀐 순간 | 승인마다(2026-10-08 개정 — 예전에는 새 판마다) — 가장 최근 승인에 이 기록이 있으면 +10분 검토 요청(`merge_review`)은 건너뛴다(NT-T66) |
| `ru_unit_due_soon` (RU-56a) | 실·팀장 | 그 단위 기한 15분 전, 승인 전·승인 뒤 바뀜일 때 | 부서·주차 |
| `ru_hq_ready` · `ru_hq_complete` (RU-54) | 본부장 | 다 모인 순간 / 「실·팀 → 본부」 기한(일부) — 먼저 한 번, 일부였으면 다 모일 때 한 번 더 | 본부·주차 |
| `ru_hq_reapprove:<승인 id>` (RU-55a) | 본부장 | 승인 뒤 본부본 판이 바뀐 순간 | 풀린 승인마다 |
| `ru_hq_due_soon` (RU-56) | 본부장 | 「본부 → 총괄」 기한 15분 전, 승인 전·뒤 바뀜일 때 | 본부·주차 |
| `ru_org_ready:<사람>` · `ru_org_complete:<사람>` (RU-57) | 총괄 각자 | 모두 들어온 순간 / 「본부 → 총괄」 기한(일부) | 총괄·주차 |
| `ru_org_changed:<받은 실행 id>:<사람>` (RU-57a) | 전사본을 받은 총괄 | 받은 뒤 전사본이 바뀐 순간 | 받은 판마다 |
| `ru_hq_failed:<열쇠>` · `ru_org_failed:<열쇠>` (RU-57b) | 본부 담당자 · 총괄 | 조립이 실패한 순간 | 실패한 입력마다 |

- **없앤 것**: `ru_hq_collect`(본부 담당자 「이어 붙이세요」) · `hq_approved:<id>`(본부 담당자 「승인 완료 — [총괄에 제출]」) ·
  본부 담당자의 `ru_hq_due_soon` · 총괄의 「이어 붙이세요」 문구. 할 일이 없는 사람에게 가는 알림은 소음이다(§4-2와 같은 원칙)
- **사건 알림은 스케줄러를 기다리지 않는다** — 그 사건을 맞춘 요청 뒤(`after()`)에서 바로 판정한다. 시각 알림만 스케줄러가 본다
- **기록을 먼저 잡고 보낸다** (2026-10-08) — 같은 종류를 사건과 시각 둘이 판정할 수 있다(RU-54·57: 「다 모인 순간」과 기한). 보내기 전에
  (부서·주차·종류) 유일 키로 `NotifyLog`를 넣고 넣은 쪽만 보낸다 — 같은 순간에 돌아도 한 번이다. 아무에게도 안 나갔으면 그 줄을 지운다(12 §8)
- 실·팀 사람에게 가는 것(NT-46′·47′·52, RU-56a)은 **부서 알림 스위치(NT-30)**도, 본부·총괄에 가는 것은 **3단계 스위치(RU-52)**를 따른다
- 테스트 서버는 실제 메신저 대신 **가짜 알림 수신함**으로 보낸다(RU-41 · §9) — 밖으로는 하나도 나가지 않고, 받은 것은 `NotifyLog`에 「보냄」으로 남는다. 자동 진행 자체는 끝까지 돈다

## 5. 더 쓸 수 있는 곳 (검토만 — 아직 만들지 않음)

넣기 쉬운 것부터가 아니라 **사람이 실제로 막히는 순간**부터 적는다.

| 후보 | 언제 | 왜 / 조심할 점 |
|---|---|---|
| ~~병합 완료·실패 알림~~ | ~~목 14:20~~ | **만들었다 (NT-40, §4-2)** |
| **제출 확인** | 제출 직후 | 「접수됐습니다」. 다만 화면이 이미 «제출 완료»를 보여준다 — **중복 알림은 신뢰를 깎는다.** 권하지 않음 |
| **주 시작 안내** | 월 09:00 | 「이번 주 시작」. 매주 오면 곧 안 읽는다. 월간 주(그 달 마지막 주)에만 보내면 값이 있다 |
| **명단 등록 요청** | 집계 제외자가 제출했을 때 | 운영자에게 «명단 밖인데 냈습니다». 드문 일이라 소음이 없다 |

**공통 원칙**: 알림은 **행동을 바꿀 수 있을 때만** 보낸다. 「알고만 있으세요」는 화면이 할 일이다.
같은 말을 두 번 하지 않는다 — 두 번째부터 안 읽힌다.

## 6. 사내 샘플 폼과의 대조 (2026-08-26)

받은 원본 샘플(`UCM_알림_전송테스트.html`)의 폼 필드와 우리가 보내는 필드를
기계적으로 대조했다 — **16개 필드가 완전히 일치**한다.

```
Action CMD Contents Contents_Encode Option RecvId SendID SendName
SendName_Encode Subject Subject_Encode SystemName SystemName_Encode
URL URL_Encode key
```

빠진 것도, 우리가 더 보내는 것도 없다. (`SendID`에는 `_Encode`가 없다 — 원본도 그렇다)

한 가지만 달랐다: `Option`을 우리는 `WA=DEFAULT`로 두었는데 **사내 샘플은 `WA=EDGE`**다.
샘플 값을 기본으로 바꿨다 — 우리가 「더 안전해 보이는」 값을 고르는 것보다
**사내에서 실제로 동작을 확인한 값**을 따르는 편이 낫다.
Edge가 없는 PC가 있으면 `MESSENGER_URL_OPTION=WB=NEW,WA=DEFAULT`로 바꾼다.

> **원본 주석에 `<!-- NCP_TEST_Cluster -->`가 있다.** 이 엔드포인트는 **테스트 클러스터**일
> 수 있다. 실제 운영 메신저 주소가 따로 있는지 확인이 필요하다.

## 7. 본문에 링크는 넣을 수 없다 (2026-08-26 실측)

「Tincase」 글자에 하이퍼링크를 걸어 보려고 두 가지를 실제로 보내 확인했다.

| 시도 | 결과 |
|---|---|
| `<a href="…">Tincase</a>` | **태그가 글자 그대로** 보인다 — 본문 HTML 미지원 |
| `Tincase(http://…)` | 주소가 길게 늘어지고 **클릭되지 않는다** |

**링크는 `URL` 필드 하나뿐이다.** 그 값은 **제목**에 걸려서, 알림이나 제목을 누르면 열린다
(알림함에서 제목이 파란 링크로 표시된다). 본문에는 아무 표식도 넣지 않는다 —
억지로 넣으면 더 지저분해진다.

## 7-2. 문자(SMS)는 이 API로 보낼 수 없다 (2026-08-26 조사)

「회의 중에도 받게 문자로」라는 요구가 있었다. **UCWare 연동 문서 전체를 확인한 결과
문자 발송 기능이 없다.** 명령은 `ALERT`·`CONFIRM`·`MSG_LINK` 셋뿐이고, 수신자를 가리키는
필드는 `RecvId`(사번) 하나다. 휴대폰 번호를 받는 파라미터가 아예 없다.

그래서 «Tincase에서 문자를 보낸다»는 **새 채널을 붙이는 일**이지 설정 문제가 아니다.
현실적인 선택지는 셋이고, 순서대로 권한다.

| 방법 | 비용 | 개인정보 | 비고 |
|---|---|---|---|
| **① UCWare 모바일 앱** | 없음 | 사내에 머문다 | 이미 사번으로 보내는 알림이 **그대로 폰에 뜬다.** 전산팀에 «모바일 클라이언트가 배포돼 있는지»만 확인하면 된다 |
| **② 메일 전달** | 없음 | 사내에 머문다 | `@kei.re.kr`로 보내면 폰 메일 앱이 푸시한다. 발송 코드는 새로 필요하다 |
| **③ 외부 문자 서비스** | 건당 과금 · 계약 필요 | **밖으로 나간다** | 이름·사번·부서가 외부 사업자를 지난다. 공공기관이라 개인정보 처리 위탁 절차가 붙는다 |

**①을 먼저 확인해야 한다.** 알림은 이미 사번으로 나가고 있으므로, 모바일 앱만 깔려 있으면
**코드를 한 줄도 안 고치고** 지금 이 순간 해결된다. 새 채널을 만드는 것은 그게 안 될 때다.

③은 되도록 피한다 — 알림 하나 때문에 전 직원의 소속·사번이 외부로 나가는 구조가 된다.

## 8. 문제 해결

| 증상 | 원인 |
|---|---|
| `ECONNREFUSED` | 방화벽에서 `12555/TCP` Outbound 막힘 · 사내망 아님 |
| 한글 깨짐 | `*_Encode` 누락 |
| 안 옴 | 사번 불일치 · 수신자 메신저 미로그인(보관함에는 적재) · 방해금지 |
| CORS 오류 | 브라우저에서 직접 호출함 — **서버에서만** 호출한다 |

## 9. 가짜 알림 수신함 — 시험·시연 서버 (2026-10-08 · NT-56)

v2 전환(10/12) 전 주말에 알림을 **보내지 않고** 끝까지 시험하려고 만들었다. 같은 앱 안의 주소가 메신저 노릇을 한다 —
클라이언트(`src/server/messenger.ts`)는 진짜 메신저와 구별하지 않고 보내고, 수신함은 받은 폼을 그대로 적는다.

```
진짜     앱 ──POST 폼──▶ 사내 메신저(12555) ──▶ 사람 화면 팝업
시험     앱 ──POST 폼──▶ 같은 앱 /api/dev/messenger-sink ──▶ STORAGE_ROOT/dev/messenger-sink.jsonl ──▶ /ops/notify-sink(운영자)
```

| | 값 |
|---|---|
| 켜는 법 | `TINCASE_ENV=test`(또는 `demo`) **그리고** `MESSENGER_SINK=on` — 테스트 compose가 둘 다 준다 |
| 주소 | `MESSENGER_URL=http://127.0.0.1:3000/api/dev/messenger-sink` (컨테이너 안 — 밖으로 나가는 길이 없다) |
| 허용 목록 | `MESSENGER_ALLOWLIST="*"` — 받는 곳이 이 앱 자신이라 거를 사람이 없다. 거르면 「누구에게 갔을 것인가」가 남지 않는다(NT-56d) |
| 응답 | `send ok` — 진짜 메신저의 성공 응답과 같다 |
| 종류 | 머리 `x-tincase-kind`(`merge_review` · `ru_org_ready:<사람>` …) — **수신함으로 갈 때만** 붙는다. 진짜 메신저 요청은 그대로 |
| 보기 | 운영자 `/ops/notify-sink` — 새 것부터, 종류·받는 사람으로 거르기, [비우기](두 번 누름) |
| 운영 | `TINCASE_ENV`가 없으면 경로·화면이 **누구에게나 404**. 운영이 수신함 주소를 받거나 시험 서버가 실제 주소를 받으면 **뜨지 않는다**(OPS-46) |

테스트 서버는 운영 사본이라 수신함에 **실명**이 쌓인다 — 그래서 화면은 운영자만 연다(TACP-26). 가짜 사람만으로 한 주를 돌려 보려면
시연 저장소에서 리허설을 한다([REHEARSAL.md](../REHEARSAL.md) — 각 알림이 맞는 사람에게 한 번, 제 창 안에 갔는지 판정까지).
