# R-001. HWP 파일 포맷 실측 조사 결과

> 상태: **완료 (실측 검증됨)** · 조사일 2026-08-13 · 대상 `~/MWreports/*.hwp`
>
> 이 문서는 추측이 아니라 **실제 배포 중인 파일을 파싱해서 얻은 측정값**이다.
> 병합 엔진 스펙([08-hwp-merge-engine](../spec/08-hwp-merge-engine.md))의 모든 설계 근거가 여기서 나온다.

---

## 1. 요약 (결론부터)

| 질문 | 실측 답 |
|---|---|
| 실제 양식 확장자 | **`.hwp` (HWP 5.0 바이너리/OLE)** — `.hwpx` 아님 |
| 누름틀(필드) 사용 | **없음.** 셀에 일반 문단 텍스트로 직접 기입 |
| 병합 셀 | **없음.** 전 셀 `(colSpan, rowSpan) = (1,1)` 균일 5열 격자 |
| 리눅스 순수 코드로 읽기 | **가능** — 레코드 파싱 완전 성공 |
| 리눅스 순수 코드로 쓰기 | **가능** — 왕복 바이트 동일성 + 실제 수정·재생성 검증 완료 |
| 한글 프로그램 필요 여부 | **불필요** |

> **핵심 근거**: 파싱 → 무수정 재직렬화 결과가 원본과 **바이트 단위 완전 동일**(SHA-256 일치).
> 즉 레코드 모델이 무손실이며, "건드리지 않은 것은 절대 변하지 않는다"가 보장된다.
> → 스펙 §2 "표 안 깨짐"이 희망이 아니라 **구조적 성질**이 된다.

## 3. 컨테이너 구조 (OLE Compound File)

```
FileHeader                256 B    ← 시그니처 + 버전 + 플래그
DocInfo                  1443 B    ← zlib(raw deflate) 압축, 122~126 레코드
BodyText/Section0        2790 B    ← zlib(raw deflate) 압축, 466~655 레코드
HwpSummaryInformation     489 B
PrvText                  1080 B    ← 미리보기 평문(UTF-16LE), 최대 1024자
PrvImage                29832 B    ← 미리보기 PNG (파일 크기의 대부분)
DocOptions/_LinkDoc       524 B
Scripts/DefaultJScript     85 B
Scripts/JScriptVersion     13 B
```

- `FileHeader[32:36]` = `00 01 01 05` → HWP **5.1.0.0**
- `FileHeader[36] & 0x01` = 1 → **본문 스트림 압축됨**
- 압축은 **raw deflate** (zlib 헤더 없음). Node `zlib.inflateRawSync` / Python `zlib.decompress(data, -15)`

> `PrvText`는 셀 내용을 `<...>` 구분자로 나열해 주므로 **디버깅/미리보기에 매우 유용**하다.
> 단 1024자에서 잘리므로 **정본 데이터 소스로 쓰면 안 된다.** (실제로 `8월_2주차`는 3번 표가 잘려 안 보였다.)

## 4. 레코드 구조

모든 스트림은 동일한 TLV 레코드 스트림이다.

```
UINT32 header:
  bits  0..9   tagID   (10 bit)
  bits 10..19  level   (10 bit)   ← 트리 깊이
  bits 20..31  size    (12 bit)
if size == 0xFFF:  UINT32 realSize 가 뒤따름   ← 확장 길이
그 뒤 size 바이트의 payload
```

### 4.1 등장하는 태그

| tagID | 이름 | 역할 |
|---|---|---|
| 66 | `PARA_HEADER` | 문단 헤더 (글자 수 포함) |
| 67 | `PARA_TEXT` | 문단 텍스트 (UTF-16LE) |
| 68 | `PARA_CHAR_SHAPE` | 글자모양 적용 구간 |
| 69 | `PARA_LINE_SEG` | 줄 배치 정보 (한글이 열 때 재계산) |
| 71 | `CTRL_HEADER` | 컨트롤 헤더 (`tbl `, `secd`, `cold`) |
| 72 | `LIST_HEADER` | 표 **셀** 헤더 — 셀 주소가 여기 있음 |
| 77 | `TABLE` | 표 정의 (행·열 수) |

### 4.2 표의 레코드 배치 (실측)

```
PARA_HEADER               lvl=0        ← 표를 담는 문단
  PARA_TEXT               lvl=1        ← 내용은 컨트롤 문자 11 하나뿐
  PARA_CHAR_SHAPE         lvl=1
  PARA_LINE_SEG           lvl=1
  CTRL_HEADER  id='tbl '  lvl=1
    TABLE                 lvl=2        ← rows/cols
    LIST_HEADER           lvl=2        ← 셀 (0,0)
    PARA_HEADER           lvl=2
      PARA_TEXT           lvl=3        ← "구분"
      PARA_CHAR_SHAPE     lvl=3
      PARA_LINE_SEG       lvl=3
    LIST_HEADER           lvl=2        ← 셀 (1,0)
    PARA_HEADER           lvl=2
      ...
```

**셀은 좌→우, 상→하 순서로 평탄하게(flat) 나열된다.** 행 구분자 레코드는 없다.
따라서 `LIST_HEADER` 블록 = 셀 1개이며, 한 행은 연속된 5개 블록이다.

### 4.3 `TABLE` 레코드 (tagID 77) 바이트 레이아웃

| offset | 타입 | 내용 | 실측값 |
|---|---|---|---|
| 0 | UINT32 | property | `0x04000006` |
| 4 | UINT16 | **nRows** | 9 / 10 / 14 / 5 |
| 6 | UINT16 | **nCols** | 5 (전 파일 동일) |
| 8 | INT16 | cellSpacing | 0 |
| 10 | INT16 ×4 | margin L/R/T/B | 510, 510, 141, 141 |
| 18 | UINT16 × nRows | **rowSize[]** (행별 셀 수) | 전부 5 |
| 18+2n | UINT16 | borderFillID | — |
| 20+2n | UINT16 | validZoneInfo 개수 | **0** (영역 정보 없음 → 단순) |

레코드 총 길이 = `18 + 2·nRows + 4`. 실측 일치 (rows=9 → 40 B, rows=14 → 50 B). ✔

### 4.4 `LIST_HEADER` 레코드 (tagID 72) — 셀 주소

47 바이트 고정. 앞부분만 필요하다.

| offset | 타입 | 내용 |
|---|---|---|
| 0 | UINT32 | 문단 수 (항상 1) |
| 4 | UINT32 | 속성 |
| 8 | UINT16 | **colAddr** (0-based 열) |
| 10 | UINT16 | **rowAddr** (0-based 행) |
| 12 | UINT16 | colSpan — **전부 1** |
| 14 | UINT16 | rowSpan — **전부 1** |
| 16 | UINT32 | 셀 너비 (HWPUNIT) |
| 20 | UINT32 | 셀 높이 |
| 24.. | | 여백 등 |

검증 예 (빈 양식 1번 표):

```
"구분"          08~15: 00 00 | 00 00 | 01 00 | 01 00   → (col 0, row 0)
"업무실적 내용"  08~15: 01 00 | 00 00 | 01 00 | 01 00   → (col 1, row 0)
"1-1"           08~15: 00 00 | 01 00 | 01 00 | 01 00   → (col 0, row 1)
"제10차 인사위원회" 08~15: 01 00 | 01 00 | 01 00 | 01 00   → (col 1, row 1)
```

> **행 추가/삭제 = `rowAddr` 재계산 + `TABLE.nRows`/`rowSize[]` 갱신.** 그 외에는 손댈 것이 없다.
> 열 너비·테두리·여백은 셀 레코드에 실려 있으므로 **기존 행을 복제하면 서식이 그대로 따라온다.**

### 4.5 `PARA_HEADER` (tagID 66) — 24 B

| offset | 타입 | 내용 |
|---|---|---|
| 0 | UINT32 | **nChars** — ⚠ 최상위 비트가 플래그 |
| 4 | UINT32 | controlMask |
| 8 | UINT16 | paraShapeID |
| 10 | UINT8 | styleID |
| 11 | UINT8 | columnType |
| 12 | UINT16 | charShape 개수 |
| 14 | UINT16 | rangeTag 개수 |
| 16 | UINT16 | lineSeg 개수 |
| 18 | UINT32 | instID |
| 22 | UINT16 | mergedTrack |

**⚠ 함정 (실측으로 발견):** `nChars` 원본값이 `0x8000000B`였다.
`0x80000000`은 플래그 비트이고 실제 글자 수는 하위 31비트(`11`)다.

```
올바른 갱신식:
  nChars = (원본값 & 0x80000000) | (PARA_TEXT 바이트길이 / 2)
```

이 비트를 지우고 쓰면 문서가 깨진다. **엔진 구현 시 반드시 보존할 것.**

### 4.6 `PARA_TEXT` (tagID 67)

- UTF-16LE.
- **문단 끝 `0x000D`(CR)를 포함**한다. `"구분"` = 6 B = `구`,`분`,`CR`.
- `nChars`는 이 CR을 **포함한 값**이다. 실측: 텍스트 31자 + CR = 32 = `0x80000020`의 하위 비트. ✔
- 인라인 컨트롤 문자(1,2,3,11,12,…)는 **16바이트(8 코드유닛)** 를 차지한다. 표 자체는 `ctrl 11`로 본문에 박혀 있다.

## 5. 양식의 논리 구조 (실측)

문서는 **동일한 5열 표 3개**로 구성된다.

| # | 제목 | 열 구성 | 빈 양식 행 수 |
|---|---|---|---|
| 1 | `1. 주요 업무실적` | 구분 / 업무실적 내용 / 일자 / 장소 / 참석자 | 1 헤더 + 8 데이터 |
| 2 | `2. 주요 업무계획` | (동일) | 1 헤더 + 8 데이터 |
| 3 | `3. 기타 특이사항` | (동일) | 1 헤더 + 4 데이터 |

`구분` 열은 `{표번호}-{행번호}` 로 자동 채워진다 — `1-1`, `1-2`, … `2-1`, … `3-1`, …

### 5.1 실제 파일에서 관찰된 가변성 ★

| 파일 | 표1 행 | 표2 행 | 표3 |
|---|---|---|---|
| 빈 양식 | 9 | 9 | 5 |
| `8월_2주차` (실제) | **10** | 9 | **없음** |
| `8월_1주차` (실제) | **14** | **14** | **없음** |

여기서 두 가지 필수 요구사항이 나온다:

1. **행 수는 내용에 맞춰 늘어난다** → 병합 엔진은 **행 삽입/삭제**를 반드시 지원해야 한다.
   (단순 텍스트 채우기만으로는 부족하다.)
2. **내용 없는 3번 표는 표째로 삭제된다** → "빈 섹션 제거" 규칙이 실재한다.

> 반대로, 표2에 `2-8` 빈 행이 남아 있는 실제 제출본이 있다.
> → **꼬리 빈 행 몇 개는 조직 관례상 허용**된다. 정확히 0으로 맞출 필요는 없다.

### 5.2 날짜 표기 관례

- 형식 `8/12` (M/D). 빈 양식 자리표시자는 `OO/OO`.
- **상시 반복 업무는 공란** — 실제 파일에서 `인포그래픽 제작`, `온라인 홍보 콘텐츠 제작 및 등록`은 일자 없음. 스펙 §3 관례와 일치. ✔

### 5.3 주차 라벨 규칙 검증 ★

`8월_2주차` 파일 내용:
- 실적 일자: `8/12`(수), `8/14`(금)
- 계획 일자: `8/19`(수)

2026년 8월의 월요일: 3, 10, 17, 24, 31.
→ 실적 주간은 **8/10 주(2번째 월요일)**, 계획 주간은 8/17 주. 라벨 `8월 2주차`와 정확히 일치.

**결론: `N주차 = 그 주 월요일이 그 달의 N번째 월요일` 규칙이 실제 관례와 일치함이 실데이터로 확인됨.**
스펙 §10의 미결 항목 3번은 이로써 해소. ([02-week-slot](../spec/02-week-slot.md) 참조)

또한 문서 구조가 **금주 실적 + 차주 계획**임이 확인된다 (실적 8/12·8/14, 계획 8/19).
→ 화요일 14:00 마감이 "이번 주 실적을 주중에 미리 쓰는" 형태임과 모순 없음.

## 6. 검증 실험 (재현 가능)

### 실험 1 — 왕복 바이트 동일성

```
파일                    레코드   원본 B    재생성 B   동일?
빈 마스터 양식            552    17,468    17,468    ✔ SHA 일치
8월_2주차                466    14,994    14,994    ✔ SHA 일치
8월_1주차                655    21,439    21,439    ✔ SHA 일치
DocInfo (3파일 모두)   122~126        —         —    ✔ 일치
```

### 실험 2 — 실제 수정 → 재생성 (Node.js 단독)

`cfb` + `node:zlib`만 사용. 한글·파이썬 없음.

1. 셀 `1-1`의 `"제10차 인사위원회"`(10자) →
   `"AI데이터팀 주간회의 및 시스템 점검 (자동병합 테스트)"`(31자) 로 교체
2. `PARA_TEXT` 22 B → 64 B, `PARA_HEADER.nChars` `0x8000000B` → `0x80000020`
3. raw deflate 재압축 → OLE 재작성 → `out.hwp`

결과:
- `file out.hwp` → `Hancom HWP (Hangul Word Processor) file, version 5.0` ✔
- **독립 구현(Python 파서)으로 재파싱 성공**, 표 구조 `rows=9 cols=5` 그대로, 나머지 셀 전부 무변경 ✔

> 쓰기 경로가 Node.js만으로 완결됨을 확인 → **파이썬 사이드카 불필요**.
> ([ADR-0002](../adr/0002-typescript-single-runtime.md))

## 8. 병합 엔진에 대한 함의

1. **일반 HWP 편집기를 만들 필요가 없다.** 우리가 만든 이 양식 하나만 다루면 된다.
2. **레코드를 새로 합성하지 않는다.** 항상 마스터 양식의 기존 행을 **복제**한다
   → 테두리·열너비·글자모양·여백이 정의상 보존된다. 이것이 "표 안 깨짐"의 보증 메커니즘이다.
3. 손대는 값은 딱 네 가지다:
   - `TABLE.nRows`, `TABLE.rowSize[]`
   - `LIST_HEADER.rowAddr`
   - `PARA_TEXT` 내용
   - `PARA_HEADER.nChars` (상위 플래그 비트 보존)
4. `PARA_LINE_SEG`는 한글이 문서를 열 때 재계산하므로 복제값 그대로 두어도 무방하다.
   (실험 2에서 텍스트를 3배로 늘렸는데도 정상)

| V-4 | 제출자가 행을 **추가**해서 올린 경우 파싱 | 하 | 파서는 nRows를 읽으므로 자동 대응. 회귀 테스트로 고정 |
| V-5 | 제출자가 셀 안에서 줄바꿈(여러 문단) 사용 | 중 | `LIST_HEADER.문단수 > 1` 처리 — 파서에서 문단 join |
| V-6 | **`cfb`가 추가하는 `\x01Sh33tJ5` 스트림** | 중 | §7.1 참조 — V-1 확인 시 함께 해소됨 |

### 7.1 `cfb` 센티널 스트림 (조사 중 발견) ★

`CFB.write()` 는 출력물에 **4바이트짜리 자체 표식 스트림을 하나 추가**한다.

```
원본  :  9개 스트림
재생성: 10개 스트림   (추가됨: \x01Sh33tJ5)
```

라이브러리 소스(`cfb.js:703 seed_cfb`)를 확인한 결과 **쓰기 경로에서 무조건 주입**된다.
쓰기 직전에 목록에서 지워도 `CFB.write()` 가 다시 넣는다 (실측 확인).

```
sentinel index in read model: 6
sentinel present after strip+write: true      ← 제거 불가
```

**평가**

- SheetJS는 XLS/DOC 출력에도 동일하게 넣으며, 그 파일들은 MS Office에서 정상 동작한다
- HWP 리더는 스트림을 **이름으로 조회**하므로 모르는 스트림은 무시하는 것이 정상 동작이다
- 따라서 위험은 낮지만 **0은 아니다**

**해소 방법**: `fixtures/verify-write-test.hwp` 에 이 센티널이 **이미 들어 있다.**
따라서 V-1(한글에서 열기) 확인 한 번으로 V-6도 같이 판정된다. 별도 작업 불필요.

**실패 시 대안** (우선순위 순)

1. 쓰기 후 버퍼에서 해당 디렉터리 엔트리를 무효화(entry type = 0)하고 형제 포인터 정리
2. 최소 CFB 라이터 자체 구현 (~200줄. 스트림 9개·소형 파일이라 난도 낮음)
3. `.hwpx` 전환 ([ADR-0001](../adr/0001-hwp5-binary-record-engine.md) 되돌리기)

> V-3은 특히 운이 좋다. **"3번 표가 삭제된 정답 파일"이 이미 손에 있으므로**,
> 우리 엔진의 출력과 바이트 비교하여 삭제 로직을 정확히 맞출 수 있다.

## 10. 재현 방법

조사에 쓴 스크립트는 `tools/` 로 정리 예정 (Phase 2 착수 시).

```bash
# 레코드 트리 덤프
python3 tools/hwp5probe.py fixtures/master-template.hwp

# 왕복 동일성 검증
python3 tools/roundtrip.py fixtures/master-template.hwp

# 표 구조 요약
python3 tools/tables.py fixtures/*.hwp
```

고정 샘플은 `fixtures/` 에 커밋되어 있다:

| 파일 | 용도 |
|---|---|
| `master-template.hwp` | 빈 마스터 양식 — 배포·병합의 기준 |
| `sample-filled-w1.hwp` | 실제 취합본 (표1·2가 14행, 표3 삭제됨) |
| `sample-filled-w2.hwp` | 실제 취합본 (표1 10행, 표2 9행, 표3 삭제됨) |
