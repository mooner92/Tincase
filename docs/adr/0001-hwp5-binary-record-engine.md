# ADR-0001. HWP 5.0 바이너리 레코드 엔진을 직접 만든다

- 상태: **채택** (2026-08-13)
- 관련: [S-08](../spec/08-hwp-merge-engine.md), [R-001](../research/001-hwp-format-findings.md)

## 맥락

병합 대상 파일을 리눅스 서버에서 읽고 써야 한다. 원 스펙(§6)은 `pyhwpx`를 제안했다.

실측 결과 전제가 어긋났다.

| 원 스펙의 전제 | 실제 |
|---|---|
| `.hwpx`일 수도 있다 | **`.hwp` 바이너리 확정** |
| 누름틀(필드)이 있을 수도 | **하나도 없음** |
| `pyhwpx`로 처리 | 한글 프로그램 + Windows 필수 → **배포 대상이 리눅스라 불가** |

## 선택지

| 안 | 내용 | 판정 |
|---|---|---|
| A | `pyhwpx` + Windows 상주 PC | ✘ 스펙 §8 "개인 PC 배제"에 위배. 상시성 문제 |
| B | LibreOffice + H2Orestart 변환 | ✘ ODT 왕복에서 표 레이아웃 손상. "표 안 깨짐" 위배 |
| C | `.hwpx`로 양식 전환 후 XML 처리 | △ 전 팀원 워크플로 변경 필요. 최종 제출 형식 리스크 |
| D | **HWP5 레코드 엔진 자체 구현** | ✔ |

## 결정

**D를 채택한다.**

## 근거

이 결정은 추정이 아니라 **실측 검증**에 기반한다.

1. **왕복 바이트 동일성 확인** — 3개 실파일 전부 `serialize(parse(x)) === x` (SHA-256 일치).
   레코드 모델이 무손실임이 증명됐다.
2. **실제 수정·재생성 성공** — 셀 텍스트를 10자→31자로 바꿔 재작성한 파일이
   유효한 HWP로 인식되고, 독립 구현(Python)으로 재파싱됐다.
3. **문제 범위가 좁다** — 범용 HWP 편집기가 아니라 **이 양식 하나**만 다룬다.
   병합 셀 없음, 5열 고정, 필드 없음. 실측으로 확인된 단순 구조다.
4. **"복제 원리"로 서식이 구조적으로 보존된다** — 레코드를 합성하지 않고
   기존 행 바이트를 복사하므로, 서식을 잘못 만들 방법이 없다.

## 결과

**좋은 점**
- 리눅스 순수 코드. 한글·Windows·외부 서비스 의존 없음
- 서식 보존이 우연이 아니라 설계상 보장
- 파일 전체를 완전히 통제. 디버깅 가능
- 왕복 동일성이라는 강력한 테스트 불변식 확보

**나쁜 점**
- 포맷 지식을 우리가 유지해야 한다 → R-001에 실측값을 문서화해 완화
- 한글에서 실제로 열리는지는 자동 검증 불가 → HM-25 육안 체크리스트
- 예상 밖 변형 양식에 취약 → ST-07 업로드 검증 + HM-21 부분 실패

**중립**
- 읽기 경로는 Phase 1부터 업로드 검증에 쓰이므로 Phase 2 전에 실전 검증된다

## 되돌리는 조건

한글에서 생성 파일이 열리지 않고 원인을 특정하지 못하면 → C안(`.hwpx` 전환)으로 전환.
그래서 [Q-01](../../OPEN-QUESTIONS.md) 육안 확인을 **Phase 2 최초 작업**으로 둔다.
