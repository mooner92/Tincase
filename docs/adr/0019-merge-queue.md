# ADR-0019. 마감 병합은 줄 하나에 선다 — 작업 표는 DB에, 일꾼은 프로세스 안에 하나

상태: 채택 · 2026-10-08 · 관련: [08 병합 엔진](../spec/08-hwp-merge-engine.md) HM-54·56·59~61 · [05 API](../spec/05-api.md) API-31a·65 ·
[06 페이지](../spec/06-pages.md) PG-90 · [07 컴포넌트](../spec/07-components.md) CP-130 · [TACP](../../TACP.md) v1.10 TACP-30 · [ADR-0003](0003-sqlite-prisma.md) · [ADR-0009](0009-deadline-as-event.md)

## 맥락

첫 공동 마감(10/15 목 14:00)에 13개 부서가 한 마감을 쓴다. 2026-10-08 검토(코드 감사 · 모델 서버 로그 220건 · 13개 부서 시뮬레이션)에서
1단계(HM-52·53·55·57·58 — 모델 문 · 재시도 · 상주 · 회수 · 같은 부서 겹침 막기)가 들어간 뒤에도 남은 것:

| 남은 것 | 이렇게 터진다 |
|---|---|
| 스케줄러 틱이 병합을 기다린다 | 병합 루프가 15:12를 넘기면 14:45 「승인 막는 부서장」 · 15:00 「본부 준비」 알림 창(각 12분)을 놓친다. 그동안 안전망도 돌지 않는다 |
| [지금 병합]이 요청 안에서 병합을 끝까지 붙잡는다 | 100초를 넘기면 Cloudflare 524 — 사람이 한 번 더 누른다. 1단계는 둘째를 409로 막을 뿐이다 |
| 모델이 도는 사이 저장한 수정이 덮인다 | 시작할 때만 묻는다(HM-49). 1~2분 사이의 부서장 저장은 그 뒤 쓰기에 사라진다 |
| 승인이 실행 번호에 묶여 있다 | 같은 입력으로 다시 병합하면 바이트가 같아도 「승인 뒤 바뀜」 · 검토 요청이 다시 간다 |
| 다 끝났는지 아무도 모른다 | 실패 알림은 그 부서 담당자 개인에게만. 운영자 · 기획조정실은 15:00 미도착 목록에서야 안다 |

## 결정

1. **시각표가 아니라 줄 하나.** 부서 하나에 6초가 걸릴 때도 125초가 걸릴 때도 있다(실측) — 시작 시각을 띄우면 빨리 끝난 만큼 버리고 늦게 끝난 만큼 겹친다.
   모든 병합(자동 · 마감 열기 닫힘 · [지금 병합] · [다시 병합])을 작업 표 `MergeJob`에 넣고 앞의 것이 끝나면 바로 다음을 한다. 알림은 이미 부서마다
   끝난 시각을 따라간다(HM-50).
2. **상태는 DB에, 실행은 프로세스 안 일꾼 하나.** 프로세스는 하나이고 DB는 SQLite다(ADR-0003). 재시작에도 줄이 남아야 하므로 작업은 표에 두고,
   일꾼의 상태는 `globalThis`에 둔다(Next가 모듈을 번들 층마다 따로 실어도 하나 — HM-52a와 같은 이유). 죽은 작업은 lease로 가른다 —
   기동 때 `running`은 모두 죽은 것, 그 뒤에는 `leaseUntil`이 지난 것. 프로세스가 둘이 되면 lease를 DB 임대로 바꾼다(12 「남은 위험」과 같은 자리).
3. **`MergeRun`에 `queued`를 끼우지 않는다.** 「가장 최근 실행」을 고르는 질의가 여러 곳이라 흔들린다. 작업(줄)과 실행(결과)을 나눈다.
4. **순서 — 제출 수가 적은 부서부터, 같으면 이름순** (사용자 결정 「순서는 크게 중요하지 않다 — 단순하게」). 전체 시간은 같고 「누가 늦게 끝나나」만 바뀐다.
   작은 부서부터 하면 +10분 전에 끝나는 부서가 가장 많다. 운영자가 정하는 순서 열은 두지 않는다. 그 밖은 넣은 순서(FIFO)다.
5. **같은 부서는 합류한다.** 대기 중이면 그 작업에, 병합 중이면 그 작업에(그 사이 새 제출 · 덮기 확인이 생겼으면 끝난 뒤 한 번 더). 같은 부서 병합이 동시에 둘이 될 수 없다.
6. **틱은 넣기만 한다.** 판정(HM-34 · 43 · 45 · 49)은 그대로이고 병합은 일꾼이 한다 — 3단계 알림 · 맞추기가 줄과 상관없이 매분 돈다.
7. **[지금 병합]은 202.** `{ jobId, position, joined }`를 바로 주고 화면이 2초마다 묻는다.
8. **쓰기 직전에 다시 본다.** 줄에 넣은 뒤 누가 고쳐 저장했거나 승인했으면 쓰지 않는다(덮기를 확인한 요청은 예외). 자동 작업은 최종본만 지킨다 —
   마감 전 미리보기는 마감이 덮는다(ADR-0009 「마감은 이벤트」).
9. **승인은 내용에 묶는다.** 유효한 승인 = 가장 최근 승인의 sha가 지금 파일의 sha와 같다. 같은 입력의 병합본이 바이트까지 같으므로(HM-T21 · T147 · T168) 별도의 정규화 열쇠는 두지 않는다.
10. **「병합 점검」은 운영자와 기획조정실 담당이 받는다** (사용자 결정). 줄이 빈 순간 · 늦어도 마감 +15분에 한 통, 남은 부서가 있었으면 다 끝날 때 「완료」 한 통.
    받는 사람이 넓어지는 것이라 TACP v1.10(TACP-30)에 적었다 — 문서 내용 · 사람 이름 없이 부서 이름과 상태만, 보낸 기록은 `NotifyLog`.
11. **10분을 넘겨도 모델을 계속 쓴다** (사용자 결정 — 품질 먼저). 시간을 맞추려 남은 부서를 모델 없이 처리하지 않는다. 대신 요약이 「아직 n곳 · 예상 끝」을 사실대로 말한다.

## 고르지 않은 것

- **cron · 외부 큐(Redis 등)** — 이 앱은 스케줄러를 앱 안에 둔다(HM-25 — 배포 · 이관 때 조용히 빠지지 않게). 프로세스 하나 · SQLite에 큐 서버를 더할 이유가 없다.
- **일꾼 여럿** — 모델 서버가 한 번에 하나만 처리한다(NUM_PARALLEL=1). 일꾼을 늘려도 모델 문(HM-52) 앞에서 다시 줄을 선다 — 기다림만 예산(HM-57b)을 먹는다(1단계 검증 시뮬레이션에서 그것으로 표 2개가 폴백했다).
- **2차 모델 병합을 지금 넣기** — 사용자 결정은 「검토 요청이 나가기 전에만」이다. 승인이 내용에 묶여야 안전하게 들일 수 있어 이번에는 그 바탕(HM-56)만 넣고 3단계로 둔다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 일꾼이 매달린다(약속이 끝나지 않음) | lease(멈춤 기준 + 1분)가 지나면 매분 회수해 다시 대기로 — 쥐고 있던 일꾼은 버리고 다음 일꾼이 잇는다(HM-59e). 실행 예산(HM-57b)이 모델 쪽을 끊으므로 드물다 |
| 재시작 사이에 작업이 사라진다 | 표에 있다 — 기동 때 `running`은 다시 대기(두 번째 회수부터는 실패), 그리고 일꾼을 깨운다 |
| 스케줄러가 꺼진 서버(테스트 · 시연) | 일꾼은 넣을 때 깨어나므로 [지금 병합]은 그대로 돈다. 알림 판정 고리만 걸지 않는다(예전과 같다) |
| 개발 스크립트가 같은 DB에서 병합한다 | 줄 밖이다. 1단계의 막이(HM-58 — DB의 running 행)가 그대로 409 `merging` · `busy`로 막는다 |
