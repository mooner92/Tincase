# ADR-0009 — 마감은 이벤트다

- 상태: 채택 (2026-08-27)
- 관련: HM-25 · HM-34 · HM-35 · NT-40 · NT-41 · [ADR-0008](0008-head-principal.md)

## 맥락

2026-08-27 목요일, AI홍보전략실에서 자동 병합이 실행되지 않았다. 아무 오류도 나지 않았고
아무도 몰랐다. 담당자가 화면에서 「병합 시각 10:37」을 보고 이상하다고 느껴 확인하면서 드러났다.

일어난 일:

| 시각 | |
|---|---|
| 10:37 | 담당자가 **미리 한번** 병합해 봄 (제출 4건) |
| 13:29 · 13:33 · 13:49 | 세 명이 제출 (총 7건) |
| **14:00** | **자동 병합 — 실행되지 않음** |
| 14:13 | 부서장에게 「병합본 준비됐어요, 검토 부탁드려요」 **발송됨** |

부서장은 세 명이 빠진 문서를 온전한 것으로 알고 검토했다.

원인은 한 줄이었다.

```ts
const done = await prisma.mergeRun.findFirst({
  where: { divisionId, weekSlotId, status: 'succeeded' },
});
if (done) { skipped++; continue; }   // 10:37 것이 여기 걸렸다
```

「이미 되어 있으면 건너뛴다」는 의도는 옳았다. 틀린 것은 **「되어 있다」의 정의**였다.

## 문제

이 결함에는 세 가지 성질이 겹쳐 있어서, 하나만 고치면 다른 형태로 다시 난다.

1. **자연스러운 행동이 기능을 껐다.** 마감 전에 병합을 눌러 보는 것은 실수가 아니라 확인이다.
   그런데 그 확인 한 번이 그 주 자동 병합을 영구히 무력화했다. 매주 재현될 수 있었다.
2. **조용했다.** 실패가 아니라 «건너뜀»이라 로그도 경고도 없다.
3. **알림이 거짓을 말했다.** 이게 제일 나쁘다. 병합이 안 된 것보다,
   **안 된 것을 「됐다」고 알려서 사람이 낡은 문서를 검토하게 만든 것**이 나쁘다.
   알림이 틀리면 다음부터 알림을 안 믿는다.

## 결정

**마감은 이벤트다.** 마감 시각이 지나면, 그때까지 제출된 것으로 **최종본을 반드시 한 번 만든다.**

따라서:

1. **마감 전 실행은 미리보기다.** 몇 번을 돌렸든 최종본을 대신하지 못한다.
   판정에 이름을 준다 — `hasFinalMerge(divisionId, weekSlotId, deadline)`,
   조건은 `status = 'succeeded' AND startedAt >= deadline`.
2. **알림도 최종본만 본다.** 미리보기를 「준비됐어요」로 가리키지 않는다.
3. **병합 중이면 알림을 미룬다.** 14:10에 아직 돌고 있으면 「병합본이 없어요」를 보내지 않는다 —
   멀쩡히 되고 있는 것을 다시 누르게 만들고, 그 알림이 「보냄」으로 기록돼 진짜 검토 요청을 막는다.
4. **정각이 아니라 +1분에 시작한다.** 마감 판정은 «정각까지 허용»(WS-06)이라
   14:00:00.000 업로드가 유효하다. 그 요청이 파일 저장·DB 기록을 끝낼 틈을 준다.
5. **스케줄러 주기를 5분 → 1분으로.** 위 시각들이 분 단위인데 5분 주기로는 맞출 수 없다.
   실제로 그날 알림은 전부 **3분씩 늦게** 나갔다(13:03 · 14:13 · 14:33) — 컨테이너가 뜬
   시각이 tick의 위상이 되기 때문이고, 최악의 경우 5분까지 밀린다.

목요일 오후는 이렇게 흐른다:

```
14:00  마감 — 제출 잠김                             (WS-06)
14:01  자동 병합 시작                               (HM-25·HM-35)
14:10  실/팀장: 「병합본 준비됐어요, 검토 부탁드려요」  (NT-40)
       └ 실패 시 → 담당자에게 「지금 병합을 눌러주세요」
14:30  담당자: 「최종 확인하고 제출해주세요」          (NT-40)
15:00  대외업무 마감
```

## 대안

**제출 집합을 대조해 낡으면 다시 병합한다** — 병합본의 `sourceIds`가 현재 최신 제출을 전부
담고 있지 않으면 재실행. 더 일반적이고 마감 후 지각 제출까지 잡는다.

채택하지 않은 이유: 병합이 어떤 제출을 소스에서 빼는 경우(파싱 실패 등)
**매 주기마다 영원히 재실행**된다. 마감 후에는 제출이 잠기므로(WS-06) 이 대조가 잡아낼 것이
정상 상태에서는 없고, 대신 무한 재실행이라는 새 실패 양식을 들여온다.

대조 자체는 남겼다 — 다만 **재실행이 아니라 알림 한 줄**로 쓴다
(「병합한 뒤에 N명이 더 냈어요」). 정상이면 0이라 한 글자도 나오지 않고,
0이 아니면 그건 이 ADR의 가정이 깨졌다는 뜻이다. 처분이 알림 한 줄이면 오탐 비용이 없다.

## 결과

- 마감 전 미리보기가 자동 병합을 끄지 않는다. 회귀는 `[HM-T40]`이 잡는다
  — 고친 코드를 되돌려 실제로 빨간불이 뜨는 것을 확인했다.
- 알림 오차가 5분 → 1분 미만.
- 1분 주기의 비용: 각 작업이 발송 창 밖이면 질의 한 번에 빠져나온다.
  부서 목록 조회 3회 + 부서당 순수 계산이 전부다.
- **남은 위험**: 담당자가 마감 후에 손으로 병합한 뒤 그것을 고쳐 두면, 그 편집은
  재병합으로 사라진다. 지금은 재병합이 사람의 버튼이라 스스로 덮어쓰는 일은 없지만,
  자동 재실행을 나중에 들이려면 이 지점을 먼저 풀어야 한다.
