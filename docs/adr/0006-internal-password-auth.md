# ADR-0006. 사내망 직접 접속 + 비밀번호 인증, Cloudflare는 운영자 외부 통로로 한정

- 상태: **채택** (2026-08-14, 사용자 결정)
- 관련: [S-03](../spec/03-auth.md), [ADR-0004](0004-cloudflare-access-as-identity.md) 개정
- 영향: AU-01(바인딩 정책) 개정 · AU-20~26 신설

## 맥락

v1.0.0은 Cloudflare Access를 유일한 신원 제공자로 삼고 앱을 `127.0.0.1`에만 바인딩했다.
가동 후 실제 사용 관점에서 두 가지 문제가 드러났다.

1. **사내 서버인데 사내 트래픽이 외부를 왕복한다.** 같은 건물의 PC → 인터넷 → Cloudflare 엣지 →
   터널 → 같은 건물 서버. 지연과 외부 의존이 업무 도구의 상시 경로에 놓인다.
2. **외부 의존을 전 직원 규모로 확대하는 부담.** 337명 전원의 접근을 외부 서비스 정책에 묶는 것은
   사내 도구의 신뢰 모델로 과하다.

사용자 판단: **"Cloudflare는 나만 외부 접속할 수 있게 뚫어놓고 나머지는 내부망을 쓰는 게 맞다."**

### 대안 조사 (실측)

사내망 직접 접속에는 자체 신원 확인이 필요하다. 서버에서 실제로 확인한 결과:

| 방식 | 실측 결과 | 판정 |
|---|---|---|
| KEI SMTP 릴레이로 메일 OTP | `spam.kei.re.kr` 25/465/587 **전부 차단** | ✘ 불가 |
| LDAP / AD 연동 | `ldap.kei.re.kr`·`ad.kei.re.kr` DNS 없음, 389/636 닫힘 | ✘ 불가 (IT 협의 필요) |
| 외부 SMTP(Gmail 등)로 OTP | `smtp.gmail.com:465` 열림 → 기술적으로 가능 | △ 외부 의존을 다시 도입 |
| **비밀번호 + 세션** | 외부 의존 0 | ✔ **채택** |

메일 OTP·AD는 KEI IT 협의 없이는 불가능하므로, **자립적으로 지금 되는 유일한 길이 비밀번호**다.

## 결정

**신원 제공자 두 개를 같은 seam 뒤에 둔다.**

```
사내망 <서버-내부-IP>:11111 ──► 세션 쿠키 (비밀번호 로그인)  ──┐
                                                              ├─► AccessIdentity ─► 인가(authz)
외부 worklog.excusa.uk ──────► Cloudflare Access JWT ─────────┘
```

1. **비밀번호 인증** — scrypt 해시(Node 내장, 네이티브 의존 없음). 운영자가 임시 비밀번호를
   랜덤 발급해 배포하고, **첫 로그인 시 변경을 강제**한다 (AU-22).
2. **세션 30일** — 재로그인 피로도를 줄이기 위한 사용자 결정. 슬라이딩 갱신, DB 저장으로 즉시 폐기 가능.
3. **Cloudflare Access는 운영자(Sean) 외부 통로로 한정** — Access 정책을 그의 이메일 하나로 좁힌다.
4. **바인딩을 LAN으로 개정** — `0.0.0.0:11111`. AU-01의 "127.0.0.1 전용"은 인증이 앱에 없던
   시절의 방어였다. 이제 앱 자체가 인증하므로 LAN 노출이 정당해진다.

## 근거

- 앱에 이미 `verifyAccess(headers) → AccessIdentity` 라는 **인증 seam이 있었다.**
  덕분에 이 변경은 재작성이 아니라 **가산적(additive)** 이다 — 인가 계층(`authz.ts`)은
  신원이 어디서 왔는지 모른 채 그대로 동작하고, 격리 스위트도 손대지 않았다.
- 비밀번호는 337명 규모에서 관리 부담이 있지만, **발급은 부서 온보딩 시 1회**이고
  이후는 본인 관리다. 파일럿은 12명이라 즉시 검증 가능하다.
- 외부 의존이 사라져 Cloudflare·인터넷 장애가 사내 업무를 막지 않는다.

## 결과

**좋은 점**
- 사내 트래픽이 사내에 머문다. 지연·외부 의존 제거
- 전 직원 확산 시 외부 서비스 정책에 묶이지 않는다
- 운영자만 외부 통로를 가지므로 외부 노출면이 최소화된다

**나쁜 점**
- **사내망은 평문 HTTP다.** 비밀번호와 세션 쿠키가 LAN을 평문으로 지나간다 (AU-26).
  사내망 도청 위험은 낮지만 0은 아니다 — 완화안은 AU-26에 기록
- 비밀번호 재발급 요청이 운영자에게 온다 (셀프 리셋 경로가 없다 — 메일 발송이 불가하므로)
- 초기 비밀번호 배포를 안전한 경로로 해야 한다 (개인별 전달, 출력물 폐기)

**중립**
- Cloudflare Access 설정 자체는 그대로 쓰되 정책 대상만 좁힌다. 이미 만든 코드는 그대로 유효

## 되돌리는 조건

KEI IT가 LDAP/AD 또는 사내 SMTP 릴레이 접근을 열어주면, 같은 seam에 제공자를 하나 더 붙여
비밀번호를 단계적으로 폐지할 수 있다. 그때도 `authz.ts`는 손대지 않는다.
