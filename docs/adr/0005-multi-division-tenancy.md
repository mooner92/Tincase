# ADR-0005. 단일팀 도구가 아니라 부서 단위 멀티테넌트 플랫폼으로 만든다

- 상태: **채택** (2026-08-13, 사용자 지시)
- 관련: [R-002](../research/002-kei-org-and-collection-flow.md), [S-00](../spec/00-overview.md), [S-01](../spec/01-domain-model.md), [S-03](../spec/03-auth.md)

## 맥락

초기 스펙은 "AI홍보전략실 1개 부서, 8명, 관리자 1명(Sean)"의 단일팀 도구였다.

조사(R-002) 결과 전사 구조가 드러났다:

- 주간업무 수합은 2단계다 — **부서 내부 수합 → 기획조정실 취합게시판**.
- 부서 내부 수합의 고통(부서원 취합·병합)은 Sean만의 것이 아니라
  **부서별 실무자 12명 내외가 매주 동일하게 겪는다.**
- 기획조정실 공식 지침이 "부서별 특성을 고려한 양식 선택"을 허용한다 — 부서마다 양식이 다르다.

사용자가 방향을 확정했다: 부서별 페이지(영문 슬러그 URL), 부서 간 완전 격리,
부서별 담당자의 병합 규칙 설정·파일 열람·원버튼 병합, 저장은 `/data`.

## 결정

**부서(Division)를 테넌트로 하는 멀티테넌트 플랫폼**으로 설계한다.

1. **테넌트 = 부서.** 각 부서는 자기 페이지(`/{영문슬러그}`), 자기 부서원 명단, 자기 마스터 양식,
   자기 병합 규칙, 자기 마감 정책을 가진다.
2. **격리가 기본값.** 부서 간에는 제출 현황·파일·존재 여부까지 서로 보이지 않는다 (404).
   "다른 부서원이 냈는지 안 냈는지"를 볼 수 있는 화면은 어디에도 없다 — 감시 방지가 명시 요구사항.
3. **역할은 부서 스코프.** `member`(부서원: 업로드) / `lead`(담당자: 현황·열람·규칙·병합) +
   플랫폼 전역 `operator`(테넌시 관리만, 내용 접근 없음 — AU-15).
4. **소속은 명시적 배정.** 조직도에서 기계적으로 유도하지 않는다 — 하위 실 소속 실무자가
   상위 본부 명의로 제출하는 실사례가 있다 (R-002 §4).
5. **AI홍보전략실이 첫 테넌트(파일럿).** 다른 부서는 파일럿 검증 후 온보딩 (Phase 3).

## 근거

- 같은 기능이 N개 부서에 반복 적용되는 구조 — 단일팀 하드코딩과 멀티테넌트의 구현 비용 차이가
  이 규모(부서 12~30개, 전 직원 337명)에서는 크지 않은데, 가치는 12배 이상이 된다.
- 부서별 양식·규칙 차이가 **공식적으로 존재**하므로, 전역 설정 1벌 모델은 어차피 성립하지 않는다.
- 포트폴리오 목표(스펙 §2)와도 정합 — 실사용자 있는 멀티테넌트 운영 경험.

## 결과

**좋은 점**
- Sean의 도구가 아니라 기관의 도구가 된다. 실무자 12명이 잠재 사용자
- 부서별 양식/규칙 요구를 정면으로 수용
- 격리가 스키마·인가 계층에 구조적으로 들어간다 (뒤늦게 붙이는 것보다 훨씬 싸다)

**나쁜 점**
- Phase 1 범위 증가 (부서 페이지·역할·격리·부서별 양식 관리) — 추정 +2~3일
- Cloudflare Access 정책이 이메일 8개 나열로는 못 버틴다 → 도메인 규칙 + DB 게이트로 전환 필요 (Q-13)
- 온보딩·지원 부담 — 파일럿 후 단계적 확대로 완화 (Phase 3)

**중립**
- 단일 부서만 쓰는 동안에는 사실상 기존 설계와 동일하게 동작한다 (테넌트 1개인 플랫폼)
- 2단계(취합게시판 제출)는 계속 사람이 한다 — 자동화 범위 밖 (S-00 비목표)

## 되돌리는 조건

파일럿(AI홍보전략실) 후 타 부서 수요가 실제로 없으면, 멀티테넌트 구조는 그대로 두되
온보딩(Phase 3)만 하지 않는다. 구조를 단일팀으로 되돌릴 이유는 없다 — 비용이 이미 지불된 뒤이므로.
