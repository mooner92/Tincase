# ADR-0004. Cloudflare Access를 신원 제공자로 삼고, JWT를 앱에서 검증한다

- 상태: **채택** (2026-08-13)
- 관련: [S-03](../spec/03-auth.md)

## 맥락

스펙 §5는 로그인을 만들지 말고 기존 Cloudflare Zero Trust(`aidt-kei` / `excusa.uk`)를
재사용하라고 했다. 방향은 옳다. 문제는 **앱이 신원을 어떻게 받느냐**다.

가장 흔한 구현은 Cloudflare가 넣어 주는 헤더를 그대로 믿는 것이다.

```
Cf-Access-Authenticated-User-Email: someone@kei.re.kr
```

이 헤더는 **평문이고 위조 가능**하다. 오리진에 직접 닿을 수 있는 누구든 아무 값이나 넣을 수 있다.

이 서버는 이미 `0.0.0.0`에 여러 포트(`80`, `3100`, `3101`, `5000`, `8003`, …)를 열어 두고 있다.
같은 실수를 한 번만 하면 사내망 전체에 무인증 관리자 권한이 열린다.

## 결정

**Access를 신원 제공자로 쓰되, 앱은 `Cf-Access-Jwt-Assertion` JWT를 암호학적으로 검증한다.**
동시에 앱을 `127.0.0.1`에만 바인딩한다.

두 겹을 **모두** 건다.

| 층 | 수단 | 막는 것 |
|---|---|---|
| 네트워크 | `127.0.0.1:11111` 바인딩 (AU-01) | 오리진 직접 접근 |
| 암호학 | JWKS 서명 + `iss`/`aud`/`exp` 검증 (AU-02) | 헤더 위조 |

## 근거

1. **심층 방어** — 어느 한쪽이 잘못 설정돼도 다른 쪽이 막는다
2. **안전한 실패** — Access 앱 생성을 빼먹으면 JWT가 없고, 앱은 **모든 요청을 거부**한다.
   설정 실수의 결과가 "전체 공개"가 아니라 "아무도 못 들어옴"이 된다
3. **비용이 낮다** — `jose` 라이브러리로 20줄. JWKS 캐시는 자동
4. 사칭 방지와 결합 — 검증된 신원으로만 업로더를 정하므로(AU-05) 이름 선택 UI가 사라진다

## 결과

**좋은 점**
- 로그인·세션·비밀번호·CSRF를 만들지 않는다 (스펙 §5 목표 달성)
- MAC 등록 제약 우회 (스펙 §5) — 사내 미등록 기기에서도 접근
- 퇴사자 차단은 Access 정책에서 즉시

**나쁜 점**
- `CF_ACCESS_AUD` 설정이 필요하다 ([Q-04](../../OPEN-QUESTIONS.md))
- 로컬 개발에 우회로가 필요 (AU-03) → production에서 차단됨을 테스트로 고정 (AU-T03)
- Cloudflare 장애 시 접근 불가 → 8명 사내 도구에서 수용 가능. 최후 수단은 OPS-18

**중립**
- 터널이 **원격 관리형**이라 서버에서 손댈 설정 파일이 없다.
  대시보드 작업만 필요하고 **cloudflared 재시작이 불필요**하다 (AU-10).
  기존 서비스에 영향을 주지 않는다는 뜻이라 오히려 유리하다.
