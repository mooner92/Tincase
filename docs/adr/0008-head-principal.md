# ADR-0008 — head(부서장) Principal 신설

일자: 2026-08-26 · 상태: 채택 · 관련: TACP v1.3 · ADR-0005

## 배경

취합게시판 담당자 정리(v1.23.0 데이터 작업) 과정에서 실제 조직의 역할이 드러났다:

- **부서담당자(lead)** — 답변일자를 적는 사람. 병합본을 받아 취합게시판·웹디스크에 **제출**한다.
- **실·본부·단·센터장** — 부서의 장. 병합본을 **검토**하고, 잘못된 내용을 담당자를 통해
  고치게 한다. 제출은 하지 않는다.

지금까지 장(長)들은 `onRoster=false`(집계 제외)인 member였다. 그래서 병합본을 열람할 수는
있어도(TACP-15) **수정할 수 없고, 수합 관리 화면도 볼 수 없다.** 사용자(운영자) 확인:
실·팀장들이 "본인이 보고 수정을 좀 하고 싶어" 한다 — 검토 권한의 실수요가 있다.

## 결정

**다섯 번째 Principal `head`를 신설한다.** 판정식은 `divisionRole === 'head'`.

**부서 문서에 대한 권한은 lead와 완전히 같다** — 열람·양식·규칙·병합 실행·병합본 수정.
권한을 조각내지 않는 이유: "볼 수는 있는데 못 고치는" 중간 단계를 만들면 행렬 칸이 늘고,
장이 담당자에게 "이것 좀 고쳐줘"라고 말하는 것과 직접 고치는 것 사이에 보안 경계가 없다.
어차피 같은 부서 문서다.

**lead와 다른 것은 권한이 아니라 책임(알림)이다:**

| | lead (담당자) | head (부서장) |
|---|---|---|
| 병합 후 알림 | **+30분** — "최종 확인하고 제출해주세요" | **+10분** — "검토해주세요" |
| 병합 실패 알림 | **+10분** — "지금 병합을 눌러주세요" | 받지 않는다 (고칠 수 없는 사람에게 실패는 소음이다) |

## 하지 않는 것

- **사람 관리는 여전히 operator만** (TACP-3). head는 명단·역할을 못 바꾼다.
- **남의 제출물 삭제 불가** (TACP-14 변경 없음). lead와 같은 이유다.
- **타 부서는 여전히 404** (TACP-4·5). head는 자기 부서의 장이지 전사 역할이 아니다.
- **readAll 아님.** coordinator·operator만 전 부서를 읽는다.

## 데이터 유도

ERP 인원 현황의 `직책` 열에서 기계적으로 유도한다 (수동 지정 아님):

| 직책 | 역할 | 집계 |
|---|---|---|
| 실장 · 본부장 · 단장 · 센터장 | `head` | 제외 (`rosterNote` = 직책) |
| 원장 · 경영부원장 · 연구부원장 | `member` | 제외 — 원장단은 부서의 장이 아니다 |
| 담당 | `member` (lead는 수동 지정만) | 포함 (휴직 등 수동 예외 보존) |

lead는 어떤 유도 규칙으로도 만들어지지 않는다 — 취합게시판 답변일자 기재자를
운영자가 직접 지정한다. 한 사람이 lead이면서 직책이 장인 경우 lead가 이긴다(제출 책임 우선).

## 결과

- TACP §2 "Principal은 네 가지다" → **다섯 가지**로 개정 (v1.3)
- `Scope.isHead` 신설, 문서 게이트는 `isManager = isLead || isHead`로 판정
- `requireLead` → `requireManager`로 개명 (이름이 거짓말하면 게이트가 아니다)
