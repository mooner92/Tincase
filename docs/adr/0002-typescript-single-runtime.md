# ADR-0002. 병합 엔진을 TypeScript로 구현한다 (파이썬 사이드카 없음)

- 상태: **채택** (2026-08-13)
- 관련: [ADR-0001](0001-hwp5-binary-record-engine.md), [S-08](../spec/08-hwp-merge-engine.md)

## 맥락

ADR-0001로 레코드 엔진을 직접 만들기로 했다. 어느 언어로?

hwp 관련 생태계는 파이썬에 있고, 초기 조사도 파이썬으로 했다.
반면 앱은 Next.js(Node)다. 파이썬을 쓰면 프로세스가 둘이 된다.

## 선택지

| 안 | 구성 | 비용 |
|---|---|---|
| A | Python FastAPI 사이드카 | 컨테이너 2개, HTTP 계약, 배포·모니터링 2벌 |
| B | Node에서 파이썬 스크립트 spawn | 프로세스 관리, 오류 전파, 직렬화 |
| C | **TypeScript 단일 런타임** | 라이브러리를 새로 확인해야 함 |

## 핵심 쟁점: OLE 컨테이너 쓰기

읽기는 어느 쪽이든 쉽다. **문제는 쓰기다.**

파이썬 `olefile`은 **읽기 전용**이다. OLE 복합 문서를 쓰려면 직접 구현해야 한다.
즉 "파이썬이 유리하다"는 통념이 이 작업에는 성립하지 않는다.

실측 확인:

```
npm cfb 1.2.2 (SheetJS)
  CFB.read()          → 실제 .hwp 9개 스트림 정상 읽기 ✔
  CFB.write()         → 존재 ✔
  CFB.utils.cfb_add() → 존재 ✔
```

**Node 쪽에 읽기·쓰기가 모두 되는 성숙한 OLE 라이브러리가 있다.**
그리고 raw deflate는 `node:zlib`에 내장(`inflateRawSync`/`deflateRawSync`)이다.

R-001 실험 2에서 **Node.js만으로 .hwp 수정·재생성에 성공**했다. 검증 완료.

## 결정

**C를 채택한다.** `cfb` + `node:zlib` + 자체 레코드 계층.

## 근거

1. 필요한 기능이 Node 쪽에 다 있고 **실제로 동작을 확인했다**
2. 컨테이너 1개, 런타임 1개, 테스트 러너 1개, 배포 1벌
3. API 라우트에서 엔진을 직접 호출 — IPC·직렬화 없음
4. 타입이 API 계약부터 레코드 오프셋까지 일관
5. 파이썬을 써도 OLE 쓰기를 직접 구현해야 하므로 **파이썬의 이점이 없다**

## 결과

**좋은 점**
- 배포·운영 단순화 ([S-09](../spec/09-deployment-ops.md) 컨테이너 1개)
- 업로드 검증(ST-07)에서 같은 코드 재사용
- 이미지 작아짐 (파이썬 런타임 불필요)

**나쁜 점**
- 파이썬 hwp 생태계의 참고 코드를 직접 못 쓴다 → 어차피 우리 요구에 맞는 것이 없었다
- Node의 바이너리 처리는 파이썬 `struct`보다 장황 → `Buffer.readUInt16LE` 등으로 충분
- **`cfb`가 `\x01Sh33tJ5` 센티널 스트림을 무조건 추가한다** (제거 불가, 실측 확인).
  위험은 낮고 [Q-01](../../OPEN-QUESTIONS.md)에서 함께 판정된다.
  문제가 되면 최소 CFB 라이터를 직접 구현한다 — 스트림 9개·수십 KB 규모라 ~200줄.
  이 경우에도 파이썬 `olefile`은 읽기 전용이라 **파이썬으로 옮길 이유는 여전히 없다.** ([HM-08a](../spec/08-hwp-merge-engine.md))

**중립**
- 조사 단계 파이썬 스크립트는 `tools/`에 **교차 검증용**으로 남긴다.
  독립 구현 2개로 서로를 검증하는 것은 오히려 자산이다 (실험 2에서 실제로 그렇게 썼다).
